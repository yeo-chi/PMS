# 숙박 예약 플랫폼 기획 문서

## 1. 개요

### 1.1 배경
자사 숙박 상품을 자사 서비스 및 다수의 외부 OTA(Online Travel Agency)에 동시 노출/판매한다. 동일 상품이 여러 채널에서 동시에 예약될 수 있으므로, 예약·취소·변경 요청을 **멱등하게, 중복/누락 없이** 처리하고, 채널 간 재고 정합성을 보장하는 시스템이 필요하다.

### 1.2 운영 조건
- 모든 건물은 **무인 운영**이며, 프론트 데스크(워크인) 채널은 존재하지 않는다. 예약은 **자사 서비스**와 **OTA**를 통해서만 발생한다.
- OTA는 두 가지 연동 방식이 존재할 수 있다.
  - **동기(Sync)**: OTA가 우리 응답(성공/거부)을 즉시 받아 자기 UX에 반영
  - **비동기(Async/통보형)**: OTA가 자체적으로 예약을 먼저 확정하고, 우리에게는 결과만 통보. 우리 응답을 기다리지 않음
- 본 문서는 **OTA가 통보형(Async)** 이라는 가정을 기준으로 설계한다. (가장 보수적이고 복잡한 케이스를 기준으로 하면 동기 케이스는 서브셋으로 커버됨)

### 1.3 시스템 구성
서버는 두 개의 서브모듈로 분리한다.

| 서버 | 역할 |
|---|---|
| **예약 서버 (Reservation Server)** | 호스트/OTA로부터의 예약·취소·취소요청 인입 처리. 예약 테이블, 예약 히스토리 테이블 소유. 이벤트 발생 시 운영 서버로 통보(API 호출) |
| **운영 서버 (Operation Server)** | Transactional Outbox 패턴으로 OTA·호스트에게 최종 통보 전달. 호스트, OTA, 방(상품) 정보 테이블 소유 |

## 2. 도메인 정의

### 2.1 액터
- **OTA**: 외부 예약 플랫폼 (Booking.com, Agoda 등). 예약/취소를 호출할 수 있고, 취소통보를 보내온다.
- **호스트(Host)**: 숙소 운영 주체. 시설 문제, 오버부킹 정리 등의 사유로 **취소요청**을 발의할 수 있다.
- **자사 서비스**: 자체 예약 채널. OTA와 동일한 방식으로 예약 서버에 요청을 보낸다 (하나의 "채널"로 취급).

### 2.2 액터별 가능 액션

| 액터 | 가능 액션 | 비고 |
|---|---|---|
| OTA | 예약 요청, 취소요청, **취소통보** | 통보형이므로 우리 응답을 기다리지 않음 |
| 호스트 | 취소요청 | 직접 취소 확정 권한 없음. 반드시 OTA 협의를 거쳐야 최종 확정 |
| 자사 서비스 | 예약 요청, 취소요청 | 결제까지 자사가 직접 처리하는 채널 |

### 2.3 핵심 원칙 — 취소 확정 시점
> **"누가 취소를 시작했든, 최종 확정 시점은 항상 OTA의 취소통보가 도착한 시점이다."**

- OTA발 취소: OTA가 고객과 이미 협의를 마치고 보내는 취소통보 → 도착 즉시 확정
- 호스트발 취소: 호스트는 취소를 "요청"만 할 수 있고, 대상 OTA에 취소요청을 전달한 뒤 **OTA의 취소통보가 돌아와야** 비로소 확정된다. 그 전까지 재고는 계속 점유 상태(`PENDING_CANCEL`)로 유지한다. (OTA가 협의 중 재판매가 발생하는 모순을 방지)

## 3. 시스템 아키텍처

```
                 ┌─────────────┐        ┌─────────────┐
   OTA / 자사  ──▶│  예약 서버   │──통보──▶│  운영 서버   │──▶ OTA / 호스트
   (예약/취소/    │ Reservation │  (API)  │ Operation   │   (Outbox 발송)
    취소요청)     │   Server    │◀──────  │   Server    │
                 └─────────────┘  요청    └─────────────┘
                 - reservations         - hosts
                 - reservation_history  - ota_channels
                                        - rooms (상품)
                                        - outbox_events
```

- **예약 서버**: 재고 정합성(중복 예약 방지)과 예약 상태 관리에 집중하는 도메인. 외부/내부 요청을 받아 판정하고, 판정 결과를 운영 서버에 통보만 한다.
- **운영 서버**: 채널(OTA/호스트) 정보와 상품 마스터 데이터를 관리하며, 예약 서버로부터 온 이벤트를 실제 외부 채널로 "확실하게 전달"하는 책임을 진다. Transactional Outbox 패턴으로 발송 실패 시 재시도를 보장한다.
- 두 서버 간 통신도 신뢰성이 필요하므로 동일한 멱등성/재시도 원칙이 적용된다 (상세는 6장).

## 4. 시나리오별 처리 흐름

### 4.1 OTA 예약 요청
```
OTA → 예약 서버: 예약 요청 (product_id, start_date, end_date)
예약 서버: 중복 재고 판정
  ├─ 가능 → 예약 확정 (reservations 반영, history 기록)
  └─ 불가 → 거부 판정 (이미 다른 채널에서 선점됨)
예약 서버 → 운영 서버: 확정/거부 결과 통보
운영 서버 → 대상 OTA: 확정 통보 or 거부 통보
운영 서버 → 그 외 관련 채널: 재고 마감 통보 (필요 시)
```
- OTA가 통보형이므로 예약 서버의 판정 결과와 무관하게 OTA는 이미 자사 고객에게 확정 안내를 했을 가능성이 있다.
- **거부 판정이 나는 경우** = 두 채널에서 겹치게 예약이 들어온 "오버부킹" 상황. 이 경우 나중에 도착한 요청을 자동으로 취소 처리하고, 해당 채널에는 **"중복예약으로 인한 취소"** 사유로 통보한다.

### 4.2 OTA 취소통보
```
OTA → 예약 서버: 취소통보 (해당 예약 참조값)
예약 서버: 즉시 확정 처리 (거부 불가 — 통보이므로)
예약 서버 → 운영 서버: 취소 확정 통보
운영 서버 → 그 외 관련 채널: 재고 오픈 통보 (필요 시, 신규 판매 가능 안내)
```

### 4.3 호스트 취소요청
```
호스트 → 예약 서버: 취소요청 (사유: 오버부킹 정리 / 시설 문제 / 기타)
예약 서버: 상태를 PENDING_CANCEL로 전환 (재고는 계속 점유 상태 유지, 신규 판매 불가)
예약 서버 → 운영 서버: 취소요청 발생 통보
운영 서버 → 대상 OTA: 취소요청 전달
   ...(OTA가 고객과 협의)...
OTA → 예약 서버: 취소통보 (최종 확정)
예약 서버: PENDING_CANCEL → CANCELLED 확정, 재고 오픈
예약 서버 → 운영 서버: 취소 확정 통보
운영 서버 → 관련 채널: 재고 오픈 통보
```
- 호스트가 취소를 요청한 시점과 실제 확정 시점 사이에 시간차가 존재함을 반드시 인지해야 한다. 이 기간 동안 해당 재고는 판매 불가 상태로 묶인다.
- 오버부킹 정리 목적의 호스트 취소라면, 이미 다른 채널에 확정된 예약이 있으므로 사유 코드를 OTA 표준 사유 체계에 맞춰 전달해야 한다 (페널티 산정에 영향).

### 4.4 예약 변경
- "취소 + 재예약"이 아닌 기존 예약 건에 대한 날짜 변경으로 취급한다.
- OTA/자사 서비스가 변경을 요청하면 예약 서버가 재고 판정(겹침 여부) 후 확정/거부하며, 4.1과 동일한 원칙(통보형 채널에는 거부 시 취소 통보로 처리)을 따른다.
- 예약 히스토리에는 변경 전/후 날짜가 모두 남는다.

## 5. 상태 모델

### 5.1 예약 상태 (reservations)
```
                 ┌───────────┐
   신규 요청 ──▶│ CONFIRMED │
                 └─────┬─────┘
                       │ 호스트 취소요청
                       ▼
                 ┌───────────────┐   OTA 취소통보 도착   ┌───────────┐
                 │ PENDING_CANCEL│ ─────────────────▶ │ CANCELLED │
                 └───────────────┘                     └───────────┘
                       ▲
                       │ OTA발 취소통보 (즉시 확정, PENDING 단계 없음)
                 CONFIRMED ─────────────────────────────▶ CANCELLED
```

| 상태 | 의미 | 재고 판매 가능 여부 |
|---|---|---|
| CONFIRMED | 정상 확정된 예약 | 불가 (점유 중) |
| PENDING_CANCEL | 호스트가 취소를 요청했으나 OTA 확정 대기 중 | 불가 (여전히 점유, 확정 전까지 안전하게 묶어둠) |
| CANCELLED | 최종 취소 확정 | 가능 (재고 오픈) |

### 5.2 취소요청 판정 주체 정리

| 트리거 | 확정 권한 | 확정 시점 |
|---|---|---|
| OTA 취소통보 | OTA (이미 고객과 협의 완료) | 통보 도착 즉시 |
| 호스트 취소요청 | OTA (최종 승인/통보 주체) | 호스트 요청을 전달받은 OTA가 취소통보를 보내온 시점 |

## 6. 신뢰성 원칙 (멱등성 / 정합성)

전체 시스템에 일관되게 적용되는 원칙. (구현 상세는 별도 기술 설계 문서에서 다룸)

1. **중복 요청 방어(멱등성)**: 모든 인입 요청은 고유 키로 식별하여, 동일 요청 재전송 시 재처리 없이 이전 결과를 그대로 반환한다.
2. **동시성 방어(재고 정합성)**: 동일 상품·겹치는 날짜에 대한 동시 확정 요청 중 하나만 성공하도록 보장한다. 나중 요청은 자동 거부되며, 통보형 채널에는 "중복예약으로 인한 취소"로 후속 통보한다.
3. **전달 신뢰성(Outbox)**: 예약 서버 → 운영 서버, 운영 서버 → 외부 채널 각 구간은 상태 변경과 통보 대상 기록이 하나의 트랜잭션으로 묶이며, 실패 시 자동 재시도된다. 통보 유실이 발생하지 않는다.
4. **추적성**: 모든 예약 건의 생성/변경/취소 이력은 별도 히스토리에 append-only로 남아, 사유·주체·시점을 추후 조회할 수 있다.

## 7. 오버부킹 대응 정책 (참고)

- 오버부킹은 채널 간 동기화 지연으로 인해 구조적으로 발생 가능한 문제이며, 완전 차단이 불가능하다. 목표는 **발생 확률 최소화 + 발생 시 신속·정확한 사후 처리**이다.
- 대응 우선순위
  1. 채널별 재고 buffer 운영 검토 (물리 재고보다 적게 노출)
  2. 오버부킹 발생 시 선착순(먼저 확정된 예약) 우선 원칙
  3. 가능한 경우 취소 대신 대체 객실/제휴 숙소 제공 검토 (OTA 페널티 완화)
  4. 호스트 귀책 취소는 전액 환불 원칙, OTA 표준 사유 코드로 통보

## 8. 향후 논의 필요 사항

- OTA별 취소 사유 코드 표준 체계 확인 (연동 대상 OTA 문서 확인 필요)
- 자사 서비스 채널의 결제/환불 처리 주체 및 흐름 정의
- 채널별 sync/async 여부 확정 및 처리 분기 기준 확정
- PENDING_CANCEL 상태로 장기간 머무는 건에 대한 모니터링/알림 정책

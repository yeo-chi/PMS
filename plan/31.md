# 31 [예약] Reservation 서버 REST 컨트롤러 부재 - 외부에서 호출할 방법이 없음

## Requirements

- `POST /api/reservations` — BOOK 처리 (`ReservationService.book`)
- `POST /api/reservations/{reservationId}/cancel-request` — 호스트 취소요청 (`ReservationService.cancelRequest`)
- `POST /api/reservations/cancel-confirm` — OTA 취소통보 (`ReservationService.cancelConfirm`)
- `POST /api/reservations/change` — 예약 변경 (`ReservationService.change`)
- 각 엔드포인트는 요청 DTO를 정의하고 Bean Validation(JSR 380)을 적용한다.
- `ReservationRequest.resultStatus`(SUCCESS/CONFLICT/FAILED)에 따라 적절한 HTTP 상태 코드로 매핑한다.

## Technical Approach

### 0. 실제 병합된 코드 기준 확인

`git pull` 후(main은 #13~#21까지 전부 병합돼 깨끗한 상태) `reservation/.../service/ReservationService.kt`(4개 액션 전부)와 `operation/.../controller/`(`InboundEventController`/`InboundEventRequest`/`InboundEventExceptionHandler`, #20에서 이미 병합됨)를 직접 읽었다.

- **4개 서비스 메서드의 실제 시그니처**(전부 `ReservationRequest`를 반환):
  - `book(command: BookReservationCommand): ReservationRequest` — `BookReservationCommand(platformId, platformReservationRef, roomCode, dateRange: ReservationDateRange, initiatedBy: RequestInitiator)`. `initiatedBy == HOST`면 `require()`로 `IllegalArgumentException` 발생.
  - `cancelConfirm(command: CancelConfirmCommand): ReservationRequest` — `CancelConfirmCommand(platformId, platformReservationRef, externalRequestId: String? = null)`.
  - `cancelRequest(command: CancelRequestCommand): ReservationRequest` — `CancelRequestCommand(reservationId: Long, reason: CancelRequestReason)`.
  - `change(command: ChangeReservationCommand): ReservationRequest` — `ChangeReservationCommand(platformId, platformReservationRef, newDateRange: ReservationDateRange, initiatedBy: RequestInitiator, externalRequestId: String? = null)`. `initiatedBy == HOST`면 `IllegalArgumentException`.
- **`ReservationRequest.resultStatus`/`rejectReason` 실제 조합**(전부 `ReservationService.kt`의 private const에서 확인, 4개뿐): `CONFLICT`+`"DUPLICATE_BOOKING"`(BOOK/CHANGE), `FAILED`+`"RESERVATION_NOT_FOUND"`(cancelConfirm/cancelRequest/change), `FAILED`+`"ALREADY_CANCELLED"`(cancelRequest), `FAILED`+`"RESERVATION_NOT_CHANGEABLE"`(change). 이슈 본문이 제안한 "CONFLICT/FAILED → 409/404" 단순 매핑은 부정확하다 — `FAILED`가 세 가지 서로 다른 사유를 뭉뚱그리고 있어서, `rejectReason`까지 같이 봐야 정확한 상태 코드가 나온다 (2번 참고).
- **operation의 `InboundEventController`/`InboundEventExceptionHandler`(#20) 패턴을 그대로 참고 모델로 삼는다**:
  - 컨트롤러는 얇게 — `@Valid @RequestBody`로 받아 서비스 호출, 결과를 응답으로 변환만 한다.
  - 요청 DTO는 `controller` 패키지에 별도 정의(서비스의 Command와 이름은 비슷해도 완전히 분리된 클래스) — `service`/`domain`이 웹 계층 타입을 전혀 모르게 유지.
  - `@RestControllerAdvice` + `@ExceptionHandler(IllegalArgumentException::class)`로 `require()` 가드 위반을 400으로 변환하는 패턴을 그대로 재사용한다 (BOOK/CHANGE의 HOST 가드가 정확히 이 케이스).
  - Bean Validation 실패(`@Valid`, blank/null)는 Spring MVC가 기본으로 400을 반환하므로 별도 처리 불필요 — operation과 동일.

### 1. 요청 DTO — `controller` 패키지, Command와 1:1이 아니라 REST에 맞게 얕게 편다

`ReservationDateRange`(`startDate`/`endDate`)를 중첩 객체로 받지 않고 톱레벨 필드로 펼친다 (일반적인 REST 페이로드 스타일). `RequestInitiator`/`CancelRequestReason` 같은 도메인 enum은 DTO에서 직접 참조한다(컨트롤러 → 도메인 의존은 정상적인 계층 방향이며, 이슈가 금지하는 "서비스/도메인 → 웹 계층 의존"과는 반대 방향).

```kotlin
// controller/BookReservationRequest.kt
data class BookReservationRequest(
    @field:NotBlank val platformId: String,
    @field:NotBlank val platformReservationRef: String,
    @field:NotBlank val roomCode: String,
    @field:NotNull val startDate: LocalDate,
    @field:NotNull val endDate: LocalDate,
    @field:NotNull val initiatedBy: RequestInitiator,
) {
    @get:AssertTrue(message = "startDate는 endDate보다 이전이어야 합니다")
    val isDateRangeOrdered: Boolean
        get() = startDate == null || endDate == null || startDate.isBefore(endDate)
}

fun BookReservationRequest.toCommand(): BookReservationCommand =
    BookReservationCommand(
        platformId = platformId,
        platformReservationRef = platformReservationRef,
        roomCode = roomCode,
        dateRange = ReservationDateRange(startDate, endDate),
        initiatedBy = initiatedBy,
    )
```

- `CancelRequestRequestBody(reason: CancelRequestReason)` — `reservationId`는 경로 변수라 바디에 없음.
- `CancelConfirmRequest(platformId, platformReservationRef, externalRequestId: String? = null)`.
- `ChangeReservationRequest(platformId, platformReservationRef, newStartDate, newEndDate, initiatedBy, externalRequestId)` — `BookReservationRequest`와 같은 `@AssertTrue` 날짜 순서 검증을 둔다.

`toCommand()`는 `persistent`의 `toDomain()`/`toEntity()` 확장 함수 관례를 그대로 따라 확장 함수로 둔다(멤버 메서드 아님) — 코드베이스 전체의 매핑 스타일과 일관성 유지.

`ReservationDateRange`/`RequestInitiator`/`CancelRequestReason`는 이미 `spring-boot-starter-validation`이 포함돼 있어 새 의존성 불필요 (reservation `build.gradle.kts`에 #13부터 있었음).

### 2. `ReservationRequest → HTTP 상태` 매핑 — `resultStatus`만이 아니라 `rejectReason`까지 함께 본다

```kotlin
// controller/ReservationRequestHttpStatus.kt
fun ReservationRequest.toHttpStatus(): HttpStatus =
    when (resultStatus) {
        RequestResultStatus.SUCCESS -> HttpStatus.OK
        RequestResultStatus.CONFLICT -> HttpStatus.CONFLICT            // DUPLICATE_BOOKING
        RequestResultStatus.FAILED ->
            when (rejectReason) {
                "RESERVATION_NOT_FOUND" -> HttpStatus.NOT_FOUND        // 자원이 존재하지 않음
                "ALREADY_CANCELLED" -> HttpStatus.CONFLICT              // 상태가 더 이상 요청을 허용하지 않음
                "RESERVATION_NOT_CHANGEABLE" -> HttpStatus.CONFLICT     // 상태가 더 이상 요청을 허용하지 않음
                else -> HttpStatus.CONFLICT                            // 알려지지 않은 사유의 안전한 기본값 (500 아님 — 클라이언트 요청이 원인)
            }
    }
```

- `rejectReason`은 `String`(enum 아님)이라 컴파일러가 분기 누락을 잡아주지 못한다 — `else` 분기를 반드시 두고, 알려지지 않은 사유는 500(서버 결함처럼 보임)이 아니라 409(요청이 지금 상태에서 처리될 수 없음)로 안전하게 기본 처리한다.
- BOOK(`SUCCESS`)만 `201 Created`로 별도 처리한다 — 신규 자원을 만드는 유일한 액션이기 때문. 나머지 3개 액션은 기존 자원의 상태를 바꾸는 것이므로 `SUCCESS`는 `200 OK`가 더 알맞다. `Location` 헤더는 붙이지 않는다 — 예약 조회 GET 엔드포인트가 아직 없어(이 프로젝트 어느 티켓에도 없음) 가리킬 대상이 없다.

### 3. 컨트롤러 — 서비스와 대칭으로 하나의 클래스에 4개 액션을 모은다

이슈가 "`ReservationController`(또는 액션별로 분리)"로 선택지를 열어뒀지만, `ReservationService`가 이미 4개 액션을 한 클래스에 모아둔 것과 대칭을 맞춰 **하나의 `ReservationController`**로 만든다 (URL도 전부 `/api/reservations` 하위라 자연스럽게 리소스 하나로 묶임).

```kotlin
// controller/ReservationController.kt
@RestController
@RequestMapping("/api/reservations")
class ReservationController(
    private val reservationService: ReservationService,
) {
    @PostMapping
    fun book(@Valid @RequestBody request: BookReservationRequest): ResponseEntity<ReservationRequestResponse> {
        val result = reservationService.book(request.toCommand())
        return ResponseEntity.status(if (result.resultStatus == RequestResultStatus.SUCCESS) HttpStatus.CREATED else result.toHttpStatus())
            .body(result.toResponse())
    }

    @PostMapping("/{reservationId}/cancel-request")
    fun cancelRequest(
        @PathVariable reservationId: Long,
        @Valid @RequestBody request: CancelRequestRequestBody,
    ): ResponseEntity<ReservationRequestResponse> {
        val result = reservationService.cancelRequest(CancelRequestCommand(reservationId, request.reason))
        return ResponseEntity.status(result.toHttpStatus()).body(result.toResponse())
    }

    @PostMapping("/cancel-confirm")
    fun cancelConfirm(@Valid @RequestBody request: CancelConfirmRequest): ResponseEntity<ReservationRequestResponse> {
        val result = reservationService.cancelConfirm(request.toCommand())
        return ResponseEntity.status(result.toHttpStatus()).body(result.toResponse())
    }

    @PostMapping("/change")
    fun change(@Valid @RequestBody request: ChangeReservationRequest): ResponseEntity<ReservationRequestResponse> {
        val result = reservationService.change(request.toCommand())
        return ResponseEntity.status(result.toHttpStatus()).body(result.toResponse())
    }
}
```

### 4. 응답 DTO

operation의 `InboundEventController`는 바디 없이 상태 코드만 돌려주면 충분했지만(호출자가 `toBodilessEntity()`만 씀), 이 컨트롤러의 호출자(OTA/호스트/자사 서비스)는 결과를 실제로 봐야 하므로 `ReservationRequest`를 그대로 노출하지 않고 컨트롤러 계층 응답 DTO로 변환한다 (도메인 객체를 API 응답으로 직접 직렬화하지 않는다는 원칙):

```kotlin
// controller/ReservationRequestResponse.kt
data class ReservationRequestResponse(
    val requestId: Long?,
    val reservationId: Long?,
    val resultStatus: RequestResultStatus,
    val rejectReason: String?,
    val requestedAt: OffsetDateTime,
)

fun ReservationRequest.toResponse(): ReservationRequestResponse =
    ReservationRequestResponse(
        requestId = id,
        reservationId = reservationId,
        resultStatus = resultStatus,
        rejectReason = rejectReason,
        requestedAt = requestedAt,
    )
```

### 5. 예외 처리 — operation의 `InboundEventExceptionHandler`와 동일 패턴

```kotlin
// controller/ReservationExceptionHandler.kt
@RestControllerAdvice
class ReservationExceptionHandler {
    @ExceptionHandler(IllegalArgumentException::class)
    fun handleIllegalArgument(exception: IllegalArgumentException): ResponseEntity<Void> = ResponseEntity.badRequest().build()
}
```

BOOK/CHANGE의 `require(initiatedBy != HOST) { ... }`가 던지는 `IllegalArgumentException`을 여기서 400으로 변환한다 — operation의 `InboundEventService.receive`가 `require(eventType in KNOWN_EVENT_TYPES)`를 같은 방식으로 처리한 것과 정확히 대칭.

## Testing Plan

`MockMvc` 기반 컨트롤러 테스트로 작성한다 (이슈가 명시한 방식). `@SpringBootTest` + 기존 `PostgresIntegrationTest`(Testcontainers 싱글턴)를 그대로 상속해 실제 서비스/DB까지 통과시킨다 (mock 서비스가 아니라 `ReservationServiceTest`/`ReservationChangeServiceTest`가 이미 검증한 실제 흐름을 컨트롤러 레벨에서 얇게 재확인하는 성격).

- **BOOK 성공**: `POST /api/reservations` → `201`, 응답 바디의 `resultStatus=SUCCESS`/`reservationId` 확인.
- **BOOK 겹침 거부**: 같은 room_code·겹치는 날짜로 두 번째 요청 → `409`, `rejectReason="DUPLICATE_BOOKING"`.
- **BOOK, `initiatedBy=HOST`**: → `400`(바디 없음, `IllegalArgumentException` → `ReservationExceptionHandler` 경로 검증).
- **BOOK, 필수 필드 누락/`startDate >= endDate`**: → `400`(`@Valid` 경로 검증, `AssertTrue` 포함).
- **cancelRequest 성공**: 먼저 BOOK으로 예약 생성 → `POST /api/reservations/{id}/cancel-request` → `200`, `resultStatus=SUCCESS`.
- **cancelRequest, 존재하지 않는 reservationId**: → `404`.
- **cancelRequest, 이미 CANCELLED**: → `409`, `rejectReason="ALREADY_CANCELLED"`.
- **cancelConfirm 성공**: → `200`, `CONFIRMED`/`PENDING_CANCEL` 예약 모두 `CANCELLED`로 전이 확인(서비스 테스트가 이미 검증한 것을 컨트롤러 경유로 대표 케이스 1개만).
- **cancelConfirm, 존재하지 않는 예약**: → `404`.
- **change 성공**: → `200`.
- **change 겹침 거부**: → `409`, `rejectReason="DUPLICATE_BOOKING"`.
- **change, PENDING_CANCEL/CANCELLED 상태 예약**: → `409`, `rejectReason="RESERVATION_NOT_CHANGEABLE"`.
- **change, `initiatedBy=HOST`**: → `400`.
- **`ReservationRequestHttpStatus` 매핑 단위 테스트**(Spring 컨텍스트 불필요): 확인된 4가지 `(resultStatus, rejectReason)` 조합 + 알려지지 않은 `rejectReason` 기본값(409) 케이스를 표로 검증.
- CI/로컬 실행 전제: Docker 데몬 필요(Testcontainers) — 기존 전제와 동일.

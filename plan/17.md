# 17 [예약] 예약 변경(CHANGE) 처리

## Requirements

- OTA/자사 서비스의 변경 요청에 대해 재고 판정(겹침 여부, **자기 자신은 제외**) 후 확정/거부한다. "취소+재예약"이 아니라 기존 예약 건의 날짜만 갱신하는 것으로 취급한다 (기획문서 4.4).
- 거부 시 4.1과 동일 원칙(통보형 채널에는 거부 시 취소/거부 통보로 처리)을 따른다.
- `reservation_requests`에 `CHANGE` 액션으로 `old_date_range`/`new_date_range`를 모두 기록한다 (변경 이력 추적).
- 확정 시 `reservations.date_range`를 갱신하고, `outbound_notifications`에 적절한 이벤트를 발행한다.
- `controller`는 이번 티켓 범위 밖 (#14~#16과 동일한 스코프 경계). `initiatedBy`는 BOOK과 동일하게 OTA/SELF_SERVICE만 허용 (호스트는 변경을 요청할 권한이 없음 — 기획문서 2.2).

## Technical Approach

### 0. 실제 병합된 코드 기준 확인

`git pull`로 main 최신화, `ReservationService.kt`(`book`/`cancelConfirm`/`cancelRequest` 3개 액션이 이미 한 클래스에 공존 — PR #25에서 사용자가 직접 병합 충돌을 해결해 확인됨), `ReservationRepository.kt`, `CancelConfirmRequestKey.kt`/`CancelRequestKey.kt`를 직접 읽고 그 위에 이어 붙인다.

- **`ReservationRepository.findByPlatformIdAndPlatformReservationRef(...)`가 이미 존재한다** (#15에서 추가됨). CHANGE도 OTA가 자기 쪽 참조값으로 대상을 지목하므로(기획문서 4.4는 "OTA/자사 서비스가 변경을 요청") 이 메서드를 그대로 재사용한다 — **새 조회 메서드 불필요**.
- **`ReservationService`는 기존 클래스에 네 번째 액션(`change`)으로 이어 붙인다** — `book`/`cancelConfirm`/`cancelRequest`가 이미 같은 협력 빈 세트(`reservationRepository`, `reservationRequestRepository`, `outboundNotificationRepository`, `transactionTemplate`, `objectMapper`)를 공유하는 하나의 클래스로 자리잡았다.
- **요청 단위 멱등성 + 낙관적 락 재시도 패턴은 그대로 재사용한다**: `findByRequestKey`로 정확한 재시도를 먼저 거르고, `ObjectOptimisticLockingFailureException`은 `transactionTemplate.execute` 블록 **밖**에서 잡아 매 시도마다 최신 상태를 다시 읽는 재시도 루프를 돈다 (#15/#16과 동일한 이유 — 실패한 트랜잭션의 Hibernate 세션 재사용 금지).
- **`recordConflict`(BOOK) 패턴도 재사용한다**: DB 제약 위반(`DataIntegrityViolationException`)은 낙관적 락 충돌과 **다른 실패 모드**이므로 재시도하지 않고, 새 트랜잭션으로 거부 결과를 기록한다. CHANGE는 이 두 예외를 **모두** 다뤄야 하는 첫 액션이다 (아래 2번 참고).

### 1. 선행 코드 수정 — `ReservationEntity.dateRange`를 `var`로 변경 (막히는 지점)

`persistent/ReservationEntity.kt`의 현재 필드는

```kotlin
@Type(PostgreSQLRangeType::class)
@Column(name = "date_range", columnDefinition = "daterange")
val dateRange: Range<LocalDate>,
```

`val`이라 CHANGE에서 날짜를 갱신할 수 없다. `status`가 #13에서 이미 같은 이유로 `var`가 된 전례(PR #22: "`status`는 optimistic lock 테스트 등에서 실제 UPDATE를 발생시켜야 해서 `var`로 두었다")를 그대로 따라 `dateRange`도 `var`로 바꾼다:

```kotlin
@Type(PostgreSQLRangeType::class)
@Column(name = "date_range", columnDefinition = "daterange")
var dateRange: Range<LocalDate>,
```

다른 필드(`toDomain()`/`toEntity()` 매퍼, 기존 테스트)는 `val`/`var` 여부와 무관하게 동작하므로 순수 추가 변경이다. 이 변경 없이는 CHANGE 서비스 로직 자체를 작성할 수 없다.

### 2. 요청 커맨드 · request_key

```kotlin
// service/ChangeReservationCommand.kt
data class ChangeReservationCommand(
    val platformId: String,
    val platformReservationRef: String,
    val newDateRange: ReservationDateRange,
    val initiatedBy: RequestInitiator,
    val externalRequestId: String? = null,
)
```

- `book()`과 동일하게 `require(command.initiatedBy != RequestInitiator.HOST) { ... }`로 시작한다.
- `request_key`는 `CancelConfirmRequestKey.kt`와 완전히 대칭되는 형식(스키마 주석의 CHANGE/CANCEL 포맷)으로 만든다:
  ```kotlin
  // service/ChangeRequestKey.kt
  fun buildChangeRequestKey(
      platformId: String,
      platformReservationRef: String,
      externalRequestId: String?,
      now: OffsetDateTime,
  ): String =
      if (externalRequestId != null) {
          "$platformId:$externalRequestId"
      } else {
          "$platformId:$platformReservationRef:CHANGE:${now.truncatedTo(ChronoUnit.SECONDS)}"
      }
  ```

### 3. 처리 흐름 — 두 가지 서로 다른 실패 모드를 함께 다루는 첫 액션

CHANGE는 기존 row를 UPDATE하므로 **낙관적 락 충돌**(다른 요청이 같은 예약을 먼저 바꿈)과 **exclusion 제약 위반**(새 날짜가 다른 예약과 겹침)이 **동시에** 올 수 있는 첫 액션이다. 이 둘은 서로 다른 처리(재시도 vs 거부 기록)가 필요하므로 재시도 루프 안에서 예외 타입별로 분기한다:

```kotlin
private fun changeWithRetry(command: ChangeReservationCommand, requestKey: String): ReservationRequest {
    var attempt = 1
    while (true) {
        try {
            return attemptChange(command, requestKey)
        } catch (staleVersion: ObjectOptimisticLockingFailureException) {
            // 동시성 충돌(다른 작업이 같은 row를 먼저 바꿈) — 최신 상태를 다시 읽어 재시도
            if (attempt >= CHANGE_MAX_ATTEMPTS) throw staleVersion
            attempt++
        } catch (overlapViolation: DataIntegrityViolationException) {
            // 진짜 겹침 — 재시도해도 다시 겹친다. 재시도하지 않고 거부로 확정 (BOOK의 recordConflict와 동일 이유)
            return recordChangeRejected(command, requestKey)
        }
    }
}
```

`attemptChange`(하나의 `transactionTemplate.execute` 블록):

```
reservation = reservationRepository.findByPlatformIdAndPlatformReservationRef(platformId, platformReservationRef)
if (reservation == null) → FAILED/RESERVATION_NOT_FOUND 기록, 알림 없음 (기존 패턴과 동일)
when (reservation.status) {
  PENDING_CANCEL, CANCELLED ->
    // 취소 절차가 진행 중이거나 끝난 예약의 날짜를 바꾸는 건 의미가 없다 (기획문서 4.4 범위 밖의 상태)
    FAILED/RESERVATION_NOT_CHANGEABLE 기록, 알림 없음
  CONFIRMED -> {
    oldDateRange = reservation.dateRange.toReservationDateRange()
    reservation.dateRange = command.newDateRange.toRange()
    savedReservation = reservationRepository.saveAndFlush(reservation)   // 겹치면 DataIntegrityViolationException, 자기 자신과는 비교 안 함(4번 참고)
    savedRequest = reservationRequestRepository.saveAndFlush(
        CHANGE/SUCCESS, oldDateRange=oldDateRange, newDateRange=command.newDateRange, ...)
    outboundNotificationRepository.saveAndFlush(RESERVATION_CHANGED 알림)   // 같은 트랜잭션
    return savedRequest.toDomain()
  }
}
```

`recordChangeRejected`(BOOK의 `recordConflict`와 동일 구조 — 새 트랜잭션에서 재조회 후 기록, `uq_request_key` 경합 시 재조회 폴백까지 동일하게 재사용):

```
transactionTemplate.execute {
  reservation = reservationRepository.findByPlatformIdAndPlatformReservationRef(...)   // 실패한 세션 재사용 금지, 새로 조회
  request = ReservationRequest(reservationId=reservation.id, action=CHANGE, resultStatus=CONFLICT,
                                rejectReason=DUPLICATE_BOOKING_REJECT_REASON,   // BOOK이 정의한 상수 재사용
                                oldDateRange=reservation.dateRange, newDateRange=command.newDateRange, ...)
  savedRequest = reservationRequestRepository.saveAndFlush(request.toEntity())
  outboundNotificationRepository.saveAndFlush(RESERVATION_REJECTED 알림)   // 4번 참고: BOOK/CANCEL_CONFIRM과 달리 여기선 만들 수 있다
  return savedRequest.toDomain()
} catch (DataIntegrityViolationException) { findByRequestKey(requestKey)로 재조회 후 반환 (BOOK과 동일 패턴) }
```

### 4. `outbound_notifications` — 거부 케이스도 이번엔 발행할 수 있다 (BOOK/CANCEL_CONFIRM과 다른 지점)

`outbound_notifications.reservation_id`는 여전히 `NOT NULL FK`이지만, CHANGE의 거부 케이스는 **예약 row 자체가 그대로 남아있다** (날짜만 바뀌지 않았을 뿐 — BOOK의 CONFLICT처럼 row가 아예 안 생기거나, CANCEL_CONFIRM의 not-found처럼 대상이 없는 경우와 다르다). 따라서 `reservation.id`를 그대로 참조할 수 있어, 이슈가 요구하는 "거부 시... 통보로 처리"를 실제로 구현할 수 있다.

- `event_type`은 스키마 주석이 나열한 4개 값에 없지만 컬럼 자체는 `VARCHAR(40) NOT NULL`로 `CHECK` 제약이 없다(다른 컬럼들과 달리 자유 확장 가능). 확정은 `RESERVATION_CHANGED`(신규), 거부는 이미 정의된 `RESERVATION_REJECTED`를 그대로 재사용한다(주석의 "중복예약 등으로 거부"의 "등"이 BOOK 전용이 아님을 시사).
- **핵심 주의사항 — `notification_key` 유일성**: BOOK/CANCEL_CONFIRM/CANCEL_REQUEST는 예약 생애주기당 최대 한 번만 성공하는 액션이라 `"${reservationNo}:${eventType}"` 키만으로 충분했다. **CHANGE는 같은 예약에 대해 여러 번 성공할 수 있는 첫 액션**이라, 이 형식을 그대로 쓰면 두 번째 성공한 CHANGE에서 `uq_notification_key` 위반이 난다. `savedRequest.id`(이미 `requestId`로 알림에 채우고 있는 값)를 키에 포함해 이벤트 단위로 유일하게 만든다:
  ```kotlin
  notificationKey = "$reservationNo:$RESERVATION_CHANGED_EVENT_TYPE:${savedRequest.id}"
  notificationKey = "$reservationNo:$RESERVATION_REJECTED_EVENT_TYPE:${savedRequest.id}"   // 거부도 여러 번 날 수 있으므로 동일 적용
  ```
- payload: `ReservationChangedPayload(reservationNo, platformId, roomCode, oldStartDate, oldEndDate, newStartDate, newEndDate)` — 확정/거부 공통으로 old/new를 모두 담아, 운영 서버·OTA가 "무엇을 시도했고 결과가 무엇인지" 알 수 있게 한다.

## Testing Plan

`ReservationServiceTest.kt`가 이미 399줄까지 커져 있으므로(BOOK+CANCEL_CONFIRM+CANCEL_REQUEST), CHANGE는 **새 파일** `ReservationChangeServiceTest.kt`로 분리한다 (동일한 `@SpringBootTest` + `PostgresIntegrationTest` 상속 + 생성자 주입 패턴). `buildChangeRequestKey`도 대칭되는 새 순수 단위 테스트 파일로 분리한다.

- **`buildChangeRequestKey` 단위 테스트**: `externalRequestId` 유무에 따른 포맷 검증 (`CancelConfirmRequestKey` 테스트와 대칭).
- **겹치지 않는 새 날짜로 변경 성공**: CONFIRMED 예약을 만든 뒤 겹치지 않는 새 날짜로 `change(...)` 호출 → `reservations.date_range` 갱신 확인, `reservation_requests`에 `CHANGE`/`SUCCESS`(old/new 날짜 모두 채워짐) 1건, `outbound_notifications`에 `RESERVATION_CHANGED` 정확히 1건 검증.
- **자기 자신과의 겹침은 거부 대상이 아님**: 대상 예약의 날짜를 하루 연장하는 것처럼 **원래 자기 자신의 기존 구간과 겹치는** 새 날짜로 변경 → 성공해야 함을 검증 (이슈가 명시적으로 요구한 "UPDATE 시 자연스럽게 제외"의 실제 증명 — 다른 예약과 안 겹치면 자기 자신과의 중첩은 문제 없음을 보인다).
- **다른 예약과 겹치는 날짜로 변경 거부**: 같은 `room_code`에 다른 CONFIRMED 예약을 먼저 만든 뒤, 그 예약과 겹치는 새 날짜로 대상 예약을 `change(...)` → `resultStatus=CONFLICT`, `rejectReason="DUPLICATE_BOOKING"`; **원본 예약은 기존 날짜 그대로 유지**되는지 검증(가장 중요 — 거부됐는데 날짜가 바뀌면 버그); `outbound_notifications`에 `RESERVATION_REJECTED` 1건(해당 예약의 `reservation_id`로) 검증.
- **같은 예약에 대한 두 번째 성공적인 CHANGE**: 한 번 변경에 성공한 예약을 또 다른(겹치지 않는) 날짜로 재변경 → 성공, `outbound_notifications`에 `RESERVATION_CHANGED` 이벤트가 **2건** 존재(서로 다른 `notification_key`)함을 검증 — 3번 리스크에서 지적한 유일성 수정이 실제로 동작함을 증명하는 핵심 테스트.
- **PENDING_CANCEL/CANCELLED 상태의 예약에 대한 변경 시도**: 각각 리포지토리로 직접 픽스처 생성 → `resultStatus=FAILED`, `rejectReason="RESERVATION_NOT_CHANGEABLE"`, 알림 없음 검증.
- **존재하지 않는 예약**: `FAILED`/`RESERVATION_NOT_FOUND`, 알림 없음 검증 (기존 패턴과 동일).
- **HOST가 시작한 CHANGE 요청 거부**: `IllegalArgumentException` 검증 (BOOK과 동일 가드).
- **요청 단위 멱등성**: 같은 `externalRequestId`로 재시도 → 재처리 없이 동일 결과 반환, row 수 안 늘어남 검증.
- **낙관적 락 충돌 후 재시도로 성공**: 네이티브 쿼리로 `version`을 미리 올려 첫 시도가 `ObjectOptimisticLockingFailureException`을 맞게 만든 뒤, 재시도 루프가 결국 성공하는지 검증 — **겹침 예외(`DataIntegrityViolationException`)와는 별개 테스트로 분리**해 두 예외가 서로 다른 코드 경로(재시도 vs 즉시 거부)를 탄다는 것을 각각 증명한다.
- CI/로컬 실행 전제: Docker 데몬 필요(Testcontainers) — #13~#16과 동일.

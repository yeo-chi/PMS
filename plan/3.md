## Requirements

- `reservation` 모듈에 예약 생성 비즈니스 로직을 담당하는 `ReservationService`(`service` 패키지)를 만든다.
  - `ReservationRepository`(#2에서 이미 구현됨, `reservation.persistent`)를 생성자로 주입받아 예약 저장을
    처리한다.
  - 예약 생성이 완료되면 운영 모듈이 공개하는 동기화 인터페이스를 호출해 예약 발생 사실을 전달한다. 모듈 간
    의존은 운영 모듈의 공개 API(=`operation.configuration` 패키지의 인터페이스)를 통해서만 이루어진다 —
    `reservation`이 `operation`의 `service`/`domain`/`persistent` 내부 구현 클래스를 직접 참조하지 않는다.
- `operation` 모듈에 `reservation`이 호출할 수 있는 **공개 동기화 인터페이스**를 정의한다.
  - 이름: `PlatformSyncFacade` (제안 — 이슈 본문 "동기화 인터페이스" 요구사항에 부합, 조정 가능).
  - 메서드는 하나: 예약 발생 시 필요한 정보(플랫폼 코드, 객실 ID, 예약 코드, 투숙객 식별 코드, 체크인/아웃
    일자, 예약 시각, 상태)를 파라미터로 받아 동기화를 트리거한다.
  - 위치: `operation/src/main/kotlin/yeo/chi/proejct/pms/operation/configuration/` — `plan/1.md`가 이미
    이 패키지를 "운영 모듈이 노출하는 공개 API/facade 인터페이스가 사는 자리"로 지정해 두었다.
  - `reservation`은 `operation`을 `project(":operation")` 의존성으로 이미 참조하고 있으므로(#1), 인터페이스
    도입에 새 Gradle 의존성 추가가 필요 없다.
- `PlatformSyncFacade`의 **임시 구현체**를 `operation` 모듈 내에 Spring Bean으로 등록한다.
  - 실제 외부 플랫폼 연동은 하지 않고, 로그만 남기는 no-op에 가까운 구현으로 둔다.
  - `internal class`로 선언해 `reservation` 모듈에서 구현체 타입 자체는 알 수 없고 인터페이스 타입으로만
    주입받도록 한다 (`plan/1.md`의 "operation 구현 클래스는 internal, 인터페이스만 public" 컨벤션).
  - Spring이 이 Bean을 스캔해 `reservation`의 Spring 컨텍스트(`ReservationApplication`)에 주입 가능해야
    한다 — 현재 `@ComponentScan` 설정이 이미 이를 지원하는지 반드시 확인한다 (아래 "ReservationApplication.kt
    확인 결과" 참고).
- `ReservationService`의 서비스 단위 테스트를 작성한다.
  - `ReservationRepository`, `PlatformSyncFacade` 둘 다 MockK로 mock.
  - `CLAUDE.md`/`.claude/skills/kotlin-springboot/SKILL.md` 컨벤션에 따라 Kotest `FeatureSpec`
    (`feature { scenario { ... } }`) 스타일로 작성 — JUnit5 `@Test` 클래스나 `StringSpec` 금지.
- `operation`에 새로 추가하는 임시 구현체에 대해서도 최소한의 스모크 테스트를 추가한다 (호출해도 예외가
  발생하지 않는지 확인하는 수준).

## ReservationApplication.kt 확인 결과 (사전 조사 항목)

실제 `main`의 `reservation/src/main/kotlin/yeo/chi/proejct/pms/reservation/ReservationApplication.kt`를
직접 확인한 결과, `@ComponentScan`이 `plan/1.md` 최초안(`operation` 베이스 패키지 전체)과 달리 **operation의
개별 하위 패키지를 leaf 단위로 명시**하는 형태로 이미 수정되어 있다:

```kotlin
@SpringBootApplication
@ComponentScan(
	basePackages = [
		"yeo.chi.proejct.pms.reservation",
		"yeo.chi.proejct.pms.operation.controller",
		"yeo.chi.proejct.pms.operation.service",
		"yeo.chi.proejct.pms.operation.persistent",
		"yeo.chi.proejct.pms.operation.configuration",
	],
)
@EntityScan(
	basePackages = [
		"yeo.chi.proejct.pms.reservation.persistent",
		"yeo.chi.proejct.pms.operation.domain",
	],
)
class ReservationApplication
```

`"yeo.chi.proejct.pms.operation.configuration"`과 `"yeo.chi.proejct.pms.operation.service"`가 **이미
`basePackages`에 포함되어 있다.** 즉:

- `PlatformSyncFacade` 인터페이스(→ `operation.configuration`에 위치)와 그 임시 구현체(→
  `operation.service`에 위치, 아래 참고)는 **별도 수정 없이도** `ReservationApplication`의 컴포넌트 스캔
  범위에 자동으로 포함된다.
- 따라서 **이번 티켓에서 `ReservationApplication.kt`를 수정할 필요가 없다.** (참고로 이 파일 상단 주석은
  "operation의 own basePackage는 의도적으로 스캔 대상에서 빼고 leaf 패키지만 나열해서, operation 자신의
  `@SpringBootApplication`인 `OperationApplication`이 함께 스캔되지 않도록 한다"고 설명하는데, 새 클래스들이
  이미 스캔 대상 leaf 패키지 안에 들어가므로 이 안전장치와도 충돌하지 않는다.)
- 만약 나중에 구현 중 실제로 Bean이 안 잡히는 문제가 발견되면(예: 패키지 오타), 그건 이 문서의 전제가 깨진
  것이므로 `ReservationApplication.kt`의 `@ComponentScan.basePackages`에 누락된 leaf 패키지를 추가하는
  방향으로 수정한다 — 새로운 패키지를 만들지는 않는다.

## 이번 티켓 vs #6 범위

| 항목 | 이번 티켓 (#3) | #6 (운영 모듈 동기화 로직) |
|---|---|---|
| `PlatformSyncFacade` 인터페이스 시그니처 | 정의 (신규) | 그대로 사용 (필요 시 리뷰 후 조정 가능) |
| 구현체 | 로그만 찍는 no-op (`LoggingPlatformSyncFacade`) | 실제 외부 플랫폼 API 호출 구현으로 교체/확장 |
| 재시도 | 없음 | #6에서 구현 |
| 멱등성 (외부 플랫폼 API 호출 자체의 중복 호출 방지) | 없음 — 아래 "Edge cases"에 별도 언급하는 DB 레벨 중복 저장 방지와는 다른 개념 | #6에서 구현 |
| 실패 시 처리(재시도 큐, 실패 알림 등) | 없음 (no-op은 실패하지 않음) | #6에서 설계/구현 |
| `ReservationService`가 인터페이스를 호출하는 지점/흐름 | 확정 (저장 후 호출) | 변경 없음 — #6은 인터페이스 내부 구현만 교체 |

이번 티켓은 **컴파일 가능한 계약(인터페이스)과 자리채움 구현체**를 만드는 것이 목적이며, `ReservationService`
가 이 계약에 의존하는 구조를 완성하는 것까지가 범위다. 실제 플랫폼 연동 로직은 전혀 포함하지 않는다.

## Technical Approach

### 1. `operation/src/main/kotlin/yeo/chi/proejct/pms/operation/configuration/PlatformSyncFacade.kt` (신규)

운영 모듈의 공개 API. `Reservation` 도메인 타입을 직접 참조하지 않는다 — `operation`은 `reservation`에
의존하지 않으므로(`plan/1.md` §11 "Circular dependency" 금지), 필요한 필드만 담은 전용 요청 타입
(`ReservationSyncRequest`)을 같은 파일에 함께 정의한다 (`domain/Reservation.kt`가 도메인 클래스와 enum을
한 파일에 두는 기존 컨벤션과 동일한 방식).

```kotlin
package yeo.chi.proejct.pms.operation.configuration

import java.time.LocalDate
import java.time.LocalDateTime

/**
 * reservation 모듈이 예약 생성 사실을 operation 모듈에 위임할 때 사용하는 공개 API.
 *
 * reservation은 이 인터페이스에만 의존하며, operation의 실제 구현 클래스(service/domain/persistent 패키지)를
 * 직접 참조하지 않는다 (모듈 간 의존은 운영 모듈의 공개 API를 통해서만 - 이슈 #2/#3 공통 원칙).
 *
 * 실제 외부 플랫폼 연동, 재시도, 멱등성 보장은 이 인터페이스의 구현체가 담당하며, 그 실제 구현은 #6에서
 * 채워진다. 이번 티켓(#3)에는 시그니처와 로그만 남기는 임시 구현체만 포함된다.
 */
interface PlatformSyncFacade {

    fun syncReservationCreated(request: ReservationSyncRequest)
}

data class ReservationSyncRequest(
    val platformCode: String,
    val roomId: Long,
    val reservationCode: String,
    val userIdentifyCode: String,
    val startDate: LocalDate,
    val endDate: LocalDate,
    val reservedAt: LocalDateTime,
    val status: String,
)
```

설계 노트:
- `status`를 `ReservationStatus` enum이 아니라 `String`으로 받는 이유: `operation`이 `reservation.domain`에
  의존하면 안 되므로, `reservation` 쪽에서 `ReservationStatus.name`으로 변환해 원시 타입으로 전달한다.
- 메서드 이름을 `syncReservationCreated`로 구체적으로 지은 이유: 이슈 본문이 "예약 생성 완료 시" 동기화를
  요구하므로, 향후 예약 취소 등 다른 이벤트가 추가되면 `syncReservationCancelled` 등 별도 메서드를 추가하는
  방향을 권장한다 (이번 티켓 범위 아님, 필요 시 향후 티켓에서 확장).

### 2. `operation/src/main/kotlin/yeo/chi/proejct/pms/operation/service/LoggingPlatformSyncFacade.kt` (신규)

`PlatformSyncFacade`의 임시 구현체. `operation.service` 패키지에 두는 이유는 `plan/1.md` §8 표가 이미
"`service`: `PlatformSyncClient` impls, registry/factory, retry logic(#6)"으로 이 패키지의 역할을 지정해
두었기 때문 — #6에서 진짜 구현으로 교체/확장될 자리다. `internal class`로 선언해 `reservation` 모듈에서는
구현 클래스 타입 자체에 접근할 수 없고, 오직 `PlatformSyncFacade` 인터페이스로만 주입받을 수 있다.

```kotlin
package yeo.chi.proejct.pms.operation.service

import org.slf4j.LoggerFactory
import org.springframework.stereotype.Service
import yeo.chi.proejct.pms.operation.configuration.PlatformSyncFacade
import yeo.chi.proejct.pms.operation.configuration.ReservationSyncRequest

/**
 * [임시 구현체] 실제 외부 플랫폼 API 연동/재시도/멱등성 처리는 #6에서 채운다.
 * 현재는 예약 동기화 요청이 들어왔다는 사실을 로그로만 남기고 즉시 반환한다(no-op에 가까움).
 */
@Service
internal class LoggingPlatformSyncFacade : PlatformSyncFacade {

    companion object {
        private val logger = LoggerFactory.getLogger(LoggingPlatformSyncFacade::class.java)
    }

    override fun syncReservationCreated(request: ReservationSyncRequest) {
        logger.info(
            "[TODO #6] platform sync triggered: platformCode={}, roomId={}, reservationCode={}, status={}",
            request.platformCode,
            request.roomId,
            request.reservationCode,
            request.status,
        )
    }
}
```

`@Service`(Spring 컴포넌트 스테레오타입)를 붙였으므로 `ReservationApplication`의
`@ComponentScan(basePackages = [..., "yeo.chi.proejct.pms.operation.service", ...])`에 의해 자동으로 빈으로
등록되고, `PlatformSyncFacade` 타입으로 주입 가능하다 (위 "ReservationApplication.kt 확인 결과" 참고 — 수정
불필요).

### 3. `reservation/src/main/kotlin/yeo/chi/proejct/pms/reservation/service/ReservationService.kt` (신규)

`ReservationRepository`와 `PlatformSyncFacade`를 생성자로 주입받는다. 흐름: (1) `platformCode` + `code`
조합으로 기존 예약이 있는지 확인(#2에서 이미 만들어 둔 `findByPlatformCodeAndCode` 활용 — `plan/2.md`가
"이 메서드는 #3에서 쓰일 것"이라고 이미 명시해 둔 지점), (2) 없으면 도메인 → Entity 변환 후 저장, (3) 저장된
결과를 다시 도메인으로 변환, (4) `PlatformSyncFacade`를 호출해 운영 모듈에 예약 발생 사실을 전달, (5) 도메인
객체를 반환한다. 이미 존재하는 예약이면 중복 저장/중복 동기화 호출 없이 기존 예약을 그대로 반환한다(같은
`platformCode`+`code` 조합의 중복 요청에 대한 최소한의 방어 — 플랫폼 API 자체의 네트워크 재시도 멱등성과는
다른 개념이며, 그건 #6에서 다룬다. 아래 Edge cases 참고).

```kotlin
package yeo.chi.proejct.pms.reservation.service

import org.slf4j.LoggerFactory
import org.springframework.stereotype.Service
import org.springframework.transaction.annotation.Transactional
import yeo.chi.proejct.pms.operation.configuration.PlatformSyncFacade
import yeo.chi.proejct.pms.operation.configuration.ReservationSyncRequest
import yeo.chi.proejct.pms.reservation.domain.Reservation
import yeo.chi.proejct.pms.reservation.persistent.ReservationRepository
import yeo.chi.proejct.pms.reservation.persistent.toDomain
import yeo.chi.proejct.pms.reservation.persistent.toEntity

@Service
class ReservationService(
    private val reservationRepository: ReservationRepository,
    private val platformSyncFacade: PlatformSyncFacade,
) {

    companion object {
        private val logger = LoggerFactory.getLogger(ReservationService::class.java)
    }

    @Transactional
    fun createReservation(reservation: Reservation): Reservation {
        val existing = reservationRepository.findByPlatformCodeAndCode(
            reservation.platformCode,
            reservation.code,
        )
        if (existing != null) {
            logger.info(
                "Reservation already exists for platformCode={}, code={} - skip duplicate save/sync",
                reservation.platformCode,
                reservation.code,
            )
            return existing.toDomain()
        }

        val saved = reservationRepository.save(reservation.toEntity()).toDomain()

        platformSyncFacade.syncReservationCreated(saved.toSyncRequest())

        return saved
    }

    private fun Reservation.toSyncRequest(): ReservationSyncRequest = ReservationSyncRequest(
        platformCode = platformCode,
        roomId = roomId,
        reservationCode = code,
        userIdentifyCode = userIdentifyCode,
        startDate = startDate,
        endDate = endDate,
        reservedAt = reservedAt,
        status = status.name,
    )
}
```

설계 노트:
- `@Transactional`은 `.claude/skills/kotlin-springboot/SKILL.md`의 "Service Layer" 컨벤션(`@Transactional`
  on service methods)을 따른 것. `spring-boot-starter-data-jpa`가 `spring-tx`를 이미 전이 의존성으로
  가져오므로 `reservation/build.gradle.kts`에 추가 의존성이 필요 없다.
- `toSyncRequest()`를 `ReservationService` 내부의 `private` 확장 함수로 둔 이유: 이 매핑은 서비스의 호출
  흐름에서만 쓰이는 일회성 변환이고, `domain/Reservation.kt`(순수 도메인, `operation` 패키지를 몰라야 함)나
  `persistent/ReservationEntity.kt`(영속성 매핑 전용)에 두면 두 파일의 책임과 섞이므로 서비스 계층에 둔다.
- `existing != null`이면 `platformSyncFacade`를 호출하지 않는다 — 이미 과거에 한 번 저장 시점에 동기화를
  트리거했을 것이므로, 같은 예약에 대해 매번 재호출하지 않는다는 설계다. (구현 중 이 정책이 요구사항과 다르면
  조정 가능하나, 최소한 DB 유니크 제약을 그대로 저장 시도해 예외를 던지는 것보다는 안전하다.)

### 4. Edge cases

- **멱등성의 두 층위 구분**: `ReservationService.createReservation`이 `findByPlatformCodeAndCode`로 하는
  중복 방지는 "같은 예약을 두 번 DB에 저장하지 않는다"는 애플리케이션 레벨 가드일 뿐이다. 반면 #6이 다뤄야
  할 "외부 플랫폼 API 호출 자체의 멱등성/재시도"는 완전히 다른 문제(예: 동기화 요청이 네트워크 오류로
  실패했을 때 재시도해도 플랫폼 쪽에 중복 반영되지 않아야 함)이며, 이번 티켓의 no-op 구현체는 애초에 외부
  호출을 하지 않으므로 이 문제 자체가 발생하지 않는다. 두 개념을 문서/커밋 메시지에서 혼동하지 않는다.
- **트랜잭션 경계 안에서 동기화 인터페이스를 호출하는 점**: 현재 설계는 `platformSyncFacade
  .syncReservationCreated(...)` 호출이 `@Transactional` 메서드 내부, 즉 DB 커밋 이전에 일어난다. 지금은
  no-op이라 문제가 없지만, #6에서 실제 네트워크 I/O가 들어가면 트랜잭션이 외부 호출 지연시간만큼 길어지는
  문제가 생길 수 있다. `TransactionalEventListener`로 커밋 이후에 비동기 호출하는 방식으로 바꿀지는 #6에서
  판단할 설계 결정으로 남겨두고, 이번 티켓에서는 구현하지 않는다.
- **동시성**: 동일한 `platformCode`+`code` 요청이 동시에 두 번 들어오면 `findByPlatformCodeAndCode` 조회와
  `save` 사이에 경쟁 조건이 있을 수 있다 — 다만 `ReservationEntity`의 DB 유니크 제약(`uk_reservation
  _platform_code_code`, #2에서 이미 적용됨)이 최종 방어선 역할을 하므로 데이터 정합성 자체는 깨지지 않는다
  (동시 저장 시 한쪽은 `DataIntegrityViolationException`을 던질 수 있다는 정도만 인지하고, 이번 티켓에서
  별도 예외 처리는 추가하지 않는다 — 필요해지면 후속 티켓에서 다룬다).
- **`Reservation`이 `data class`인 점**: `plan/2.md`에서 이미 언급된 대로 `id = null`인 두 "저장 전" 도메인
  인스턴스는 나머지 필드가 같으면 `equals()`상 동일 취급된다. 테스트 작성 시 `saved.id`처럼 특정 필드로
  검증하고, 저장 전/후 객체를 통째로 `shouldBe` 비교할 때는 이 점을 유의한다.
- **`internal` 구현체와 컴파일 가시성**: `LoggingPlatformSyncFacade`는 `internal`이므로 `reservation` 모듈의
  프로덕션/테스트 코드에서 이 클래스 이름으로 직접 `import`할 수 없다 (Kotlin의 `internal`은 모듈 경계까지만
  허용). `ReservationService`의 프로덕션 코드는 애초에 `PlatformSyncFacade` 인터페이스 타입으로만 의존하므로
  문제가 없고, `ReservationServiceTest`도 인터페이스를 MockK로 mock하므로 `LoggingPlatformSyncFacade`를 알
  필요가 없다.

## Testing Plan

`CLAUDE.md`/`.claude/skills/kotlin-springboot/SKILL.md`의 Kotest 스펙 스타일 컨벤션에 따라 `FeatureSpec`
(`feature { scenario { ... } }`)으로 작성한다. `ReservationRepository`와 `PlatformSyncFacade` 둘 다 MockK로
mock한다.

### 1. `reservation/src/test/kotlin/yeo/chi/proejct/pms/reservation/service/ReservationServiceTest.kt` (신규)

```kotlin
package yeo.chi.proejct.pms.reservation.service

import io.kotest.core.spec.style.FeatureSpec
import io.kotest.matchers.shouldBe
import io.mockk.Runs
import io.mockk.every
import io.mockk.just
import io.mockk.mockk
import io.mockk.slot
import io.mockk.verify
import yeo.chi.proejct.pms.operation.configuration.PlatformSyncFacade
import yeo.chi.proejct.pms.operation.configuration.ReservationSyncRequest
import yeo.chi.proejct.pms.reservation.domain.Reservation
import yeo.chi.proejct.pms.reservation.domain.ReservationStatus
import yeo.chi.proejct.pms.reservation.persistent.ReservationRepository
import yeo.chi.proejct.pms.reservation.persistent.toEntity
import java.time.LocalDate
import java.time.LocalDateTime

class ReservationServiceTest : FeatureSpec({

    fun newReservation(
        platformCode: String = "AIRBNB",
        code: String = "AIRBNB-CODE-0001",
    ) = Reservation(
        platformCode = platformCode,
        roomId = 1L,
        userIdentifyCode = "guest-001",
        startDate = LocalDate.of(2026, 9, 1),
        endDate = LocalDate.of(2026, 9, 3),
        reservedAt = LocalDateTime.of(2026, 8, 13, 10, 0),
        code = code,
    )

    feature("ReservationService.createReservation") {
        scenario("새로운 예약이면 저장 후 PlatformSyncFacade를 호출한다") {
            val reservationRepository = mockk<ReservationRepository>()
            val platformSyncFacade = mockk<PlatformSyncFacade>()
            val reservationService = ReservationService(reservationRepository, platformSyncFacade)

            val reservation = newReservation()
            val savedEntity = reservation.toEntity().apply { id = 100L }

            every {
                reservationRepository.findByPlatformCodeAndCode("AIRBNB", "AIRBNB-CODE-0001")
            } returns null
            every { reservationRepository.save(any()) } returns savedEntity
            every { platformSyncFacade.syncReservationCreated(any()) } just Runs

            val result = reservationService.createReservation(reservation)

            result.id shouldBe 100L
            result.status shouldBe ReservationStatus.CONFIRMED

            val requestSlot = slot<ReservationSyncRequest>()
            verify(exactly = 1) { platformSyncFacade.syncReservationCreated(capture(requestSlot)) }
            requestSlot.captured.platformCode shouldBe "AIRBNB"
            requestSlot.captured.reservationCode shouldBe "AIRBNB-CODE-0001"
            requestSlot.captured.roomId shouldBe 1L
            requestSlot.captured.status shouldBe "CONFIRMED"
            verify(exactly = 1) { reservationRepository.save(any()) }
        }

        scenario("이미 존재하는 예약(platformCode+code)이면 저장/동기화 없이 기존 예약을 그대로 반환한다") {
            val reservationRepository = mockk<ReservationRepository>()
            val platformSyncFacade = mockk<PlatformSyncFacade>()
            val reservationService = ReservationService(reservationRepository, platformSyncFacade)

            val reservation = newReservation()
            val existingEntity = reservation.toEntity().apply { id = 55L }

            every {
                reservationRepository.findByPlatformCodeAndCode("AIRBNB", "AIRBNB-CODE-0001")
            } returns existingEntity

            val result = reservationService.createReservation(reservation)

            result.id shouldBe 55L
            verify(exactly = 0) { reservationRepository.save(any()) }
            verify(exactly = 0) { platformSyncFacade.syncReservationCreated(any()) }
        }
    }
})
```

### 2. `operation/src/test/kotlin/yeo/chi/proejct/pms/operation/service/LoggingPlatformSyncFacadeTest.kt` (신규)

임시 구현체가 예외 없이 정상 동작(로그만 남기고 반환)하는지 확인하는 최소한의 스모크 테스트. `internal`
클래스이므로 같은 모듈(`operation`)의 테스트 소스셋에서만 직접 인스턴스화할 수 있다 (Kotlin Gradle 플러그인이
같은 서브프로젝트의 `test` 소스셋을 `main`의 friend 컴파일로 취급 — `plan/2.md`에서 `internal set`에 대해
설명한 것과 동일한 메커니즘).

```kotlin
package yeo.chi.proejct.pms.operation.service

import io.kotest.core.spec.style.FeatureSpec
import io.kotest.matchers.shouldNotBeNull
import yeo.chi.proejct.pms.operation.configuration.ReservationSyncRequest
import java.time.LocalDate
import java.time.LocalDateTime

class LoggingPlatformSyncFacadeTest : FeatureSpec({

    feature("LoggingPlatformSyncFacade") {
        scenario("syncReservationCreated 호출 시 예외 없이 완료된다 (임시 구현체, 실제 연동은 #6)") {
            val facade = LoggingPlatformSyncFacade()
            val request = ReservationSyncRequest(
                platformCode = "AIRBNB",
                roomId = 1L,
                reservationCode = "AIRBNB-CODE-0001",
                userIdentifyCode = "guest-001",
                startDate = LocalDate.of(2026, 9, 1),
                endDate = LocalDate.of(2026, 9, 3),
                reservedAt = LocalDateTime.of(2026, 8, 13, 10, 0),
                status = "CONFIRMED",
            )

            facade.shouldNotBeNull()
            facade.syncReservationCreated(request)
            // 예외 없이 반환되면 성공 - 이 구현체는 아직 아무 것도 검증할 상태를 갖지 않는다(no-op에 가까움).
        }
    }
})
```

### 3. 회귀 확인

- `reservation`의 `@ComponentScan`이 새 Bean(`PlatformSyncFacade` 구현체)을 실제로 인식하는지는 기존
  `ReservationApplicationTests.contextLoads()`(`@SpringBootTest`)가 이미 커버한다 — `ReservationService`가
  생성자에서 `PlatformSyncFacade`를 요구하므로, 만약 Bean이 하나도 없거나 여러 개(중복 후보)라면 컨텍스트
  로딩 자체가 실패하며 이 테스트가 즉시 잡아준다. 새 파일 추가 후 별도 수정 없이 이 테스트가 계속 통과하는지
  확인하는 것이 곧 "빈 주입이 실제로 동작한다"의 검증이다.

### 4. 검증 커맨드

1. `./gradlew :reservation:test --tests "*ReservationServiceTest*"` — 신규 서비스 단위 테스트 통과 확인.
2. `./gradlew :operation:test --tests "*LoggingPlatformSyncFacadeTest*"` — 임시 구현체 스모크 테스트 통과

5. `./gradlew build` — 루트에서 두 모듈 전체 빌드가 성공하는지 확인 (특히 `reservation`이
   `operation.configuration.PlatformSyncFacade`를 컴파일 타임에 문제없이 참조하는지).

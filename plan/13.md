# 13 [Setup] Reservation 서버 PostgreSQL 전환 + 스키마/도메인/Entity/Repository

## Requirements

- `reservation` 모듈의 datasource를 H2 → PostgreSQL로 전환한다 (운영/개발 모두 실제 Postgres 사용, 테스트는 Testcontainers).
- `docs/schema/reservation_server_schema.sql`에 정의된 3개 테이블을 실제 DB 스키마로 반영한다:
  - `reservations` — `status`(`CONFIRMED`/`PENDING_CANCEL`/`CANCELLED`), `date_range`(`DATERANGE`) + `room_code`에 대한 `EXCLUDE USING GIST` 겹침 방지 제약, `version`(optimistic lock), 생성 컬럼 `reservation_no`.
  - `reservation_requests` — `BOOK`/`CHANGE`/`CANCEL_REQUEST`/`CANCEL_CONFIRM` append-only 요청 로그, `request_key` 멱등키.
  - `outbound_notifications` — operation 서버 통보용 Transactional Outbox (`status`/`retry_count`/`next_retry_at`).
- `domain`(순수 Kotlin, 영속성 무관)과 `persistent`(`@Entity` + `Repository`, `toDomain()`/`toEntity()`)를 CLAUDE.md 컨벤션대로 분리한다. `domain`은 `persistent`에 의존하지 않는다.
- 이 티켓 범위는 스키마 마이그레이션 + 도메인/엔티티/리포지토리까지다. BOOK/CANCEL 등 서비스 계층 처리 흐름은 포함하지 않는다(`controller`, `service` 패키지는 이번 티켓에서 건드리지 않는다 — 실제 서비스 로직은 #14~#17에서 다룬다).
- `date_range`/`GIST` exclusion 제약, `reservation_no` 생성 컬럼은 Hibernate `ddl-auto`로 표현 불가능하므로 별도 마이그레이션 도구로 관리한다.
- 테스트는 Kotest `FeatureSpec`로 작성하고, GIST exclusion 제약처럼 H2로 재현 불가능한 동작은 Testcontainers의 실제 PostgreSQL 컨테이너로 검증한다.

## Technical Approach

### 0. 현재 상태 확인

- `reservation/build.gradle.kts`: 현재 `runtimeOnly("com.h2database:h2")`만 있고 postgres/flyway/testcontainers 의존성 없음.
- `reservation/src/main/resources/application.yaml`: `spring.application.name`, `server.port`, `operation.base-url`만 있고 `datasource`/`jpa` 설정 없음.
- `domain`, `persistent`, `controller`, `service` 패키지는 `.gitkeep`만 있는 빈 디렉터리 상태 (컨벤션상 5개 패키지 구조는 이미 잡혀 있음, 내용만 없음).
- 루트에 `docker-compose.yml` 없음. `operation` 모듈도 아직 H2 그대로(전환은 #19에서 별도 처리).
- `reservation/src/test/kotlin/.../ReservationApplicationTests.kt`(`@SpringBootTest` 컨텍스트 로딩), `ReservationModuleSmokeTest.kt`(Kotest 배선 확인용 스모크 테스트)가 이미 존재 — H2 제거 후에도 계속 통과해야 함.

### 1. Gradle (`reservation/build.gradle.kts`)

`io.spring.dependency-management` 플러그인이 Spring Boot BOM(Spring Boot 3.5.14 → Hibernate ORM 6.6.x)을 통해 postgresql/flyway/testcontainers 버전을 모두 관리하므로, 기존 파일의 스타일대로 버전 번호 없이 좌표만 추가한다.

- 제거: `runtimeOnly("com.h2database:h2")`
- 추가 (main):
  - `runtimeOnly("org.postgresql:postgresql")`
  - `implementation("org.flywaydb:flyway-core")`
  - `implementation("org.flywaydb:flyway-database-postgresql")` — Flyway 10+부터 DB별 지원이 별도 모듈로 분리되었으므로 필요.
  - `implementation("io.hypersistence:hypersistence-utils-hibernate-63")` — `daterange` ↔ `Range<LocalDate>` 매핑용 (상세 이유는 4번 항목 참고). 이 모듈은 Hibernate 6.3~6.6을 지원하므로 현재 Spring Boot 버전(Hibernate 6.6.x)과 호환된다.
- 추가 (test):
  - `testImplementation("org.springframework.boot:spring-boot-testcontainers")`
  - `testImplementation("org.testcontainers:junit-jupiter")`
  - `testImplementation("org.testcontainers:postgresql")`

기존 `implementation("org.springframework.boot:spring-boot-starter-data-jpa")`, `kotlin("plugin.jpa")`, `allOpen` 설정(엔티티용)은 그대로 유지.

### 2. Flyway 마이그레이션 (Hibernate ddl-auto 미사용)

`reservations.date_range`(`DATERANGE` + `GIST` exclusion), `reservation_no`(생성 컬럼)는 JPA 애노테이션만으로 스키마를 생성할 수 없다. **Flyway**를 도입해 `docs/schema/reservation_server_schema.sql`의 DDL을 그대로 관리한다 (Liquibase 대비 순수 SQL이라 기존 스키마 문서와 1:1 대응이 쉽고, Spring Boot 자동 구성이 가장 매끄러움. 이슈 본문도 "Flyway/Liquibase 또는 schema.sql/DDL 스크립트"로 선택지를 열어뒀으므로, 이 선택은 구현 시 확정하는 결정 사항으로 PR 설명에 남긴다).

- 파일: `reservation/src/main/resources/db/migration/V1__init_reservation_schema.sql`
  - `docs/schema/reservation_server_schema.sql`의 DDL을 그대로 옮긴다 (테이블 3개 + 인덱스 + `CREATE EXTENSION IF NOT EXISTS btree_gist;`).
  - 주의: 이 파일은 `docs/schema/reservation_server_schema.sql`의 **사본**이다. 자동 동기화 장치는 이번 티켓 범위 밖이므로, 스키마 문서가 바뀌면 마이그레이션 파일도 수동으로 맞춰야 한다는 점을 PR 설명에 명시한다.
- `reservation/src/main/resources/application.yaml`에 추가:
  ```yaml
  spring:
    datasource:
      url: jdbc:postgresql://localhost:5432/reservation
      username: reservation
      password: reservation
    jpa:
      hibernate:
        ddl-auto: validate   # Flyway가 스키마를 소유; Hibernate는 매핑 검증만
      open-in-view: false
    flyway:
      enabled: true
  ```
  (로컬 개발 기본값이며, 배포 환경에서는 환경변수/프로퍼티로 덮어쓰는 것을 전제로 한다.)

operation 서버(MySQL)용 서비스는 이슈 #19에서 같은 파일에 추가하는 것으로 남겨둔다(이번 티켓은 `reservation-db`만).

### 4. `domain` 패키지 (신규, 순수 Kotlin)

경로: `reservation/src/main/kotlin/yeo/chi/proejct/pms/reservation/domain/`

- `ReservationStatus.kt` — `enum class ReservationStatus { CONFIRMED, PENDING_CANCEL, CANCELLED }`
- `ReservationDateRange.kt` — `data class ReservationDateRange(val startDate: LocalDate, val endDate: LocalDate)` (Postgres `daterange`의 `[시작, 종료)` 반개구간 의미론을 도메인에서도 그대로 유지: `endDate`는 체크아웃일 exclusive). Hibernate/hypersistence-utils의 `Range<LocalDate>` 타입에 의존하지 않는다 — 그건 `persistent`에서만 다룬다.
- `Reservation.kt` — `data class Reservation(val id: Long?, val reservationNo: String?, val platformId: String, val platformReservationRef: String, val roomCode: String, val dateRange: ReservationDateRange, val status: ReservationStatus, val version: Int, val createdAt: OffsetDateTime, val updatedAt: OffsetDateTime)`. `id`/`reservationNo`는 신규 미저장 인스턴스에서 null 가능. 신규 생성 팩토리에서는 `version = 1`로 시작한다 (스키마의 `version INT NOT NULL DEFAULT 1`과 의미를 맞추기 위한 명시적 결정 — 근거는 6번 리스크 항목 참고).
- `ReservationRequestAction.kt` — `enum class ReservationRequestAction { BOOK, CHANGE, CANCEL_REQUEST, CANCEL_CONFIRM }`
- `RequestInitiator.kt` — `enum class RequestInitiator { OTA, HOST, SELF_SERVICE }`
- `RequestResultStatus.kt` — `enum class RequestResultStatus { SUCCESS, CONFLICT, FAILED }`
- `ReservationRequest.kt` — `data class ReservationRequest(val id: Long?, val requestKey: String, val reservationId: Long?, val platformId: String, val action: ReservationRequestAction, val initiatedBy: RequestInitiator, val roomCode: String?, val oldDateRange: ReservationDateRange?, val newDateRange: ReservationDateRange?, val resultStatus: RequestResultStatus, val rejectReason: String?, val requestedAt: OffsetDateTime)`
- `OutboundNotificationStatus.kt` — `enum class OutboundNotificationStatus { PENDING, SENT, FAILED, DEAD }`
- `OutboundNotification.kt` — `data class OutboundNotification(val id: Long?, val notificationKey: String, val reservationId: Long, val requestId: Long?, val eventType: String, val payload: String, val status: OutboundNotificationStatus, val retryCount: Int, val nextRetryAt: OffsetDateTime, val createdAt: OffsetDateTime, val updatedAt: OffsetDateTime)` (`payload`는 이번 티켓에서는 원본 JSON 문자열로만 다룬다; 타입 있는 페이로드 모델링은 후속 서비스 티켓에서).

### 5. `persistent` 패키지 (신규)

경로: `reservation/src/main/kotlin/yeo/chi/proejct/pms/reservation/persistent/`

- `ReservationEntity.kt`
  - `@Entity @Table(name = "reservations")`
  - `id: Long` — `@Id @GeneratedValue(strategy = GenerationType.IDENTITY)` (Postgres `GENERATED ALWAYS AS IDENTITY` 컬럼과 호환 — Hibernate IDENTITY 전략은 insert 문에 id를 포함하지 않고 JDBC generated-keys로 읽어온다).
  - `reservationNo: String` — `@Column(name = "reservation_no", insertable = false, updatable = false)` **+ `@Generated(event = [EventType.INSERT])`(`org.hibernate.annotations.Generated`)**. `insertable/updatable = false`만으로는 insert 이후 엔티티 필드가 갱신되지 않는다 — `@Generated`가 있어야 insert 직후 Hibernate가 별도 SELECT(또는 6.5+의 RETURNING)로 DB가 계산한 `reservation_no` 값을 다시 읽어온다. 이 애노테이션이 빠지면 저장 직후 `reservationNo`가 null로 남아 "저장 후 `reservation_no`가 채워지는지" 테스트가 실패한다.
  - `platformId`, `platformReservationRef`, `roomCode`: `String`
  - `dateRange: Range<LocalDate>` — `io.hypersistence.utils.hibernate.type.range.Range` 타입에 `@Type(PostgreSQLRangeType::class)`(`io.hypersistence.utils.hibernate.type.range.PostgreSQLRangeType`) + `@Column(name = "date_range", columnDefinition = "daterange")`를 함께 지정한다. Hibernate 6.2+가 `org.hibernate.range.Range`를 애노테이션 없이 네이티브로 인식한다는 주장은 공식 문서/릴리즈 노트에서 확인되지 않았으므로(리스크 6번 참고) **hypersistence-utils 경로를 1순위로 채택**하고, 애노테이션 없는 네이티브 매핑은 별도로 검증할 필요가 있을 때만 시도한다.
  - `status: ReservationStatus` — `@Enumerated(EnumType.STRING)`
  - `version: Int` — `@Version`
  - `createdAt`, `updatedAt: OffsetDateTime`
  - `fun ReservationEntity.toDomain(): Reservation`, `fun Reservation.toEntity(): ReservationEntity` 확장 함수를 같은 파일에 정의 (도메인의 `ReservationDateRange` ↔ 엔티티의 `Range<LocalDate>` 변환 포함).
- `ReservationRepository.kt` — `interface ReservationRepository : JpaRepository<ReservationEntity, Long>` (+ `findByReservationNo`, `findByPlatformIdAndPlatformReservationRef` 등 조회 메서드는 조회 니즈가 실제로 생기는 후속 티켓에서 추가; 이번 티켓은 기본 CRUD만 보장)
- `ReservationRequestEntity.kt` + `toDomain()`/`toEntity()`
  - `reservationId: Long?` — FK는 컬럼만 매핑(`@Column(name = "reservation_id")`)하고 `@ManyToOne` 연관관계는 만들지 않는다 (교차 애그리게잇 참조를 값으로만 다루는 컨벤션 유지, N+1/불필요한 연관로딩 방지).
  - `action: ReservationRequestAction`, `initiatedBy: RequestInitiator`, `resultStatus: RequestResultStatus` — 모두 `@Enumerated(EnumType.STRING)`
  - `oldDateRange`, `newDateRange: Range<LocalDate>?` — `dateRange`와 동일하게 `@Type(PostgreSQLRangeType::class)` + `columnDefinition = "daterange"` 적용.
- `ReservationRequestRepository.kt` — `interface ReservationRequestRepository : JpaRepository<ReservationRequestEntity, Long>` (+ `findByRequestKey`)
- `OutboundNotificationEntity.kt` + `toDomain()`/`toEntity()`
  - `payload: String` — `@JdbcTypeCode(SqlTypes.JSON)` (Hibernate 6 네이티브 JSON 매핑, `jsonb` 컬럼과 호환)
  - `status: OutboundNotificationStatus` — `@Enumerated(EnumType.STRING)`
- `OutboundNotificationRepository.kt` — `interface OutboundNotificationRepository : JpaRepository<OutboundNotificationEntity, Long>` (+ `findByNotificationKey`, 폴링 워커가 후속 티켓(#18)에서 쓸 `findByStatusInAndNextRetryAtLessThanEqual` 정도는 미리 시그니처만 추가해도 무방하나 필수는 아님 — 필요 최소로 유지)

`id` 필드는 컨벤션상 non-null(`Long`)로 두되, 신규 미저장 엔티티 생성용 팩토리 함수(`Reservation.toEntity()`)에서는 `id = 0`(IDENTITY 전략에서 무시됨) 처리. `!!` 사용 금지 컨벤션 준수 — nullable 언랩은 전부 `requireNotNull`/`?.let` 사용.

### 6. 리스크/결정 사항 (구현 시 검증 필요)

- **`Range<LocalDate>` ↔ `daterange` 매핑**: `hypersistence-utils-hibernate-63`의 `PostgreSQLRangeType`을 1순위로 채택한다. "Hibernate 6.2+가 애노테이션 없이 `Range<LocalDate>`를 네이티브로 매핑한다"는 근거는 웹 검색으로도 공식 문서에서 재확인되지 않았고, Vlad Mihalcea의 레퍼런스 구현도 hypersistence-utils의 `@Type(PostgreSQLRangeType.class)` + `columnDefinition = "daterange"` 조합을 사용한다 — 이 경로로 먼저 구현하고, `ReservationRepositoryTest`가 통과하는 시점에 최종 확정한다.
- **`reservation_no` 생성 컬럼 재조회**: `@Column(insertable = false, updatable = false)`만으로는 insert 후 엔티티에 값이 채워지지 않는다. 반드시 `@Generated(event = [EventType.INSERT])`(`org.hibernate.annotations.Generated`)를 함께 붙여 insert 직후 재조회하도록 한다.
- **`version` 초기값**: 스키마는 `version INT NOT NULL DEFAULT 1`이지만, JPA `@Version` 필드는 insert 시 Hibernate가 항상 명시적으로 값을 채워 넣으므로 DB `DEFAULT`가 실제로 적용되는 경우는 없다(컬럼 값이 항상 명시됨). 따라서 도메인 팩토리에서 신규 `Reservation` 생성 시 `version = 1`을 명시적으로 채워, 스키마 문서가 말하는 "첫 저장 시 version은 1"이라는 불변식과 실제 저장값을 일치시킨다.
- **Flyway vs Liquibase**: 순수 SQL이 이미 `docs/schema/`에 존재하고 팀 컨벤션에 별도 언급이 없어 Flyway를 채택. Liquibase의 changelog 추상화는 이 티켓 스코프에서 이점이 없음.
- **연관관계 매핑 없음**: `reservation_requests.reservation_id`, `outbound_notifications.reservation_id/request_id`는 JPA `@ManyToOne`이 아니라 순수 컬럼(Long)으로 다룬다. Aggregate 간 지연 로딩/N+1 문제를 피하고, `operation` 서버와의 교차 DB 참조 패턴(FK 제약 없음)과 일관성을 맞추기 위함.

## Testing Plan

모든 테스트는 Kotest `FeatureSpec` (`feature { scenario { } }`)로 작성한다.

- **공용 테스트 인프라**: `reservation/src/test/kotlin/.../persistent/PostgresIntegrationTest.kt` — `PostgreSQLContainer` 싱글턴(companion object, JVM당 1회 기동)을 두고 `@DynamicPropertySource`로 `spring.datasource.*`를 등록하는 추상 베이스 클래스. Kotest 스펙은 JUnit5 `@Testcontainers`/`@Container` 라이프사이클 콜백에 온전히 얹히지 않을 수 있어, 프레임워크 무관하게 동작하는 `@DynamicPropertySource` + 싱글턴 컨테이너 패턴을 기본으로 채택한다 (`@ServiceConnection` 자동 구성은 검증되면 대체 가능). 구체 테스트 클래스는 `@DataJpaTest` + `@AutoConfigureTestDatabase(replace = Replace.NONE)`로 이 베이스를 확장.
- **`ReservationEntityMapperTest`** (Spring 컨텍스트 불필요, 순수 단위 테스트): `toDomain()`/`toEntity()` 왕복 변환 검증, `ReservationDateRange` ↔ `Range<LocalDate>` 경계값(시작일/종료일 exclusive) 검증.
- **`ReservationRepositoryTest`** (`@DataJpaTest` + Testcontainers):
  - 기본 저장/조회 후, DB에서 다시 읽어온(또는 `@Generated`로 재조회된) 엔티티의 `reservation_no`가 `platform_id:platform_reservation_ref` 형태로 채워지는지 확인 (`@Generated` 애노테이션이 실제로 동작하는지 검증하는 테스트이기도 함).
  - `excl_room_date_overlap`: 같은 `room_code`에 대해 `CONFIRMED`/`PENDING_CANCEL` 상태이면서 겹치는 `date_range`로 저장 시 예외(`DataIntegrityViolationException`) 발생 검증.
  - 날짜가 겹치지 않으면 저장 성공, `CANCELLED` 상태끼리는 겹쳐도 저장 성공(부분 exclusion 조건 검증).
  - `uq_reservation_no` 위반 시나리오 (동일 `platform_id`+`platform_reservation_ref` 재삽입).
  - 신규 저장 시 `version`이 `1`로 저장되는지 확인 (도메인 팩토리 기본값 검증).
  - `version` optimistic lock: 두 트랜잭션에서 같은 row를 로드 후 순차 업데이트 시 두 번째 커밋에서 `ObjectOptimisticLockingFailureException` 발생 검증.
- **`ReservationRequestRepositoryTest`** (`@DataJpaTest` + Testcontainers): `request_key` UNIQUE 제약 위반 시 예외, `reservation_id`로 조회.

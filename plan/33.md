# 33 [운영] 동일 상품을 노출 중인 다른 채널로 재고 마감/오픈 통보가 팬아웃되지 않음

## Requirements

- 예약 확정(`RESERVATION_CONFIRMED`)/취소확정(`RESERVATION_CANCELLED`) 이벤트 수신 시, 해당 `room_code`를 노출 중인 *다른* 활성 채널(`room_channel_listings`, 이벤트를 발생시킨 채널 자신은 제외)에도 재고 마감/오픈 통보를 `outbox_events`에 함께 발행한다.
- 확정 → 재고 마감(`INVENTORY_CLOSED`), 취소확정 → 재고 오픈(`INVENTORY_REOPENED`).
- 이벤트 payload에 `room_code`가 없다면 필요한 필드를 추가한다.

## Technical Approach

### 0. 실제 병합된 코드 기준 확인

`git pull` 후(main은 #13~#21, #35까지 병합돼 깨끗함, `#34`로 보이는 미커밋 변경이 `OutboundNotificationDispatchWorker` 쪽에 남아있으나 이 티켓과 무관한 파일이라 영향 없음) `InboundEventService.kt`(#20), `RoomRepository`/`RoomChannelListingRepository`/`RoomEntity`/`RoomChannelListingEntity`(#19), 그리고 reservation 쪽 5개 payload data class(`ReservationConfirmedPayload`/`ReservationCancelledPayload`/`ReservationCancelRequestedPayload`/`ReservationChangedPayload`/`ReservationRejectedPayload`, #14~#17+#32)를 직접 읽었다.

- **`room_code`는 이미 모든 payload에 있다** — 5개 private payload data class 전부 `roomCode: String` 필드를 갖고 있다(코드로 직접 확인). 이슈가 "필요하다면 추가"라고 조건부로 적어둔 부분은 **이미 충족돼 있어 reservation 쪽 변경이 필요 없다**.
- **`RoomRepository`/`RoomChannelListingRepository`는 여전히 커스텀 조회 메서드가 없다** (`JpaRepository<T, Long>`만) — plan/19.md가 "실제 니즈가 생기는 후속 티켓에서 추가"로 미뤄둔 부분이 바로 이 티켓이다. `RoomChannelListingEntity.platformId`가 리스팅 행에 이미 직접 저장돼 있어(스키마 설계상 `ota_channels`를 조인하지 않고도 통보 대상 채널의 `platform_id`를 바로 얻을 수 있다) — `otaChannelId`를 거쳐 `OtaChannelRepository`까지 조인할 필요가 없다.
- **중요한 운영상의 사실**: `hosts`/`ota_channels`/`rooms`/`room_channel_listings`를 채우는 CRUD API/서비스가 이 프로젝트 어디에도 아직 없다(#19는 엔티티/리포지토리까지만, 그 이후 어떤 티켓도 이 마스터 데이터의 생성 경로를 만들지 않았다). 즉 **지금 실제로 이벤트가 들어와도 `rooms`/`room_channel_listings`가 비어있어 팬아웃이 실질적으로 발생하지 않는다** — 이 티켓은 로직을 올바르게 구현하고 테스트로 검증하는 것이지, 실제 데이터가 있어야 동작을 "보게" 되는 건 아니다. 이 갭 자체는 이 티켓 범위가 아니므로 별도 이슈로 남겨두는 것을 제안한다(마스터 데이터 등록 API는 이 프로젝트에서 아직 다뤄지지 않은 영역).

### 1. 팬아웃 대상 이벤트 타입 — 재고가 실제로 바뀌는 두 이벤트만

기획문서 4.1~4.4를 다시 확인한 결과, "재고 마감/오픈"은 실제로 방의 점유 상태가 바뀌는 시점에만 의미가 있다:

| 원본 이벤트 | 재고 변화 | 팬아웃 이벤트 |
|---|---|---|
| `RESERVATION_CONFIRMED` | 점유 시작(마감) | `INVENTORY_CLOSED` |
| `RESERVATION_CANCELLED` | 점유 해제(오픈) | `INVENTORY_REOPENED` |
| `CANCEL_REQUESTED` | 없음(`PENDING_CANCEL`도 여전히 점유 상태 유지) | 팬아웃 안 함 |
| `RESERVATION_REJECTED` | 없음(애초에 점유된 적 없음 — BOOK 겹침 거부, CHANGE 겹침 거부 둘 다) | 팬아웃 안 함 |

```kotlin
private val FAN_OUT_EVENT_TYPE_BY_SOURCE =
    mapOf(
        "RESERVATION_CONFIRMED" to "INVENTORY_CLOSED",
        "RESERVATION_CANCELLED" to "INVENTORY_REOPENED",
    )
```

`CHANGE`(`RESERVATION_CHANGED`)는 기획문서 4.4가 팬아웃을 명시하지 않고, 이슈 본문도 "예약 확정/취소확정"만 언급하므로 이번 티켓 범위에서 제외한다 — 필요하면 별도 이슈로 분리(날짜 변경은 기존 구간 오픈 + 신규 구간 마감이 동시에 일어나 로직이 더 복잡해짐).

### 2. 리포지토리 신규 메서드

```kotlin
interface RoomRepository : JpaRepository<RoomEntity, Long> {
    fun findByRoomCode(roomCode: String): RoomEntity?
}

interface RoomChannelListingRepository : JpaRepository<RoomChannelListingEntity, Long> {
    fun findByRoomId(roomId: Long): List<RoomChannelListingEntity>
}
```

상태 필터링(`ACTIVE`만, 자기 자신 제외)은 리포지토리 메서드 시그니처를 늘리기보다 서비스 레이어에서 `.filter { }`로 처리한다 — 노출 채널 수가 방 하나당 소수(수 개 채널)일 것으로 예상돼 DB 쿼리 조건을 늘리는 것보다 단순함이 낫다고 판단(`ReservationRepository`가 조회 메서드를 최소로 유지해온 것과 같은 태도).

### 3. `InboundEventService.processNew()` — 원본 통보 저장 후, 같은 트랜잭션에서 팬아웃

```kotlin
private fun processNew(request: InboundEventRequest) {
    transactionTemplate.execute {
        val payloadJson = objectMapper.writeValueAsString(request.payload)
        inboundEventRepository.saveAndFlush(InboundEvent(..., payload = payloadJson, ...).toEntity())

        val platformId = requireNotNull(request.payload.get("platformId")?.asText()) { ... }
        outboxEventRepository.saveAndFlush(
            OutboxEvent(
                outboxKey = "${request.reservationNo}:OTA_CHANNEL:$platformId:${request.eventType}",
                targetType = OutboxTargetType.OTA_CHANNEL,
                targetCode = platformId,
                reservationNo = request.reservationNo,
                eventType = request.eventType,
                payload = payloadJson,
                status = OutboxEventStatus.PENDING,
                retryCount = 0,
                nextRetryAt = LocalDateTime.now(),
            ).toEntity(),
        )

        FAN_OUT_EVENT_TYPE_BY_SOURCE[request.eventType]?.let { fanOutEventType ->
            fanOutToOtherChannels(request, payloadJson, platformId, fanOutEventType)
        }
    }
}

private fun fanOutToOtherChannels(
    request: InboundEventRequest,
    payloadJson: String,
    originatingPlatformId: String,
    fanOutEventType: String,
) {
    val roomCode =
        requireNotNull(request.payload.get("roomCode")?.asText()) {
            "payload에 roomCode가 없습니다: notificationKey=${request.notificationKey}"
        }
    // 방 마스터 데이터가 아직 없으면(이 프로젝트에 등록 API가 없어 흔히 있을 수 있는 상태) 팬아웃 대상도
    // 없다는 뜻이므로 조용히 건너뛴다 — 원본 통보(이벤트를 발생시킨 채널 대상)는 이미 위에서 저장됐으니
    // 실패로 처리하지 않는다.
    val room = roomRepository.findByRoomCode(roomCode) ?: return

    roomChannelListingRepository
        .findByRoomId(room.id)
        .filter { it.status == RoomChannelListingStatus.ACTIVE && it.platformId != originatingPlatformId }
        // 리스팅은 활성이어도 채널 자체가 SUSPENDED일 수 있다 — 이슈 본문엔 명시가 없지만, 중단된
        // 채널에 통보를 보내는 건 의미가 없으므로 채널 상태도 함께 확인한다 (#21이 이미 만들어둔
        // OtaChannelRepository.findByPlatformId를 재사용, 새 조회 메서드 불필요).
        .filter { listing -> otaChannelRepository.findByPlatformId(listing.platformId)?.status == OtaChannelStatus.ACTIVE }
        .forEach { listing ->
            outboxEventRepository.saveAndFlush(
                OutboxEvent(
                    outboxKey = "${request.reservationNo}:OTA_CHANNEL:${listing.platformId}:$fanOutEventType",
                    targetType = OutboxTargetType.OTA_CHANNEL,
                    targetCode = listing.platformId,
                    reservationNo = request.reservationNo,
                    eventType = fanOutEventType,
                    payload = payloadJson,   // 원본 payload를 그대로 재사용 — roomCode/날짜 등 다른 채널이 필요로 할 정보가 이미 다 들어있어 새 payload 형태를 만들지 않는다.
                    status = OutboxEventStatus.PENDING,
                    retryCount = 0,
                    nextRetryAt = LocalDateTime.now(),
                ).toEntity(),
            )
        }
}
```

- `RESERVATION_CONFIRMED`/`RESERVATION_CANCELLED`는 예약 생애주기에서 각각 최대 한 번만 발생하므로(reservation 쪽 설계상 보장됨), `reservation_no:OTA_CHANNEL:<다른채널>:INVENTORY_CLOSED|REOPENED` 형태의 `outbox_key`는 별도 타임스탬프/`request_id` 없이도 자연히 유일하다 (`CHANGE`처럼 반복 가능한 액션이 아님 — plan/17.md 4번에서 다룬 유일성 문제가 여기선 재현되지 않는다).
- 팬아웃 도중 예외가 나면 트랜잭션 전체(원본 통보 포함)가 롤백된다 — 별도 격리 장치를 두지 않는다. `receive()`가 이미 `notification_key` 기준으로 재시도-안전하게 설계돼 있어(#20), reservation 쪽 발신 워커가 나중에 같은 알림을 재전송하면 처음부터 다시 시도된다. 이 정도로 충분하다고 판단(과설계 지양).

## Testing Plan

#20이 이미 만들어둔 `operation/.../controller/InboundEventControllerTest.kt`(MockMvc 기반)에 시나리오를 추가하는 방식으로 확장한다.

- **2개 이상 채널에 노출된 방에 예약 확정 이벤트 수신**: `rooms` 1건 + 같은 `room_code`로 `room_channel_listings` 3건(플랫폼 A/B/C, 전부 `ACTIVE`) 픽스처 생성 → `platformId=A`로 `RESERVATION_CONFIRMED` 수신 → `outbox_events`가 정확히 3건(원본 A 대상 `RESERVATION_CONFIRMED` 1건 + B/C 대상 `INVENTORY_CLOSED` 2건) 생성되는지 검증. A 자신에게 `INVENTORY_CLOSED`가 추가로 가지 않는지도 확인.
- **취소확정 이벤트는 `INVENTORY_REOPENED`로 팬아웃**: 위와 동일한 구조로 `RESERVATION_CANCELLED` 수신 시 B/C에 `INVENTORY_REOPENED` 검증.
- **노출 채널이 자기 자신뿐이면 팬아웃 없음**: `room_channel_listings`가 A 하나뿐인 상태에서 `RESERVATION_CONFIRMED` 수신 → `outbox_events`가 원본 1건만 생성(팬아웃 0건) 검증 (이슈가 명시한 테스트 케이스).
- **비활성 리스팅/채널 제외**: B는 리스팅 `INACTIVE`, C는 리스팅은 `ACTIVE`이지만 `ota_channels.status=SUSPENDED` → 둘 다 팬아웃 대상에서 빠지는지 검증.
- **`CANCEL_REQUESTED`/`RESERVATION_REJECTED`는 팬아웃 없음**: 원본 통보 1건만 생성되고 팬아웃이 발생하지 않는지 검증 (재고 변화가 없는 이벤트라는 1번 결정 사항의 근거를 테스트로 증명).
- **방을 찾을 수 없으면 팬아웃만 건너뛰고 원본 통보는 정상 저장**: `rooms`에 해당 `room_code`가 아예 없는 상태에서 이벤트 수신 → `200` 응답, 원본 `outbox_events` 1건은 정상 생성, 예외 없음 검증 (마스터 데이터 미비 상태에서도 시스템이 정상 동작함을 증명).
- CI/로컬 실행 전제: Docker 데몬 필요(Testcontainers, MySQL) — 기존과 동일.

# 34 [운영] 예약 변경(RESERVATION_CHANGED) 통보가 호스트/다른 채널로 전달되지 않음

## Requirements

- reservation 서버가 CHANGE 성공 시 발행하는 `RESERVATION_CHANGED` 이벤트를 operation이 알지 못해(#20/#33이 명시적으로 스코프 밖으로 뺐던 부분) 매번 `400`으로 거부되고 있었다 — reservation의 발신 워커는 이를 발송 실패로 보고 재시도하다가 `maxRetryCount` 소진 시 `DEAD`로 영구 종료한다. 즉 **예약 변경 통보가 항상 유실**되고 있었다(기획문서 6.3 "통보 유실이 발생하지 않는다" 위반).
- 예약 변경은 (a) 예약을 소유한 원 채널, (b) 같은 방을 노출 중인 다른 활성 OTA 채널, (c) 방을 소유한 호스트 — 세 곳 모두에 통보가 가야 한다.

## Technical Approach

### 1. `KNOWN_EVENT_TYPES`에 `RESERVATION_CHANGED` 추가

원 채널(OTA_CHANNEL) 대상 통보는 기존 `OutboxEvent.of(...)` 경로가 이벤트 타입에 무관하게 이미 처리하므로, 이 목록에 추가하는 것만으로 (a)는 자동으로 해결된다.

### 2. `FAN_OUT_EVENT_TYPE_BY_SOURCE`에 `RESERVATION_CHANGED` → `INVENTORY_CHANGED` 추가

#33이 확립한 팬아웃 로직(`fanOutToOtherChannels`)을 그대로 재사용한다. #33/#20이 CHANGE를 스코프에서 뺀 이유("기존 구간 오픈 + 신규 구간 마감이 동시에 일어나 로직이 더 복잡해짐")는, `ReservationChangedPayload`에 `oldStartDate`/`oldEndDate`/`newStartDate`/`newEndDate`가 이미 다 담겨 있다는 점(#17)을 감안하면 실제로는 문제가 아니다 — 이벤트를 둘로 쪼개지 않고 `INVENTORY_CHANGED` 하나로 원본 payload를 그대로 재사용해 전달하면, 받는 쪽이 old/new 두 정보를 한 번에 얻는다.

### 3. `OutboxEvent.ofHost(...)` 신규 팩토리 + `InboundEventService.notifyHost(...)`

`RESERVATION_CHANGED` 수신 시 payload의 `roomCode`로 `rooms`를 찾고, `rooms.host_id`(내부 FK)로 `hosts`를 찾아 `hosts.host_id`(논리 키)를 `targetCode`로 하는 `HOST` 대상 `outbox_events` row를 만든다. 방/호스트 마스터 데이터가 없으면 팬아웃과 동일한 원칙으로 조용히 건너뛰고 원본 통보는 그대로 저장한다.

`#21`이 이미 만들어둔 `deliverToHost` 스텁(로그만 남기고 `SENT` 처리 — hosts 테이블에 웹훅/콜백 채널이 없어 실제 발송 인프라가 없음)을 그대로 재사용한다. `#21`의 "이 분기는 지금은 절대 실행되지 않는다"는 전제는 이제 틀렸지만(`RESERVATION_CHANGED`가 실제로 이 경로를 태운다), 스텁으로 유지한다는 결정 자체는 그대로 유효하다 — 실제 이메일/SMS 발송 인프라는 여전히 이 프로젝트 범위 밖이다.

## 리뷰 중 발견해 함께 수정한 문제

구현 후 재검토 과정에서 outbox_key 충돌로 인한 통보 유실 가능성을 발견해 같은 티켓에서 함께 고쳤다.

- **문제**: `outbox_key`가 `reservationNo:targetType:targetCode:eventType`로만 구성돼 있었다. 같은 방이 같은 `platform_id`에 대해 `external_product_id`가 다른 리스팅을 2개 이상 가지면(스키마상 가능 — `uq_listing_key`는 `platform_id` 단독이 아니라 `(platform_id, external_product_id)` 조합에 걸려 있다), `fanOutToOtherChannels`가 두 리스팅에 대해 동일한 `outbox_key`로 insert를 시도해 `DataIntegrityViolationException`이 났다. `receive()`의 범용 catch가 이를 `notification_key` 동시 중복 수신 레이스로 오인해 트랜잭션 전체(원본 통보 포함)를 롤백시키면서도 `200`을 반환 — 통보가 조용히 유실됐다.
- **수정 1**: `OutboxEvent.ofB(...)`의 `outboxKey`에 `listing.externalProductId`를 포함해 리스팅별로 유일하게 만들었다(`targetCode`는 여전히 `platformId`만 — 채널 조회에 쓰이므로 그대로 둠).
- **수정 2 (방어 로직)**: `receive()`의 `catch (DataIntegrityViolationException)`가 무조건 성공 처리하던 것을, catch 후 `findByNotificationKey`로 재확인하도록 바꿨다 — 진짜 존재하면(=notification_key 레이스 맞음) 성공 처리하고, 없으면(=다른 제약 위반으로 롤백된 것) 예외를 다시 던져 호출자가 재시도/에러를 받게 한다(reservation의 `recordConflict`와 동일한 재확인 패턴). 수정 1로 현재 알려진 충돌 원인은 없어졌지만, 앞으로 비슷한 종류의 예상 못한 제약 위반이 생겨도 조용히 유실되지 않도록 하는 일반적인 방어책이다.
- 테스트로 재현: 같은 채널에 `external_product_id`만 다른 리스팅 2개를 둔 방에 예약 확정 이벤트를 보내 `outbox_events` 3건(원 채널 1 + 다른 리스팅 2)이 각각 다른 `outbox_key`로 정상 생성되는지 검증.

## Testing Plan

`operation/.../controller/InboundEventControllerTest.kt`에 시나리오를 추가하는 방식으로 확장했다.

- **`RESERVATION_CHANGED` 신규 수신 성공**: 기존 4개 이벤트 타입 목록에 추가해 동일한 검증(원 채널 대상 `outbox_events` 1건) 재사용.
- **다른 채널로 `INVENTORY_CHANGED` 팬아웃**: 2개 이상 채널에 노출된 방에 `RESERVATION_CHANGED` 수신 → 원 채널을 제외한 다른 채널에 `INVENTORY_CHANGED` 통보 생성 검증.
- **호스트 대상 `outbox_event` 생성**: `RESERVATION_CHANGED` 수신 시 방을 소유한 호스트의 `host_id`를 `targetCode`로 갖는 `HOST` 대상 row가 생기는지 검증.
- **변경이 아닌 이벤트는 호스트 통보 없음**: `RESERVATION_CONFIRMED` 등 다른 이벤트 타입은 `HOST` 대상 `outbox_event`를 만들지 않는지 검증.
- **호스트를 찾을 수 없으면 호스트 통보만 건너뜀**: 방 마스터 데이터가 없으면 원본 통보(`OTA_CHANNEL` 대상)는 정상 저장되고 `HOST` 대상 row만 생성되지 않는지 검증.
- **같은 채널에 서로 다른 상품 코드로 2개 리스팅된 방**: `outbox_key` 충돌 없이 각각 별도 팬아웃되는지 검증(수정 1의 회귀 테스트).
- CI/로컬 실행 전제: Docker 데몬 필요(Testcontainers, MySQL) — 기존과 동일.

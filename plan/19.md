# 19 [운영] Operation 서버 MySQL 전환 + 스키마/도메인/Entity/Repository

## Requirements

- `operation` 모듈의 datasource를 H2 → MySQL 8.0+로 전환한다 (운영/개발 모두 실제 MySQL 사용, 테스트는 Testcontainers).
- `docs/schema/operation_server_schema.sql`의 6개 테이블을 실제 DB 스키마로 반영한다: `hosts`, `ota_channels`, `rooms`(hosts FK), `room_channel_listings`(rooms/ota_channels FK, 생성 컬럼 `listing_key`), `inbound_events`(수신측 멱등성, `notification_key` UNIQUE), `outbox_events`(발신용 Transactional Outbox, `outbox_key` UNIQUE).
- 컨벤션대로 `domain`(순수 Kotlin)과 `persistent`(`@Entity`+`Repository`, `toDomain()`/`toEntity()`)를 분리한다.
- 이번 티켓 범위는 스키마 마이그레이션 + 도메인/엔티티/리포지토리까지다. 수신 API(#20)와 발신 워커(#21)는 후속 티켓에서 다룬다 — `controller`/`service` 패키지는 건드리지 않는다.

## Technical Approach

### 0. reservation 모듈(#13, PR #22)의 전례를 그대로 참고하되, MySQL이라 달라지는 지점을 구분한다

`reservation` 모듈이 Postgres 전환 때 겪은 시행착오(PR #22의 "Plan과의 구현 시 결정/차이점")를 그대로 재사용할 수 있는 부분과, MySQL이라서 근본적으로 다르게 가야 하는 부분을 나눠서 설계한다.

**그대로 재사용 가능** (DB 무관):
- `domain`/`persistent` 분리, `toDomain()`/`toEntity()` 매퍼 패턴.
- `@Id @GeneratedValue(strategy = GenerationType.IDENTITY)` — MySQL의 `AUTO_INCREMENT`도 Postgres의 `GENERATED ALWAYS AS IDENTITY`와 동일하게 `IDENTITY` 전략으로 매핑된다.
- Flyway로 스키마를 직접 관리하고 `ddl-auto: validate`만 쓰는 원칙, `docs/schema/operation_server_schema.sql`을 그대로 마이그레이션 파일로 복사.
- 생성 컬럼(`reservation_no` ↔ `listing_key`)에 `@Column(insertable=false, updatable=false)` + `@Generated`가 필요하다는 교훈.
- `payload` JSON 컬럼에 `@JdbcTypeCode(SqlTypes.JSON)` 매핑 (MySQL의 `JSON` 타입도 Hibernate 6의 동일 메커니즘으로 매핑된다, `columnDefinition = "json"`으로 지정).

**MySQL이라서 다르게 가야 하는 지점** (아래 1~3번에서 상세):
1. Flyway MySQL 지원 모듈이 `flyway-core`에 번들되어 있지 않다 (Postgres와 같은 패턴, 다른 좌표).
2. 타임스탬프 타입 — 스키마가 `DATETIME(6)`을 쓰므로 `OffsetDateTime`이 아니라 `LocalDateTime`을 써야 한다.
3. `created_at`/`updated_at`을 애플리케이션이 아니라 **MySQL 스스로 관리**한다 (`DEFAULT CURRENT_TIMESTAMP(6)` / `ON UPDATE CURRENT_TIMESTAMP(6)`) — reservation 모듈은 반대로 애플리케이션이 `OffsetDateTime.now()`를 직접 채워 넣는다.

MySQL support is a separate dependency... `org.flywaydb:flyway-mysql`"). reservation 모듈의 `flyway-database-postgresql`과 정확히 같은 이유·같은 패턴.
- 추가 (test):
  - `testImplementation("org.springframework.boot:spring-boot-testcontainers")`
  - `testImplementation("org.testcontainers:junit-jupiter")`

- `hypersistence-utils`는 필요 없다 — operation 스키마는 PostgreSQL range 타입을 쓰지 않는다 (reservation 전용 의존성).

### 4. `domain` 패키지 (신규, 순수 Kotlin)

경로: `operation/src/main/kotlin/yeo/chi/proejct/pms/operation/domain/`

값이 같은 상태 enum(예: `hosts.status`/`ota_channels.status`가 둘 다 ACTIVE/SUSPENDED)이라도 서로 다른 도메인 개념이므로 **공유하지 않고 테이블별로 분리한다** (한쪽에만 상태값이 추가돼야 할 때 다른 쪽까지 강제로 오염되는 걸 방지 — reservation 모듈이 `ReservationRequestAction`/`CancelRequestReason`을 개념별로 분리한 것과 같은 원칙).

- `HostStatus.kt`(`ACTIVE`/`SUSPENDED`), `Host.kt`(`id`, `hostCode`, `name`, `contactEmail: String?`, `contactPhone: String?`, `status`, `createdAt`, `updatedAt`)
- `OtaChannelIntegrationMode.kt`(`SYNC`/`ASYNC`), `OtaChannelStatus.kt`(`ACTIVE`/`SUSPENDED`), `OtaChannel.kt`(`id`, `platformId`, `name`, `integrationMode`, `callbackBaseUrl: String?`, `apiKeyRef: String?`(시크릿 매니저 참조 키 — 평문 시크릿 자체가 아님, 스키마 주석 그대로), `status`, `createdAt`, `updatedAt`)
- `RoomStatus.kt`(`ACTIVE`/`INACTIVE`), `Room.kt`(`id`, `roomCode`, `hostId: Long`, `name`, `address: String?`, `capacity: Int?`, `status`, `createdAt`, `updatedAt`)
- `RoomChannelListingStatus.kt`(`ACTIVE`/`INACTIVE`), `RoomChannelListing.kt`(`id`, `listingKey: String?`(생성 컬럼, 신규 미저장 인스턴스는 null), `roomId: Long`, `otaChannelId: Long`, `platformId`, `externalProductId`, `status`, `createdAt`, `updatedAt`)
- `InboundEvent.kt`(`id`, `notificationKey`, `reservationNo`, `eventType`, `payload: String`, `receivedAt`) — reservation 서버의 `reservation_no`를 문자열로만 보관(교차 DB, FK 없음).
- `OutboxTargetType.kt`(`OTA_CHANNEL`/`HOST`), `OutboxEventStatus.kt`(`PENDING`/`SENT`/`FAILED`/`DEAD`), `OutboxEvent.kt`(`id`, `outboxKey`, `targetType`, `targetCode`, `reservationNo`, `eventType`, `payload: String`, `status`, `retryCount: Int`, `nextRetryAt`, `createdAt`, `updatedAt`)
- **타임스탬프 필드는 전부 `java.time.LocalDateTime`**(`OffsetDateTime` 아님) — 5번 참고.

### 5. 타임스탬프 타입 — `LocalDateTime`을 쓰는 이유 (reservation과의 핵심 차이)

스키마는 `TIMESTAMPTZ`(Postgres, reservation)가 아니라 **`DATETIME(6)`**(MySQL, operation)을 쓴다. `DATETIME`은 타임존 정보를 전혀 갖지 않는 타입이다 (MySQL의 `TIMESTAMP`와 다름 — `TIMESTAMP`는 UTC로 저장 후 세션 타임존에 맞춰 변환하지만, 이 스키마는 `DATETIME`을 선택했다). 따라서 `OffsetDateTime`으로 매핑하면 DB 컬럼이 실제로 갖지 않는 오프셋 정보를 애플리케이션이 임의로 가정하게 되어 의미상 틀리다. **`java.time.LocalDateTime`**으로 매핑하는 것이 스키마의 실제 의미와 일치한다. 이는 reservation 모듈의 관례(`OffsetDateTime`)를 그대로 복사하면 안 되는 지점이므로, PR 설명에 명시적으로 남긴다.

### 6. `created_at`/`updated_at`을 애플리케이션이 아니라 DB가 관리한다 (reservation과의 두 번째 핵심 차이)

reservation 스키마는 `updated_at TIMESTAMPTZ NOT NULL DEFAULT now()`만 있고 `ON UPDATE` 트리거가 없어서, `ReservationService`가 매번 `OffsetDateTime.now()`를 직접 채워 넣는다. operation 스키마는 4개 마스터 테이블(`hosts`/`ota_channels`/`rooms`/`room_channel_listings`)과 `outbox_events`에 **`updated_at ... DEFAULT CURRENT_TIMESTAMP(6) ON UPDATE CURRENT_TIMESTAMP(6)`**를 명시적으로 선언해뒀다 — 이건 "MySQL이 알아서 관리하게 하라"는 스키마 설계자의 의도로 읽는 게 맞다 (reservation과 다르게 설계된 것이 실수가 아니라 의도임).

- `createdAt`/`updatedAt`은 `@Column(insertable=false, updatable=false)` + **`@Generated(event = [EventType.INSERT, EventType.UPDATE])`**로 매핑한다 (reservation의 `reservation_no`가 `EventType.INSERT`만 쓰는 것과 달리, `updated_at`은 UPDATE 시에도 DB가 값을 다시 계산하므로 두 이벤트 모두 필요 — Hibernate가 INSERT/UPDATE 직후 각각 재조회한다).
- `inbound_events.received_at`은 `DEFAULT CURRENT_TIMESTAMP(6)`만 있고 `ON UPDATE`가 없다(append-only 테이블이라 자연스러움) — `EventType.INSERT`만 지정한다 (reservation_no와 동일 패턴).
- 애플리케이션 코드에서 이 필드들에 값을 채워 넣지 않는다 — `toEntity()` 매퍼도 이 필드들을 무시하거나, 엔티티 생성자에서 nullable로 두고 신규 저장 시 무시되도록 한다 (신규 미저장 `Host`/`OtaChannel`/... 도메인 인스턴스는 `createdAt`/`updatedAt`을 애초에 안 가짐 — `Reservation.createNew()`가 `id`/`reservationNo`를 null로 두는 것과 같은 패턴을, 여기서는 시각 필드까지 확장한 것).

### 7. `persistent` 패키지 — FK가 실제로 있어도 `@ManyToOne`은 쓰지 않는다

`rooms.host_id`, `room_channel_listings.room_id`/`ota_channel_id`는 reservation 모듈과 달리 **같은 DB 안의 진짜 FK 제약**이다 (`REFERENCES hosts(id)` 등). 그럼에도 다음 이유로 plain `Long` 컬럼(연관관계 매핑 없음)을 유지한다:

- reservation 모듈이 이미 확립한 컨벤션(교차 애그리게잇 참조는 값으로만 다룸)과의 일관성.
- 아직 `service` 계층이 없어 지연 로딩/조인 전략을 어떻게 쓸지 알 수 없는 시점에 성급하게 연관관계를 맺을 이유가 없음(YAGNI — reservation의 `ReservationRepository`가 조회 메서드를 "니즈가 생기는 후속 티켓까지" 미룬 것과 같은 태도).
- FK 제약 자체는 DB 레벨에서 그대로 무결성을 보장하므로, `@ManyToOne` 없이도 참조 무결성 검증(7번 테스트 계획)은 가능하다.

각 엔티티(`HostEntity`, `OtaChannelEntity`, `RoomEntity`, `RoomChannelListingEntity`, `InboundEventEntity`, `OutboxEventEntity`)는 reservation의 `ReservationEntity` 패턴을 그대로 따른다: `@Id @GeneratedValue(IDENTITY)`, `@Enumerated(EnumType.STRING)` 상태 필드, 생성 컬럼(`listing_key`)에 `insertable/updatable=false` + `@Generated`, `payload`에 `@JdbcTypeCode(SqlTypes.JSON)` + `columnDefinition = "json"`.

- `RoomEntity`/`RoomChannelListingEntity`의 상태 필드(`status`)는 향후(#20/#21 이후) 상태 전이가 있을 수 있으므로 reservation의 `ReservationEntity.status` 전례처럼 **`var`**로 둔다. 나머지 필드는 `val` 유지.
- 리포지토리는 reservation `#13`의 전례를 그대로 따라 **멱등키 조회 메서드만 지금 추가**하고, 그 외 조회는 미룬다:
  - `InboundEventRepository : JpaRepository<InboundEventEntity, Long> { fun findByNotificationKey(notificationKey: String): InboundEventEntity? }` — #20이 수신 멱등성 체크에 바로 쓸 수 있어야 하므로 (reservation의 `ReservationRequestRepository.findByRequestKey`가 #13에서 이미 추가됐던 것과 동일한 이유).
  - `OutboxEventRepository : JpaRepository<OutboxEventEntity, Long> { fun findByOutboxKey(outboxKey: String): OutboxEventEntity? }` — 동일한 이유 (reservation의 `OutboundNotificationRepository.findByNotificationKey`와 대칭).
  - `HostRepository`/`OtaChannelRepository`/`RoomRepository`/`RoomChannelListingRepository`는 `JpaRepository<T, Long>`만 두고 커스텀 메서드는 추가하지 않는다 (`ReservationRepository`가 #13에서 그랬던 것과 동일 — #20/#21에서 실제 조회 니즈가 생기면 그때 추가).

## Testing Plan

모든 테스트는 Kotest `FeatureSpec`.

- **공용 테스트 인프라**: `operation/src/test/kotlin/.../persistent/MySqlIntegrationTest.kt` — `PostgresIntegrationTest`와 대칭되는 `MySQLContainer` 싱글턴(companion object) + `@DynamicPropertySource` 베이스 클래스.
- **엔티티 매퍼 단위 테스트**(Spring 컨텍스트 불필요): 6개 엔티티 각각 `toDomain()`/`toEntity()` 왕복 변환 검증.
- **`HostRepositoryTest`**: 기본 CRUD, `uq_host_code` 위반 시 `DataIntegrityViolationException` 검증, `created_at`/`updated_at`이 저장 직후 자동으로 채워지는지(`@Generated` 동작 확인) 검증, 이후 값을 바꿔 재저장했을 때 `updated_at`이 갱신되는지(`ON UPDATE` 트리거 동작 확인 — `created_at`은 그대로인지도 함께) 검증.
- **`OtaChannelRepositoryTest`**: `uq_platform_id` 위반 검증, 기본 CRUD.
- **`RoomRepositoryTest`**: `uq_room_code` 위반 검증. 존재하지 않는 `host_id`로 저장 시 FK 제약 위반(`DataIntegrityViolationException`) 검증.
- **`RoomChannelListingRepositoryTest`**: 저장 후 `listing_key`가 `platform_id:external_product_id` 형태로 채워지는지(`@Generated` 검증, reservation의 `reservation_no` 테스트와 대칭) 확인. `uq_listing_key` 위반 검증. 존재하지 않는 `room_id`/`ota_channel_id`로 저장 시 FK 위반 검증.
- **`InboundEventRepositoryTest`**: `uq_notification_key` 위반 검증, `findByNotificationKey` 조회 검증.
- **`OutboxEventRepositoryTest`**: `uq_outbox_key` 위반 검증, `findByOutboxKey` 조회 검증.
- **기존 `OperationApplicationTests`/`OperationModuleSmokeTest` 갱신**: H2 제거로 실제 datasource가 필요해지므로 `MySqlIntegrationTest`를 사용하도록 업데이트해 컨텍스트 로딩(Flyway 마이그레이션 성공 포함)을 검증한다.
- CI/로컬 실행 전제: Docker 데몬 필요(Testcontainers) — reservation 모듈과 동일.

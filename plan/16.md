# 16 [예약] 호스트 취소요청(CANCEL_REQUEST) 처리 - PENDING_CANCEL 전이

## Requirements

- 호스트가 취소요청(CANCEL_REQUEST)을 보내면 대상 예약 상태를 `CONFIRMED → PENDING_CANCEL`로 전환한다. 호스트는 취소를 **확정**할 권한이 없다 — 최종 확정은 항상 OTA의 취소통보(#15 CANCEL_CONFIRM)가 도착한 시점이다 (기획문서 2.3 핵심 원칙).
- `PENDING_CANCEL` 상태에서도 재고는 계속 점유 상태로 유지한다 (신규 판매 불가). `excl_room_date_overlap` GIST exclusion 제약은 이미 `WHERE status IN ('CONFIRMED', 'PENDING_CANCEL')`로 PENDING_CANCEL도 겹침 방지 대상에 포함하고 있으므로, 이 전이 로직이 그 제약을 깨지 않는지 확인한다 (아래 2번 근거 참고 — 실제로는 깨질 여지가 없음을 설계로 증명한다).
- `reservation_requests`에 `initiated_by=HOST`, `action=CANCEL_REQUEST`로 기록하고, 호스트가 제시한 취소 사유(오버부킹 정리/시설 문제/기타)를 함께 남긴다.
- `outbound_notifications`에 `CANCEL_REQUESTED` 이벤트를 예약 상태 변경과 같은 트랜잭션으로 append한다 (운영 서버가 대상 OTA에 전달).
- 이미 `PENDING_CANCEL`이거나 `CANCELLED`인 예약에 대한 재요청은 적절히 거부/멱등 처리한다.
- `controller`는 이번 티켓 범위 밖 (#14/#15와 동일한 스코프 경계).

## Technical Approach

### 0. 실제 병합 상태 확인 — main은 아직 BOOK(#14)까지만 포함한다

`git pull` 후 `git log --oneline`으로 직접 확인: main은 `#23`(BOOK, #14) 머지까지만 반영돼 있다. **`#24`(CANCEL_CONFIRM, #15)는 아직 `OPEN` 상태로 병합되지 않았다** (`gh pr view 24` 확인). 즉 지금 시점의 `ReservationRepository`는

```kotlin
interface ReservationRepository : JpaRepository<ReservationEntity, Long>
```

그대로이고, `ReservationService`에는 `book()`만 있다. 이 플랜은 이 실제 상태를 기준으로 작성한다.

- PR #24(아직 미병합)는 CANCEL_CONFIRM을 위해 `ReservationRepository.findByPlatformIdAndPlatformReservationRef(...)`를 새로 추가할 예정이다(plan/15.md 참고). **CANCEL_REQUEST는 이 메서드가 필요 없다** — 아래 1번 참고. 따라서 이번 티켓과 #15 사이에 `ReservationRepository`를 둘러싼 실질적인 충돌은 없을 것으로 예상되지만, 구현 시작 시점에 `#15`가 먼저 머지돼 있을 수 있으므로 그때의 `main`을 다시 확인해서 이미 있는 메서드를 중복 추가하지 않도록 주의한다.

### 1. 대상 예약 식별 — 새 조회 메서드가 필요 없다

CANCEL_CONFIRM(#15)은 **OTA가 자기 쪽 참조값**(`platformId`+`platformReservationRef`)으로 예약을 지목하므로 커스텀 조회 메서드가 필요했다. 반면 CANCEL_REQUEST는 **호스트가 우리 시스템 안에서** 취소를 요청하는 흐름이고, `reservations.id`(내부 기술 PK)는 이미 `JpaRepository<ReservationEntity, Long>`가 기본으로 제공하는 `findById(id): Optional<ReservationEntity>`로 조회 가능하다. 따라서 **`ReservationRepository`에 아무 것도 추가하지 않는다.**

```kotlin
// service/CancelRequestCommand.kt
data class CancelRequestCommand(
    val reservationId: Long,
    val reason: CancelRequestReason,
)
```

### 2. 취소 사유 — 신규 domain enum, `reservation_requests.reject_reason` 컬럼 재사용

기획문서 4.3은 사유를 "오버부킹 정리 / 시설 문제 / 기타"로 명시한다. 다른 액션들의 관례(`ReservationRequestAction`, `RequestInitiator`, `RequestResultStatus` 모두 도메인 enum)를 따라 새 domain enum을 추가한다:

```kotlin
// domain/CancelRequestReason.kt
enum class CancelRequestReason {
    OVERBOOKING_CLEANUP,
    FACILITY_ISSUE,
    OTHER,
}
```

**결정 사항**: 스키마에는 "호스트가 취소를 요청한 사유"를 담을 전용 컬럼이 없다. `reservation_requests.reject_reason VARCHAR(50)`은 주석상 "예: 'DUPLICATE_BOOKING', 'ROOM_UNAVAILABLE'"로 거부 사유용처럼 보이지만, `action`/`initiated_by`/`result_status`와 달리 `CHECK` 제약이 없는 자유 텍스트 컬럼이라 값의 의미를 강제하지 않는다. **`reject_reason`에 `CancelRequestReason.name`을 담아 재사용**한다 — 스키마를 건드리지 않고, 기획문서 4.3("오버부킹 정리 목적의 호스트 취소라면... 사유 코드를 OTA 표준 사유 체계에 맞춰 전달")이 요구하는 "사유가 하류(OTA)까지 흘러가야 한다"는 요구를 만족시키는 가장 낮은 리스크의 방법이다. 이 재사용은 `SUCCESS` 결과에도 값이 채워진다는 점에서 컬럼명과 다소 어긋나므로, PR 설명에 명시적으로 남긴다.

### 3. 처리 흐름 (`ReservationService.cancelRequest`, 기존 클래스에 이어 붙임)

CANCEL_REQUEST는 **새 row를 insert하는 게 아니라 기존 row의 상태만 바꾸는 UPDATE**라서 BOOK류의 "성공 시도 / 충돌 기록" 트랜잭션 분리가 필요 없다. 다만 동시 상태 변경(예: 같은 예약에 대해 호스트 재요청과 OTA 취소통보가 겹치는 경우)에 대비해 #15에서 확립한 **낙관적 락 재시도 루프**(트랜잭션 블록 밖에서 `ObjectOptimisticLockingFailureException`을 잡고, 매 시도마다 최신 상태를 다시 읽어 새 트랜잭션으로 재시도)를 그대로 재사용한다.

```
1. requestKey = buildCancelRequestKey(reservationId, now)   // 호스트는 OTA의 external_request_id가 없으므로 항상
                                                              // reservation_no + ':CANCEL_REQUEST:' + 초단위 타임스탬프 형식
2. reservationRequestRepository.findByRequestKey(requestKey) 존재하면 → 그 결과 그대로 반환 (같은 초 안의 정확한 재시도 방어)
3. 최대 N회 재시도 루프:
   transactionTemplate.execute {
     reservation = reservationRepository.findById(command.reservationId).orElse(null)
     if (reservation == null) {
       request = ReservationRequest(reservationId=null, action=CANCEL_REQUEST, initiatedBy=HOST,
                                     resultStatus=FAILED, rejectReason="RESERVATION_NOT_FOUND", ...)
       return reservationRequestRepository.saveAndFlush(request.toEntity()).toDomain()   // 알림 없음 (NOT NULL FK, #14/#15와 동일 이유)
     }
     when (reservation.status) {
       CONFIRMED -> {
         reservation.status = PENDING_CANCEL
         savedReservation = reservationRepository.saveAndFlush(reservation)   // 낙관적 락 충돌 시 예외
         request = ReservationRequest(reservationId=savedReservation.id, action=CANCEL_REQUEST, initiatedBy=HOST,
                                       resultStatus=SUCCESS, rejectReason=command.reason.name, ...)
         savedRequest = reservationRequestRepository.saveAndFlush(request.toEntity())
         outboundNotificationRepository.saveAndFlush(CANCEL_REQUESTED 알림)   // 같은 트랜잭션
         return savedRequest.toDomain()
       }
       PENDING_CANCEL -> {
         // 상태 기반 멱등성: 원하는 목표 상태(취소 요청됨)에 이미 도달 — 재전이/재알림 없이 감사 기록만 추가
         request = ReservationRequest(reservationId=reservation.id, action=CANCEL_REQUEST, initiatedBy=HOST,
                                       resultStatus=SUCCESS, rejectReason=command.reason.name, ...)
         return reservationRequestRepository.saveAndFlush(request.toEntity()).toDomain()
       }
       CANCELLED -> {
         // 이미 최종 취소된 건에 대한 취소요청은 의미가 없다 — 실패로 기록, 알림 없음
         request = ReservationRequest(reservationId=reservation.id, action=CANCEL_REQUEST, initiatedBy=HOST,
                                       resultStatus=FAILED, rejectReason="ALREADY_CANCELLED", ...)
         return reservationRequestRepository.saveAndFlush(request.toEntity()).toDomain()
       }
     }
   }
   ↑ ObjectOptimisticLockingFailureException을 블록 밖에서 잡아 재시도 (#15와 동일 패턴). N회 실패 시 예외 전파.
```

- `CONFIRMED`만 실제 전이 대상이고, 그 외 두 상태는 전이 없이 결과만 기록한다 — 이슈의 "CONFIRMED 상태에서만 PENDING_CANCEL로 전이 가능하도록 상태 가드"를 그대로 구현.
- **exclusion 제약 안전성**: `CONFIRMED → PENDING_CANCEL` UPDATE는 `room_code`/`date_range`를 바꾸지 않고, 전이 전후 상태 모두 `excl_room_date_overlap`의 `WHERE status IN ('CONFIRMED','PENDING_CANCEL')` 대상에 이미 포함돼 있었다 — 즉 이 row가 차지하던 배타적 구간은 전이 전후로 동일하다. 새로운 겹침을 만들지 않으므로 이 UPDATE로 exclusion 제약 위반이 발생할 수 없다 (다른 row와의 관계는 전혀 바뀌지 않음).

### 4. `outbound_notifications`

`CONFIRMED → PENDING_CANCEL`로 실제 전이한 경우에만 발행한다 (PENDING_CANCEL/CANCELLED 재요청, 예약 없음 케이스는 발행하지 않음 — #14/#15와 동일한 원칙: 상태 변경이 실제로 일어난 경우에만 하류에 통보).

- `notificationKey = "${reservation.reservationNo}:CANCEL_REQUESTED"` — 이 전이는 예약 생애주기에서 최대 한 번만 성공하므로(성공 이후엔 PENDING_CANCEL 분기가 알림을 만들지 않음) 타임스탬프 없이도 유일성이 보장된다.
- payload: `ReservationCancelRequestedPayload(reservationNo, platformId, roomCode, startDate, endDate, reason)` — `reason`을 포함해 운영 서버가 OTA 표준 사유 코드로 매핑할 수 있게 한다 (기획문서 4.3, 매핑 자체는 운영 서버 쪽 후속 티켓 범위).

## Testing Plan

`ReservationServiceTest.kt`에 `feature("CANCEL_REQUEST 처리")` 블록을 추가한다 (같은 `ReservationService` 빈, #15와 동일한 확장 방식). `buildCancelRequestKey`는 대칭되는 순수 단위 테스트 파일로 분리한다.

- **`buildCancelRequestKey` 단위 테스트** (Spring 컨텍스트 불필요): `reservationNo:CANCEL_REQUEST:초단위타임스탬프` 포맷 검증.
- **CONFIRMED → PENDING_CANCEL**: `reservationService.book(...)`으로 CONFIRMED 예약을 만든 뒤 `cancelRequest(reservationId, OVERBOOKING_CLEANUP)` 호출 → `reservations.status = PENDING_CANCEL` 확인, `reservation_requests`에 `CANCEL_REQUEST`/`HOST`/`SUCCESS`/`rejectReason="OVERBOOKING_CLEANUP"` 1건, `outbound_notifications`에 `CANCEL_REQUESTED`/`PENDING` 정확히 1건 검증.
- **PENDING_CANCEL 상태에서 신규 겹침 요청 거부 유지**: 위에서 PENDING_CANCEL로 만든 예약과 같은 `room_code`·겹치는 날짜로 `reservationService.book(...)`을 호출 → 여전히 `CONFLICT`로 거부되는지 검증 (재고 점유 유지 확인 — GIST exclusion이 PENDING_CANCEL도 막는다는 것을 BOOK 경로로 교차 검증).
- **이미 PENDING_CANCEL인 예약에 재요청**: 위 결과에 대해 `cancelRequest(...)`를 한 번 더 호출 → 예외 없이 `SUCCESS` 반환(멱등), `reservations.status`는 그대로 `PENDING_CANCEL`(추가 UPDATE 없음, `version` 안 올라감), `outbound_notifications` row 수는 늘지 않음, `reservation_requests`에는 새 감사 기록 1건만 추가됨을 검증.
- **이미 CANCELLED인 예약에 요청**: (CANCEL_CONFIRM이 아직 없으므로 리포지토리로 직접 `status=CANCELLED` 픽스처 생성 — #15 선행 불필요, plan/15.md와 동일한 방식) `cancelRequest(...)` 호출 → `resultStatus=FAILED`, `rejectReason="ALREADY_CANCELLED"`, `outbound_notifications` 생성 안 됨 검증.
- **존재하지 않는 예약**: 존재하지 않는 `reservationId`로 호출 → `resultStatus=FAILED`, `rejectReason="RESERVATION_NOT_FOUND"`, 알림 없음 검증.
- **낙관적 락 충돌 재시도**: `ReservationRepositoryTest`/#15와 같은 방식으로 네이티브 쿼리로 `version`을 미리 올려 첫 시도가 `ObjectOptimisticLockingFailureException`을 맞게 만든 뒤, 재시도 루프가 결국 `PENDING_CANCEL` 전이에 성공하는지 검증.
- CI/로컬 실행 전제: Docker 데몬 필요(Testcontainers) — #13~#15와 동일.

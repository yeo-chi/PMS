# #1 [Setup] Gradle 멀티모듈 구조 생성 (reservation, operation)

> **Revision 2** — supersedes the previous version of this plan. Two architecture decisions changed after
> review, while the ticket is already being implemented:
> 1. **Package structure unified** across both modules to exactly 5 packages: `controller`, `service`,
>    `domain`, `persistent`, `configuration`. (`repository` → `persistent`; operation's `config` + `api` →
>    merged into `configuration`; operation's `client` → absorbed into `service`; reservation's `dto`
>    package removed.)
> 2. **Both `reservation` and `operation` are now independently runnable Spring Boot applications**, each
>    with its own `org.springframework.boot` plugin, its own `@SpringBootApplication` entry point
>    (`ReservationApplication.kt` / `OperationApplication.kt`), and its own `application.yaml` with a
>    non-conflicting `server.port`. The root `pms` project is no longer a runnable app — it becomes a pure
>    Gradle parent/aggregator project (plugin-version registry + shared `group`/`version`/`repositories`
>    only). The existing root `PmsApplication.kt` and `PmsApplicationTests.kt` are **removed**.
>
> Everything below reflects the current, up-to-date decision. Do not implement anything from Revision 1
> (thin root app module, library-only submodules, manual `mavenBom` import, `dto`/`repository`/`api`/`client`
> packages) — it is obsolete.

> **Post-implementation note (issue #12)**: after this ticket (and #3) shipped, issue #12 ("reservation-
> operation 통신을 인프로세스 호출에서 실제 HTTP 통신으로 전환") removed the `reservation → operation` Gradle
> compile dependency (`implementation(project(":operation"))`) entirely and replaced it with real HTTP calls
> (`operation` exposes `POST /api/platform-syncs` via a new `controller` package; `reservation` calls it with
> a Spring `RestClient`). As a result, several statements below that describe `reservation` as Gradle-
> depending on `operation`, embedding `operation`'s beans/entities in-process via `@ComponentScan`/
> `@EntityScan`, or relying on Kotlin `internal` visibility to enforce a compile-time module boundary are
> **no longer accurate** — they described the pre-#12 design. See `plan/12.md` for the current, correct
> architecture. The specific stale passages are flagged inline below rather than rewritten in place, to
> preserve this document's value as a historical record of the #1 scaffolding decision.

> **Note on the source issue body** (unchanged from Revision 1): `gh issue view 1`'s body talks about a
> `Reservation` JPA entity/enum/repository, which does not match this issue's title. Cross-checking the rest
> of the backlog (`gh issue view 2..6`) shows every issue's body actually matches the *next* issue's title
> (issue #1's body == issue #2's title, issue #2's body == issue #3's title, etc.) — this is a copy/paste
> offset error in the tracker, not a real requirement for this ticket. This plan treats the **issue title**
> as the authoritative scope ("Setup: create a Gradle multi-module structure with `reservation` and
> `operation` modules") and leaves all actual domain/entity/repository/service/controller *content* to the
> dedicated tickets where it already exists correctly (#2 domain/persistence, #3 service, #4 controller, #5
> operation domain/persistence, #6 operation sync/retry logic). **This ticket only scaffolds the two
> modules and their entry points** — package skeletons, build config, and boot wiring. No real business
> logic is added here.

## Requirements

- Two Gradle subprojects, `reservation` and `operation`, each independently buildable **and independently
  runnable** as its own Spring Boot application (own `main()`, own embedded server port, own H2 instance).
- Both modules use the identical 5-package internal layout: `controller`, `service`, `domain`,
  `persistent`, `configuration`. No `dto`, `repository`, `client`, `api`, or `config` packages.
- `reservation` depends on `operation` (Gradle `project(":operation")`, `implementation` scope) because
  reservation delegates platform sync to operation (per issue #2's technical approach: "모듈 간 의존은 운영
  모듈의 공개 API를 통해서만"). `operation` must **not** depend on `reservation` — no circular dependency.
  **[Superseded by issue #12]** — this Gradle compile dependency was removed entirely; `reservation` and
  `operation` now communicate exclusively over HTTP (`reservation`'s `RestPlatformSyncClient` calls
  `operation`'s `POST /api/platform-syncs`), so there is no compile-time dependency in either direction.
- Because `reservation`'s Spring context also loads `operation`'s beans/entities/repositories in-process
  (it embeds `operation` as a library, on top of `operation` also being separately runnable), reservation's
  `@SpringBootApplication` class must explicitly `@ComponentScan` / `@EntityScan` /
  `@EnableJpaRepositories` across both `yeo.chi.proejct.pms.reservation` and `yeo.chi.proejct.pms.operation`
  base packages — they are sibling packages, not a parent/child pair, so Spring Boot's default
  same-package-and-below scanning is not enough.
  **[Superseded by issue #12]** — `ReservationApplication` no longer scans any `operation` package at all;
  it is a bare `@SpringBootApplication` relying on default same-package-and-below scanning, since
  `reservation` no longer embeds `operation`'s beans/entities in-process.
- Root `pms` project stops being an application: no `@SpringBootApplication` class, no `application.yaml`,
  no `bootJar`/`bootRun` task, no test sources at the root. It only hosts `settings.gradle.kts` and a thin
  root `build.gradle.kts` (shared plugin versions + `group`/`version`/`repositories` for both children).
- Preserve existing toolchain/version choices: Kotlin `2.0.21`, Spring Boot `3.5.14`,
  `io.spring.dependency-management` `1.1.7`, Java 21 toolchain, H2, Kotest/MockK test stack.
- `reservation` and `operation` must be able to run **at the same time** on the same machine without port
  collisions (distinct `server.port` per module).
- No real domain code (entities, repositories, services, controllers) is added in this ticket — only build
  configuration, entry-point classes, package scaffolding, `application.yaml` files, and lightweight
  smoke/context-load tests proving both apps boot correctly.

### 3. Root `build.gradle.kts` (pure parent project — no source, no app)

Declares every plugin version exactly once (`apply false`) so both child modules can request the same
plugin `id` without repeating the version string, and centralizes `group`/`version`/`repositories` via
`allprojects`. This is the standard Gradle multi-module pattern for keeping plugin versions in sync across
sibling subprojects.

```kotlin
plugins {
    kotlin("jvm") version "2.0.21" apply false
    kotlin("plugin.spring") version "2.0.21" apply false
    kotlin("plugin.jpa") version "2.0.21" apply false
    id("org.springframework.boot") version "3.5.14" apply false
    id("io.spring.dependency-management") version "1.1.7" apply false
}

allprojects {
    group = "yeo.chi.proejct"
    version = "0.0.1-SNAPSHOT"

    repositories {
        mavenCentral()
    }
}
```

No `src/` directory remains at the repo root after this ticket. Delete:
- `src/main/kotlin/yeo/chi/proejct/pms/PmsApplication.kt`
- `src/main/resources/application.yaml`
- `src/test/kotlin/yeo/chi/proejct/pms/PmsApplicationTests.kt`
- the now-empty `src/` directory tree.

### 6. Entry points

`reservation/src/main/kotlin/yeo/chi/proejct/pms/reservation/ReservationApplication.kt` — must explicitly
scan/entity-scan/repository-scan the sibling `operation` package, since it is not a sub-package of
`reservation`:

```kotlin
package yeo.chi.proejct.pms.reservation

import org.springframework.boot.autoconfigure.SpringBootApplication
import org.springframework.boot.autoconfigure.domain.EntityScan
import org.springframework.boot.runApplication
import org.springframework.context.annotation.ComponentScan
import org.springframework.data.jpa.repository.config.EnableJpaRepositories

@SpringBootApplication
@ComponentScan(
    basePackages = [
        "yeo.chi.proejct.pms.reservation",
        "yeo.chi.proejct.pms.operation",
    ],
)
@EntityScan(
    basePackages = [
        "yeo.chi.proejct.pms.reservation.domain",
        "yeo.chi.proejct.pms.operation.domain",
    ],
)
@EnableJpaRepositories(
    basePackages = [
        "yeo.chi.proejct.pms.reservation.persistent",
        "yeo.chi.proejct.pms.operation.persistent",
    ],
)
class ReservationApplication

fun main(args: Array<String>) {
    runApplication<ReservationApplication>(*args)
}
```

`operation/src/main/kotlin/yeo/chi/proejct/pms/operation/OperationApplication.kt` — operation has no
dependency on reservation, so the default same-package-and-below scanning is sufficient, no explicit

```yaml

    name: reservation
```

`operation/src/main/resources/application.yaml`:


(`./gradlew :operation:bootRun` and `./gradlew :reservation:bootRun` in two terminals) without a port

### 8. Unified 5-package convention

Both modules use exactly these packages under their own base package
(`yeo.chi.proejct.pms.reservation.*` / `yeo.chi.proejct.pms.operation.*`):

| Package | reservation | operation |
|---|---|---|
| `controller` | `ReservationController` (#4) | future ops-facing endpoints |
| `service` | `ReservationService` (#3) | `PlatformSyncClient` impls, registry/factory, retry logic (#6) — absorbs the old "client" role |
| `domain` | `Reservation` entity, status enum (#2) | `Platform`, `RoomPlatformMapping` entities (#5) |
| `persistent` | `ReservationRepository` (#2) | `PlatformRepository`, `RoomPlatformMappingRepository` (#5) |
| `configuration` | reservation-local `@Configuration` classes | `@Configuration` beans **and** the public sync API/facade interface (e.g. a future `PlatformSyncFacade`) that `reservation` is allowed to depend on — absorbs the old "config" + "api" roles |

No `dto` package: request/response shaping for #4's controller should live alongside the controller (e.g.
as nested/top-level classes in the `controller` package) rather than a separate `dto` package.

Module-boundary convention carried over from Revision 1 (still applies, nothing to implement yet): mark
`operation`'s concrete implementation classes inside `service`/`domain`/`persistent` as Kotlin `internal` so
they're invisible to `reservation` at compile time; only the interfaces/facades placed in
`operation`'s `configuration` package should be `public`. `@ComponentScan`/`@EntityScan`/
`@EnableJpaRepositories` use string package names, so this Kotlin-level `internal` restriction does not
interfere with Spring/Hibernate wiring reservation performs into operation's beans/entities.

**[Superseded by issue #12]** — the rationale above (`internal` visibility enforcing a compile-time module
boundary against `reservation`) no longer applies, because issue #12 removed the `reservation → operation`
Gradle compile dependency entirely. `operation.service.LoggingPlatformSyncFacade` is still `internal class`
in the code (unchanged, harmless), but this is now vestigial rather than load-bearing: `reservation` cannot
reach any `operation` class at compile time regardless of visibility modifiers, since the two modules
communicate only via HTTP (`operation`'s new `controller.PlatformSyncController` REST endpoint, called by
`reservation`'s `service.RestPlatformSyncClient`). See `plan/12.md` for the current design.

### 11. Edge cases / things to watch for

- **Circular dependency**: never add `implementation(project(":reservation"))` to `operation`'s
  `build.gradle.kts`. **[Superseded by issue #12]** — as of #12, `reservation` no longer depends on
  `operation` either (the former `implementation(project(":operation"))` in `reservation/build.gradle.kts`
  was removed), so there is no Gradle project dependency between the two modules in either direction; they
  are fully independent, separately deployable Spring Boot applications communicating only over HTTP.
- **`project(":operation")` dependency vs. `operation` applying the Boot plugin**: this is safe with the
  Spring Boot Gradle plugin used here (3.5.14). The plugin does *not* disable the plain `jar` task — it
  keeps `jar` enabled with an automatic `-plain` classifier alongside the separate executable `bootJar`
  (already observable in this repo's own `build/libs/pms-0.0.1-SNAPSHOT-plain.jar` +
  `pms-0.0.1-SNAPSHOT.jar` output from the current single-module build). `reservation`'s
  `project(":operation")` dependency resolves against operation's plain classes jar (via the standard
  `apiElements`/`runtimeElements` outgoing variant), while `./gradlew :operation:bootJar` still produces a
  separately runnable fat jar. No extra Gradle configuration is required to make both work together.
- **`resolveMainClassName` ambiguity**: each module's `bootJar`/`bootRun` only scans that module's own
  compiled output for a class with `main()`, not its dependencies' compiled output, so `reservation`
  will not mistakenly try to boot `OperationApplication` (and vice versa) even though `operation`'s classes
  are on `reservation`'s classpath.
- **Version drift**: Kotlin/Spring Boot/dependency-management versions are declared exactly once, in root
  `build.gradle.kts` (`apply false`), and referenced by `id`/`kotlin(...)` without a version string in both
  child modules — keep these plugin `id`s in sync if a version ever needs bumping (bump only the root file).
- **H2 scope**: both modules need `runtimeOnly("com.h2database:h2")` now (each is independently runnable
  with its own datasource), not `testRuntimeOnly` as in Revision 1.
- **Port collision**: `reservation` = `8081`, `operation` = `8082`. Keep these distinct if either changes.
- **Component/Entity scanning**: only `reservation` needs the explicit `@ComponentScan`/`@EntityScan`/
  `@EnableJpaRepositories` cross-package annotations (§6), because only `reservation` depends on
  `operation`. Do not add the reverse in `OperationApplication.kt`. **[Superseded by issue #12]** — since
  #12 removed the `reservation → operation` Gradle dependency, `ReservationApplication` no longer carries
  any cross-package `@ComponentScan`/`@EntityScan`/`@EnableJpaRepositories` at all; it is a bare
  `@SpringBootApplication` like `OperationApplication` always was.
- **Stale build output**: run `./gradlew clean` once after restructuring so old flat-layout compiled
  classes under root `build/` don't linger.

## Testing Plan

1. `./gradlew clean build` — full multi-module build succeeds (root has no compiled sources of its own;
   `reservation` and `operation` each compile and package independently).
2. `./gradlew projects` — confirms `:reservation` and `:operation` are registered as subprojects of the
   root `pms` project, and that root itself has no application code.
3. `./gradlew :reservation:dependencies --configuration compileClasspath` — output includes
   `project :operation`, confirming the intended one-way dependency.
4. `./gradlew :operation:dependencies --configuration compileClasspath` — output does **not** include
   `project :reservation`, confirming no circular dependency.
5. `./gradlew :reservation:test` — `ReservationApplicationTests.contextLoads()` passes, proving
   reservation's Spring context loads successfully with `operation`'s component-scanned beans and
   entity/repository-scanned classes merged in via the explicit `basePackages`.
6. `./gradlew :operation:test` — `OperationApplicationTests.contextLoads()` passes, proving operation's
   Spring context loads independently on its own.
7. `./gradlew test` — the Kotest `ReservationModuleSmokeTest` / `OperationModuleSmokeTest` pass, confirming
   JUnit5 + Kotest + MockK are correctly wired in each module's test source set.
8. `./gradlew :reservation:bootJar` and `./gradlew :operation:bootJar` both succeed and produce two
   separate executable fat jars; confirm the root project has no `bootJar`/`bootRun` task at all
   (`./gradlew tasks --all` at root should not list them for the root project).
9. Manual smoke check: run `./gradlew :operation:bootRun` and, in a second terminal,
   `./gradlew :reservation:bootRun` — both start successfully at the same time on ports `8082` and `8081`
   respectively with no port conflict, confirming true independent runnability.

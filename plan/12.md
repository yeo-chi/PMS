# #12 [Fix] reservation-operation 통신을 인프로세스 호출에서 실제 HTTP 통신으로 전환

> **전제 조건 (반드시 먼저 확인)**: 이 계획을 작성하는 시점(`main` = `070f3b9`, PR #10까지 반영)에는 이슈 #3
> ("[예약] 서비스 로직 작성")이 아직 `main`에 머지되지 않았다. `git show main:reservation/src/main/kotlin/yeo/chi
> /proejct/pms/reservation/service/ReservationService.kt`는 `fatal: path ... does not exist in 'main'`으로
> 확인된다 — `main`에는 `reservation/service`, `reservation/configuration`, `operation/controller` 패키지 자체가
> 아직 비어 있고, `operation/configuration/PlatformSyncFacade.kt` / `operation/service/
> LoggingPlatformSyncFacade.kt`도 없다. 해당 코드는 로컬 브랜치 `feature/3-reservation-service`(커밋
> `71c4d32`)에만 존재한다.
>
> 이 문서는 **이슈 #3이 머지되어 아래 baseline이 `main`에 존재하는 상태**를 전제로 작성한다:
> - `reservation/src/main/kotlin/.../reservation/service/ReservationService.kt` — `ReservationRepository` +
>   `PlatformSyncFacade`(operation의 것)를 생성자 주입받아 `createReservation()`을 구현.
> - `operation/src/main/kotlin/.../operation/configuration/PlatformSyncFacade.kt` — 인터페이스 +
>   `ReservationSyncRequest` data class.
> - `operation/src/main/kotlin/.../operation/service/LoggingPlatformSyncFacade.kt` — `internal class`
>   no-op 구현체, `@Service`.
> - `ReservationApplication.kt`의 `@ComponentScan`이 `operation.controller/service/persistent/
>   configuration`을 leaf 패키지로 나열하고, `@EntityScan`이 `operation.domain`을 포함.
> - `reservation/build.gradle.kts`가 `implementation(project(":operation"))`을 가짐.
>
> developer 서브에이전트는 **이슈 #3 브랜치가 먼저 머지된 뒤** 이 계획을 적용해야 한다. 만약 구현 시점에
> 아직 #3이 머지되지 않았다면, `feature/3-reservation-service`의 최종 코드(위 baseline)를 그대로 가져와
> 병합한 뒤 아래 변경을 적용한다. 아래 "Technical Approach"의 모든 diff/전체 코드는 이 baseline을 기준으로
> 작성되었다.

## Requirements

이슈 #12 원문 요구사항 (`gh issue view 12`):

- `reservation`과 `operation`을 Gradle 컴파일 의존 관계 없이 완전히 독립시킨다
  (`implementation(project(":operation"))` 제거).
- `operation`에 실제 REST 엔드포인트(`controller` 패키지)를 추가해 예약 동기화 요청을 HTTP로 받는다.
- `reservation`은 자체 DTO를 정의하고, HTTP 클라이언트(Spring `RestClient`)로 `operation` 서버에 실제 네트워크
  호출을 한다 (요청/응답 DTO는 각자 독립적으로 정의 — 공유하지 않음).
- `ReservationApplication`의 `operation` 패키지 대상 `@ComponentScan`/`@EntityScan`을 제거한다.
- `CLAUDE.md`/`plan/1.md`의 "reservation→operation Gradle 의존, internal 가시성으로 모듈 경계 강제" 컨벤션을
  "HTTP 통신으로 분리, Gradle 의존 없음"으로 갱신할 필요가 있다는 점을 인지한다 (실제 문서 수정은 이 planner
  작업 범위 밖이며, developer가 구현 PR에서 반영해야 할 후속 작업).

이 계획에서 구체화한 세부 요구사항 (사용자가 이미 확정한 설계 결정을 그대로 반영, 재설계하지 않음):

1. `reservation/build.gradle.kts`에서 `implementation(project(":operation"))`을 제거한다. `settings.gradle.kts`,
   `operation/build.gradle.kts`는 변경하지 않는다 (원래도 `operation`→`reservation` 방향 의존이 없었으므로
   단방향 의존 제거는 `reservation` 쪽 파일만 건드리면 된다).
2. `operation`의 `controller` 패키지에 `PlatformSyncController`(REST 엔드포인트)를 신규 추가한다. 기존
   `PlatformSyncFacade`/`LoggingPlatformSyncFacade`는 그대로 두고, 새 컨트롤러가 이 facade를 호출한다.
3. `reservation`은 `operation`의 `ReservationSyncRequest`를 공유하지 않고, 자체 요청 DTO
   (`PlatformSyncRequest`, reservation 소유)를 새로 정의한다.
4. `reservation` 모듈 내에 `PlatformSyncClient` 인터페이스를 신규 정의하고, `ReservationService`가
   (operation의 `PlatformSyncFacade`가 아니라) 이 인터페이스에 의존하도록 교체한다. 실제 HTTP 호출은
   `RestPlatformSyncClient`(`RestClient` 기반 구현체)가 담당한다.
5. `ReservationApplication.kt`에서 `operation` 패키지를 대상으로 하는 `@ComponentScan`/`@EntityScan`을 전부
   제거한다.
6. `operation` 서버 base url을 `reservation`의 `application.yaml`에 설정값(`operation.base-url`, 기본값
   `http://localhost:8082`)으로 두고, `@ConfigurationProperties`로 타입 세이프하게 주입한다.
7. `CLAUDE.md`/`plan/1.md`의 관련 서술 갱신은 이번 planner 작업 범위가 아니며, developer가 구현 PR에서
   반영해야 할 후속 작업임을 명시한다 (아래 "후속 작업" 절 참고).

### 1. `operation/build.gradle.kts` / `settings.gradle.kts` 변경 불필요 근거

`git diff main feature/3-reservation-service -- reservation/build.gradle.kts operation/build.gradle.kts`가
빈 결과를 반환한다 — 즉 이슈 #3도 두 build 파일을 건드리지 않았고, 현재 `operation/build.gradle.kts`에는
애초에 `implementation(project(":reservation"))` 같은 역방향 의존이 존재한 적이 없다. 이번 티켓은 단방향으로
`reservation → operation` 의존만 끊는 작업이므로, `operation` 쪽 Gradle 설정과 `settings.gradle.kts`
(`include("reservation")` / `include("operation")`만 있음, 프로젝트 간 의존 선언은 각 모듈의
`build.gradle.kts`에만 존재)는 그대로 둔다.

### 3. `operation`의 새 REST 엔드포인트 — `controller/PlatformSyncController.kt` (신규)

`operation/src/main/kotlin/yeo/chi/proejct/pms/operation/controller/PlatformSyncController.kt`:

```kotlin
package yeo.chi.proejct.pms.operation.controller

import org.springframework.http.HttpStatus
import org.springframework.http.ResponseEntity
import org.springframework.web.bind.annotation.PostMapping
import org.springframework.web.bind.annotation.RequestBody
import org.springframework.web.bind.annotation.RequestMapping
import org.springframework.web.bind.annotation.RestController
import yeo.chi.proejct.pms.operation.configuration.PlatformSyncFacade
import yeo.chi.proejct.pms.operation.configuration.ReservationSyncRequest
import java.time.LocalDate
import java.time.LocalDateTime

/**
 * reservation 모듈이 예약 생성 사실을 HTTP로 전달하는 진입점.
 *
 * reservation과 operation은 이제 Gradle 컴파일 의존이 없는 별도 프로세스이므로, 이 컨트롤러가 받는
 * [PlatformSyncHttpRequest]는 operation.configuration.ReservationSyncRequest와 필드 구성이 동일하지만
 * 완전히 별개의 타입이다 (reservation 쪽의 PlatformSyncRequest와도 공유하지 않는다 - 이슈 #12 요구사항).
 * 이 컨트롤러는 HTTP 요청 바디를 받아 기존 [PlatformSyncFacade]로 그대로 위임한다 - 실제 동기화 로직
 * (외부 플랫폼 연동, 재시도)은 여전히 #6 범위이며 이번 티켓에서 변경하지 않는다.
 */
@RestController
@RequestMapping("/api/platform-syncs")
class PlatformSyncController(
    private val platformSyncFacade: PlatformSyncFacade,
) {

    @PostMapping
    fun syncReservationCreated(
        @RequestBody request: PlatformSyncHttpRequest,
    ): ResponseEntity<Void> {
        platformSyncFacade.syncReservationCreated(request.toFacadeRequest())
        return ResponseEntity.status(HttpStatus.ACCEPTED).build()
    }
}

data class PlatformSyncHttpRequest(
    val platformCode: String,
    val roomId: Long,
    val reservationCode: String,
    val userIdentifyCode: String,
    val startDate: LocalDate,
    val endDate: LocalDate,
    val reservedAt: LocalDateTime,
    val status: String,
) {
    fun toFacadeRequest(): ReservationSyncRequest = ReservationSyncRequest(
        platformCode = platformCode,
        roomId = roomId,
        reservationCode = reservationCode,
        userIdentifyCode = userIdentifyCode,
        startDate = startDate,
        endDate = endDate,
        reservedAt = reservedAt,
        status = status,
    )
}
```

**HTTP 스펙**: `POST /api/platform-syncs`, `Content-Type: application/json`, 성공 시 `202 Accepted` (본문
없음 - 비동기적으로 "요청을 받아들였다"는 의미가 `syncReservationCreated`라는 이름의 이벤트 성격과 맞고,
현재 `LoggingPlatformSyncFacade`는 실제로 즉시 처리를 끝내지만 향후 #6에서 실제 처리가 비동기/큐잉으로 바뀔
가능성을 열어둔다).

**설계 노트 - Bean Validation을 붙이지 않은 이유**: `.claude/skills/kotlin-springboot/SKILL.md`는 DTO에
JSR-380(`@NotNull`, `@Valid` 등) 검증을 권장하지만, `jakarta.validation.constraints.*` 어노테이션과 실제
검증기(Hibernate Validator)를 쓰려면 `spring-boot-starter-validation` 의존성이 필요하다. `operation/
build.gradle.kts`는 이번 티켓 범위에서 변경 불필요하다고 이미 확정되어 있으므로, 이번 컨트롤러에는 Bean
Validation을 추가하지 않는다. 요청 검증이 필요해지면 `spring-boot-starter-validation`을 `operation`에 추가하는
별도 후속 작업으로 처리한다 (이번 티켓 범위 아님 - 이슈 본문에도 검증 요구사항 없음).

### 4. `reservation`의 새 클라이언트 추상화 — `service/PlatformSyncClient.kt` (신규)

`reservation/src/main/kotlin/yeo/chi/proejct/pms/reservation/service/PlatformSyncClient.kt`:

```kotlin
package yeo.chi.proejct.pms.reservation.service

import java.time.LocalDate
import java.time.LocalDateTime

/**
 * reservation이 operation 서버에 예약 동기화를 위임할 때 사용하는 내부 추상화.
 *
 * reservation과 operation은 더 이상 Gradle 컴파일 의존이 없으므로(이슈 #12), 이 인터페이스는 operation의
 * PlatformSyncFacade와 이름/역할이 유사해 보이지만 완전히 별개의, reservation 모듈 소유 타입이다. 실제 구현체
 * [RestPlatformSyncClient]는 HTTP로 operation 서버를 호출한다. ReservationService는 이 인터페이스에만
 * 의존하므로, 서비스 단위 테스트에서는 이 인터페이스를 MockK로 mock할 수 있다.
 */
interface PlatformSyncClient {

    fun syncReservationCreated(request: PlatformSyncRequest)
}

data class PlatformSyncRequest(
    val platformCode: String,
    val roomId: Long,
    val reservationCode: String,
    val userIdentifyCode: String,
    val startDate: LocalDate,
    val endDate: LocalDate,
    val reservedAt: LocalDateTime,
    val status: String,
)
```

**패키지 배치 근거**: `CLAUDE.md`는 `dto` 패키지를 금지하므로 이 DTO는 어딘가의 기존 5개 패키지에 속해야
한다. `plan/1.md` §8은 원래 (구 설계 기준) operation의 `service` 패키지를 "`PlatformSyncClient` impls,
registry/factory, retry logic"의 자리로 지정해 두었다 — 이번 티켓의 `PlatformSyncClient`는 그 이름을
그대로 재사용하지만 **reservation 모듈 소유의 아웃바운드 클라이언트**라는 점에서 역할이 다르다(패키지가
`yeo.chi.proejct.pms.reservation.service`로 서로 다르므로 컴파일 충돌은 없다). `operation`이
`operation.configuration`에 "공개 API"를 두었던 것과 달리, `reservation`의 `PlatformSyncClient`는 이제
`reservation` 모듈 밖에서 참조하는 타입이 아니므로(Gradle 의존 자체가 없어짐) "공개 API"의 의미가 없다 —
`ReservationService`(비즈니스 로직)가 협력하는 내부 컬래보레이터이므로, 같은 이유로 `ReservationRepository`가
`persistent`에 있는 것처럼 `service` 패키지에 두는 것이 자연스럽다.

### 5. `reservation`의 HTTP 구현체 — `service/RestPlatformSyncClient.kt` (신규)

`reservation/src/main/kotlin/yeo/chi/proejct/pms/reservation/service/RestPlatformSyncClient.kt`:

```kotlin
package yeo.chi.proejct.pms.reservation.service

import org.slf4j.LoggerFactory
import org.springframework.http.MediaType
import org.springframework.stereotype.Component
import org.springframework.web.client.RestClient

@Component
class RestPlatformSyncClient(
    private val operationRestClient: RestClient,
) : PlatformSyncClient {

    companion object {
        private val logger = LoggerFactory.getLogger(RestPlatformSyncClient::class.java)
        private const val PLATFORM_SYNC_PATH = "/api/platform-syncs"
    }

    override fun syncReservationCreated(request: PlatformSyncRequest) {
        logger.info(
            "Calling operation platform-sync API: platformCode={}, reservationCode={}",
            request.platformCode,
            request.reservationCode,
        )
        operationRestClient.post()
            .uri(PLATFORM_SYNC_PATH)
            .contentType(MediaType.APPLICATION_JSON)
            .body(request)
            .retrieve()
            .toBodilessEntity()
    }
}
```

`operationRestClient: RestClient`는 §6에서 등록하는 Bean을 그대로 주입받는다. `.retrieve().toBodilessEntity()`
호출은 응답 본문을 읽지 않되, 4xx/5xx 응답이면 `RestClientResponseException`(또는 하위 타입)을 던진다 —
이번 티켓에서는 이 예외를 별도로 잡지 않고 그대로 호출자(`ReservationService.createReservation`, `@Transactional`)
로 전파한다 (아래 "Edge cases" §9 참고, 재시도/서킷브레이커는 명시적으로 #6 범위).

### 8. `ReservationService.kt` 수정 (`PlatformSyncFacade` → `PlatformSyncClient`)

`reservation/src/main/kotlin/yeo/chi/proejct/pms/reservation/service/ReservationService.kt` 전체 코드
(baseline 대비 변경점: import에서 `yeo.chi.proejct.pms.operation.configuration.*` 두 줄 제거,
생성자 파라미터 타입/이름 `platformSyncFacade: PlatformSyncFacade` → `platformSyncClient: PlatformSyncClient`,
호출부 `platformSyncFacade.syncReservationCreated(...)` → `platformSyncClient.syncReservationCreated(...)`,
`toSyncRequest()`의 리턴 타입 `ReservationSyncRequest` → `PlatformSyncRequest`. 로직/흐름은 baseline과 동일):

```kotlin
package yeo.chi.proejct.pms.reservation.service

import org.slf4j.LoggerFactory
import org.springframework.stereotype.Service
import org.springframework.transaction.annotation.Transactional
import yeo.chi.proejct.pms.reservation.domain.Reservation
import yeo.chi.proejct.pms.reservation.persistent.ReservationRepository
import yeo.chi.proejct.pms.reservation.persistent.toDomain
import yeo.chi.proejct.pms.reservation.persistent.toEntity

@Service
class ReservationService(
    private val reservationRepository: ReservationRepository,
    private val platformSyncClient: PlatformSyncClient,
) {

    companion object {
        private val logger = LoggerFactory.getLogger(ReservationService::class.java)
    }

    @Transactional
    fun createReservation(reservation: Reservation): Reservation {
        val existing = reservationRepository.findByPlatformCodeAndCode(
            reservation.platformCode,
            reservation.code,
        )
        if (existing != null) {
            logger.info(
                "Reservation already exists for platformCode={}, code={} - skip duplicate save/sync",
                reservation.platformCode,
                reservation.code,
            )
            return existing.toDomain()
        }

        val saved = reservationRepository.save(reservation.toEntity()).toDomain()

        platformSyncClient.syncReservationCreated(saved.toSyncRequest())

        return saved
    }

    private fun Reservation.toSyncRequest(): PlatformSyncRequest = PlatformSyncRequest(
        platformCode = platformCode,
        roomId = roomId,
        reservationCode = code,
        userIdentifyCode = userIdentifyCode,
        startDate = startDate,
        endDate = endDate,
        reservedAt = reservedAt,
        status = status.name,
    )
}
```

`PlatformSyncClient`/`PlatformSyncRequest`는 `ReservationService`와 같은 패키지(`reservation.service`)에
있으므로 별도 import가 필요 없다.

### 9. Edge cases

- **HTTP 호출 실패 처리 범위**: 이슈 본문(#12)은 재시도/서킷브레이커를 전혀 언급하지 않는다 — "실제 HTTP
  통신으로 전환"이 핵심이며, 실패 시 재시도/멱등성 보장은 `plan/3.md`가 이미 명시한 대로 #6 범위다. 이번
  티켓에서는 `RestPlatformSyncClient`가 던지는 예외(`RestClientResponseException`,
  `ResourceAccessException` 등 연결 실패 포함)를 잡지 않고 그대로 `ReservationService.createReservation()`
  (`@Transactional`)까지 전파시킨다 — 즉 operation 호출이 실패하면 예약 저장 트랜잭션도 롤백된다. 이 동작
  자체는 #3에서 이미 확정된 "동기화 호출이 트랜잭션 내부에서 일어난다"는 설계를 그대로 유지하는 것이며(전송
  수단만 인프로세스→HTTP로 바뀜), 트랜잭션 경계를 커밋 이후로 옮기거나 재시도를 추가하는 것은 이번 티켓
  범위가 아니다(#6에서 재검토).
- **두 서버가 모두 떠 있어야 실제 동작**: `reservation`(8081)과 `operation`(8082)이 각각 별도 프로세스로
  기동되어 있어야 `ReservationService.createReservation()`이 끝까지 성공한다. `RestClient` Bean 생성
  자체(`RestClientConfiguration`)는 네트워크 연결을 미리 맺지 않으므로, `operation`이 꺼져 있어도
  `reservation` 프로세스 부팅이나 `@SpringBootTest` 컨텍스트 로딩은 실패하지 않는다 — 실패는 실제
  `createReservation()` 호출 시점(HTTP 요청 시점)에만 발생한다.
- **`ReservationApplicationTests`(`@SpringBootTest`) 회귀 여부**: `operation`의 Bean을 더 이상 스캔하지
  않으므로, `reservation` 컨텍스트가 필요로 하는 모든 Bean(`ReservationRepository`, `ReservationService`,
  `PlatformSyncClient` = `RestPlatformSyncClient`, `RestClient`, `OperationClientProperties`)이 전부
  `reservation` 자신의 컴포넌트 스캔 범위 안에서 해결되어야 한다 — §4~§8의 모든 신규 클래스가
  `yeo.chi.proejct.pms.reservation.*` 패키지에 있으므로 기본 스캔으로 충분하고, `operation`이 꺼져 있어도
  `RestClient`/`RestPlatformSyncClient` Bean 생성 자체는 성공하므로(위 항목 참고) `contextLoads()`는 여전히
  통과해야 한다. 만약 실패한다면 `RestClientConfiguration`/`OperationClientProperties` 배치나
  `@EnableConfigurationProperties` 등록이 누락된 것이므로 확인한다.
- **JSON 직렬화 date/time 포맷**: `PlatformSyncRequest`/`PlatformSyncHttpRequest`의 `startDate`/`endDate`
  (`LocalDate`), `reservedAt`(`LocalDateTime`)이 Jackson 기본 설정으로 ISO-8601 문자열로 직렬화/역직렬화되는지
  테스트(§10의 `RestPlatformSyncClientTest`, `PlatformSyncControllerTest`)에서 실제로 확인한다. Spring
  Boot의 Jackson 자동 설정은 클래스패스의 `jackson-datatype-jsr310`(`spring-boot-starter-web` →
  `spring-boot-starter-json`을 통해 양쪽 모듈 모두 전이 의존성으로 포함됨)을 자동 감지해 `JavaTimeModule`을
  등록하고 `WRITE_DATES_AS_TIMESTAMPS`를 기본적으로 비활성화하므로, 별도 설정 없이 ISO-8601 문자열로
  주고받아야 정상이다.
- **`internal` 가시성 컨벤션과의 관계**: `operation.service.LoggingPlatformSyncFacade`는 여전히
  `internal class`다 — 이는 원래 "`reservation`이 Gradle로 `operation`을 컴파일 의존할 때 구현 클래스를
  못 보게 막는다"는 목적이었는데, 이번 티켓으로 그 Gradle 의존 자체가 사라지므로 이 `internal` 표시는 이제
  실질적 효과가 없다(HTTP로만 통신하므로 애초에 컴파일 타임 접근이 불가능하다). 다만 `internal`을 `public`
  으로 되돌릴 필요도 없다 — `operation` 모듈 내부에서 `PlatformSyncController`가 인터페이스
  (`PlatformSyncFacade`)로만 주입받으므로 여전히 정상 동작하며, 굳이 가시성을 넓힐 이유가 없다. 이 컨벤션의
  "서술"(문서)만 갱신 대상이고 "코드"는 그대로 둔다 (§11 참고).
- **삭제되는 코드 없음**: `reservation`이 `operation.configuration.PlatformSyncFacade`/
  `ReservationSyncRequest`를 참조하던 유일한 지점은 `ReservationService.kt`이며, 이는 "삭제"가 아니라 §8의
  교체로 처리된다. `operation` 쪽 `PlatformSyncFacade.kt`/`LoggingPlatformSyncFacade.kt`는 그대로 유지된다
  (요구사항에 명시됨).

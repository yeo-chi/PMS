# 15 [예약] OTA 취소통보(CANCEL_CONFIRM) 처리

## Requirements

- OTA가 보내는 취소통보(CANCEL_CONFIRM)는 통보형이므로 **거부 불가** — 도착 즉시 확정 처리한다 (동시성 충돌이 나도 CONFLICT로 되돌리지 않고 내부적으로 해소해야 함, BOOK과 다른 지점).
- 대상 예약이 `CONFIRMED`였든 `PENDING_CANCEL`이었든 관계없이 `CANCELLED`로 전이한다 (재고 오픈).
- 이미 `CANCELLED`인 예약에 대한 재통보는 에러 없이 멱등하게 무시한다 (재전이 없음, 재알림 없음).
- `reservation_requests`에 `CANCEL_CONFIRM` 액션으로 기록하고, `outbound_notifications`에 `RESERVATION_CANCELLED` 이벤트를 예약 상태 변경과 **같은 트랜잭션**으로 append한다.
- `version`(optimistic lock)으로 동시 상태 변경 충돌을 감지한다.
- `controller`는 이번 티켓 범위 밖 (#14 BOOK 티켓과 동일한 스코프 경계).

## Technical Approach

### 0. 실제 머지된 코드 기준 확인 (plan 문서가 아니라 PR #22/#23 결과물)

`gh pr view 22`/`gh pr view 23`로 병합된 실제 구현과 `main`의 현재 코드를 직접 읽고 그 위에 이어 붙인다.

- **`ReservationStatus.PENDING_CANCEL`은 이미 존재한다** (`domain/ReservationStatus.kt`, #13에서 도입). 사용자 요청대로, PENDING_CANCEL로의 전이 로직 자체(호스트 취소요청 처리)는 #16에서 만들어질 예정이지만, 이 enum 값과 `persistent` 매핑(`@Enumerated(EnumType.STRING)`)은 이미 완성돼 있다. 따라서 **이 티켓의 테스트는 #16을 기다리지 않고도**, `ReservationRepositoryTest`가 이미 하는 것처럼 `Reservation(..., status = ReservationStatus.PENDING_CANCEL, ...).toEntity()`를 리포지토리로 직접 저장해 PENDING_CANCEL 픽스처를 만들 수 있다. `ReservationService.cancelConfirm(...)`는 "현재 상태가 PENDING_CANCEL인 row"만 다루면 되고, 그 상태에 어떻게 도달했는지는 몰라도 된다 — #16과의 결합은 없다.
- **`ReservationEntity.status`는 `var`다** (`persistent/ReservationEntity.kt:43`). `ReservationRepositoryTest`의 낙관적 락 테스트가 이미 `entity.status = ReservationStatus.CANCELLED` 후 `saveAndFlush`로 버전 충돌을 검증하는 패턴을 쓰고 있다 — CANCEL_CONFIRM도 동일한 패턴(엔티티 상태 직접 변경 + dirty checking)을 그대로 재사용한다.
- **`ReservationRepository`에는 아직 조회 메서드가 없다** (`JpaRepository<ReservationEntity, Long>`만, plan/13.md가 "조회 니즈가 실제로 생기는 후속 티켓에서 추가"라고 미뤄둔 부분). CANCEL_CONFIRM은 OTA가 보낸 `platformId`+`platformReservationRef`(자사 예약 참조값이 아니라 **채널이 발급한 참조값** — 기획문서 4.2 "취소통보 (해당 예약 참조값)")로 대상 예약을 찾아야 하므로, 이번 티켓에서 처음으로 조회 메서드를 추가한다:
  ```kotlin
  // persistent/ReservationRepository.kt
  interface ReservationRepository : JpaRepository<ReservationEntity, Long> {
      fun findByPlatformIdAndPlatformReservationRef(platformId: String, platformReservationRef: String): ReservationEntity?
  }
  ```
- **`ReservationService`는 BOOK 처리와 같은 클래스에 이어서 작성한다** (별도 `ReservationCancellationService`로 쪼개지 않음). 이슈 Technical Approach는 두 선택지를 열어뒀지만, 이미 존재하는 `ReservationService`가 `reservationRepository`/`reservationRequestRepository`/`outboundNotificationRepository`/`transactionTemplate`/`objectMapper`를 전부 갖고 있어 그대로 재사용 가능하고, 클래스를 쪼개면 같은 협력 빈 세트를 또 주입해야 한다. 파일이 과도하게 커지면(CHANGE/CANCEL_REQUEST까지 붙는 #16/#17 이후) 그때 분리를 재검토한다.
- **BOOK의 `recordConflict` 패턴에서 얻은 교훈을 그대로 따른다**: DB 제약/낙관적 락 예외는 `transactionTemplate.execute { }` 블록 **안에서 잡지 않는다**. PR #23에서 실제로 "예외 이후 flush된 Hibernate 세션"이 `AssertionFailure`를 일으키는 문제를 테스트로 재현했고, 예외를 트랜잭션 밖으로 흘려보내 트랜잭션/세션이 정상 롤백되게 한 뒤 별도 트랜잭션으로 재시도/재조회하도록 고쳤다. CANCEL_CONFIRM의 낙관적 락 재시도도 동일하게, 실패한 시도의 트랜잭션이 완전히 끝난 뒤 **새 `transactionTemplate.execute` 블록**으로 재시도한다.

### 1. 요청 커맨드

```kotlin
// service/CancelConfirmCommand.kt
data class CancelConfirmCommand(
    val platformId: String,
    val platformReservationRef: String,
    // OTA가 통보 단위로 발급한 값이 있으면 채운다. 없으면 null.
    val externalRequestId: String? = null,
)
```

- `request_key`는 스키마 주석의 CANCEL 포맷을 그대로 따른다 (`platform_id + ':' + external_request_id` 또는 `reservation_no + ':' + action + ':' + 요청시각(초단위)`):
  ```kotlin
  // service/CancelConfirmRequestKey.kt (BookRequestKeyTest.kt와 대칭되는 순수 함수 + 단위 테스트)
  fun buildCancelConfirmRequestKey(
      platformId: String,
      platformReservationRef: String,
      externalRequestId: String?,
      now: OffsetDateTime,
  ): String =
      if (externalRequestId != null) {
          "$platformId:$externalRequestId"
      } else {
          "$platformId:$platformReservationRef:CANCEL_CONFIRM:${now.truncatedTo(ChronoUnit.SECONDS)}"
      }
  ```
  `externalRequestId`가 없는 케이스는 초 단위로 묶이므로, **같은 초 안에 도착한 정확히 동일한 재시도**만 이 키로 멱등 처리된다. 그보다 더 늦게(다른 초에) 도착하는 "진짜 재통보"는 아래 2번의 **상태 기반 멱등성**(이미 CANCELLED면 무시)이 최종 방어선이 된다 — BOOK의 "요청 단위 멱등성"과는 성격이 다른, CANCEL_CONFIRM 고유의 이중 방어임을 설계 근거로 남긴다.

### 2. 처리 흐름 (`ReservationService.cancelConfirm`)

```
1. requestKey = buildCancelConfirmRequestKey(command, now)
2. reservationRequestRepository.findByRequestKey(requestKey) 존재하면 → 그 결과의 toDomain() 그대로 반환 (요청 단위 멱등성, BOOK과 동일)
3. 최대 N회(예: 3회) 재시도 루프:
   transactionTemplate.execute {
     reservation = reservationRepository.findByPlatformIdAndPlatformReservationRef(command.platformId, command.platformReservationRef)
     if (reservation == null) {
       // 예약 자체가 없음 — reservation_id를 채울 수 없어 outbound_notifications는 만들지 않는다 (BOOK의 CONFLICT 케이스와 동일한 이유, NOT NULL FK 참고 4번)
       request = ReservationRequest(reservationId=null, action=CANCEL_CONFIRM, resultStatus=FAILED, rejectReason="RESERVATION_NOT_FOUND", ...)
       return reservationRequestRepository.saveAndFlush(request.toEntity()).toDomain()   // 재시도 불필요, 즉시 반환
     }
     when (reservation.status) {
       CANCELLED -> {
         // 상태 기반 멱등성: 이미 목표 상태 — 재전이도 재알림도 하지 않는다
         request = ReservationRequest(reservationId=reservation.id, action=CANCEL_CONFIRM, resultStatus=SUCCESS, oldDateRange=reservation.dateRange, ...)
         return reservationRequestRepository.saveAndFlush(request.toEntity()).toDomain()
       }
       CONFIRMED, PENDING_CANCEL -> {
         reservation.status = CANCELLED
         savedReservation = reservationRepository.saveAndFlush(reservation)   // 낙관적 락 충돌 시 ObjectOptimisticLockingFailureException
         request = ReservationRequest(reservationId=savedReservation.id, action=CANCEL_CONFIRM, resultStatus=SUCCESS, oldDateRange=이전 dateRange, ...)
         savedRequest = reservationRequestRepository.saveAndFlush(request.toEntity())
         outboundNotificationRepository.saveAndFlush(RESERVATION_CANCELLED 알림)   // 같은 트랜잭션
         return savedRequest.toDomain()
       }
     }
   }
   ↑ ObjectOptimisticLockingFailureException을 이 블록 "밖"에서 잡아 재시도. N회 다 실패하면 예외를 그대로 전파한다
     (OTA 취소통보는 "거부 불가"이지 "무한 재시도 보장"은 아니므로, 병적인 경합 상황은 호출자/재시도 정책에 맡긴다).
```

- `when (reservation.status)`는 3개 값(`CONFIRMED`/`PENDING_CANCEL`/`CANCELLED`)을 모두 다루는 exhaustive 분기로 작성해 `else` 없이 컴파일러가 누락을 잡아주게 한다.
- 재시도 루프는 매 시도마다 `findByPlatformIdAndPlatformReservationRef`로 **다시 조회**한다 (낙관적 락 충돌 후에는 최신 `version`을 다시 읽어야 하므로, 실패한 시도에서 들고 있던 stale 엔티티를 재사용하지 않는다).

### 3. `reservation_requests` 필드 매핑

스키마 주석("old_date_range DATERANGE, -- CHANGE/CANCEL 일 때만 값 존재")에 따라 CANCEL_CONFIRM은 `oldDateRange`를 채운다:

- `action = ReservationRequestAction.CANCEL_CONFIRM`
- `initiatedBy = RequestInitiator.OTA` (기획문서 2.2: 취소통보는 OTA만 보낼 수 있음 — HOST/SELF_SERVICE는 이 액션의 주체가 될 수 없으므로 커맨드에 `initiatedBy` 필드를 아예 두지 않고 서비스에서 상수로 고정한다. BOOK처럼 `require(initiatedBy != HOST)` 같은 런타임 검증이 필요 없어짐)
- `roomCode = reservation.roomCode`, `oldDateRange = reservation.dateRange`(전이 전 값), `newDateRange = null`
- `reservationId`: 찾은 경우 항상 채움(이미 CANCELLED였던 케이스 포함), 못 찾은 경우만 `null`
- `resultStatus`: 정상 전이/이미 CANCELLED 모두 `SUCCESS`, 예약 없음만 `FAILED`(스키마 주석의 "FAILED(기타 오류)"에 해당 — CONFLICT는 겹침 전용이라 이 액션에서는 쓰지 않음)

### 4. `outbound_notifications` — "예약 없음" 케이스는 발행하지 않는다 (plan/14.md와 동일한 이유)

`outbound_notifications.reservation_id`는 `docs/schema/reservation_server_schema.sql:126`에서 `NOT NULL REFERENCES reservations(id)`다. `platformId`+`platformReservationRef`로 예약을 못 찾은 경우 참조할 `reservation_id`가 없으므로 알림을 만들 수 없다 — `reservation_requests`에 `FAILED`/`RESERVATION_NOT_FOUND`로만 기록하고 끝낸다. 이미 `CANCELLED`인 케이스도 상태 변경이 없으므로 알림을 다시 만들지 않는다(중복 하류 통보 방지). 알림은 오직 "이번 호출로 실제 `CANCELLED`로 전이한" 경우에만 만든다.

- `notificationKey = "${reservation.reservationNo}:RESERVATION_CANCELLED"`
- payload: BOOK의 `ReservationConfirmedPayload`와 대칭되는 `ReservationCancelledPayload(reservationNo, platformId, roomCode, startDate, endDate)` — 전이 전 날짜 범위를 담아 운영 서버가 "어느 기간이 오픈됐는지" 알 수 있게 한다.

## Testing Plan

기존 `ReservationServiceTest.kt`에 `feature("CANCEL_CONFIRM 처리")` 블록을 추가하는 방식을 권장한다 (같은 `ReservationService` 빈을 테스트하므로 새 파일보다는 기존 파일 확장이 자연스러움 — 파일이 과도하게 길어지면 그때 쪼갠다). `buildCancelConfirmRequestKey`는 `BookRequestKeyTest.kt`와 대칭되는 새 순수 단위 테스트 파일로 분리한다.

- **`buildCancelConfirmRequestKey` 단위 테스트** (Spring 컨텍스트 불필요): `externalRequestId` 있을 때/없을 때 포맷 검증, 같은 입력이면 같은 키, `externalRequestId`가 다르면 다른 키.
- **CONFIRMED → CANCELLED**: `reservationService.book(...)`으로 CONFIRMED 예약을 만든 뒤 같은 `platformId`+`platformReservationRef`로 `cancelConfirm(...)` 호출 → `reservations.status = CANCELLED` 확인, `reservation_requests`에 `CANCEL_CONFIRM`/`SUCCESS` 1건, `outbound_notifications`에 `RESERVATION_CANCELLED`/`PENDING` 정확히 1건 검증.
- **PENDING_CANCEL → CANCELLED**: `reservationRepository.saveAndFlush(Reservation(..., status = PENDING_CANCEL, ...).toEntity())`로 서비스 계층을 거치지 않고 직접 픽스처를 만든 뒤(#16 선행 불필요) `cancelConfirm(...)` 호출 → 동일하게 `CANCELLED` 전이 및 알림 1건 검증.
- **이미 CANCELLED인 예약에 재통보**: 위 두 케이스 중 하나를 먼저 `CANCELLED`로 만든 뒤 다시 `cancelConfirm(...)` 호출(서로 다른 `externalRequestId` 또는 시간차를 둬 request_key가 다르게) → 예외 없이 반환, `reservations.status`는 그대로 `CANCELLED`(추가 UPDATE 없음, `version` 안 올라감), `outbound_notifications` row 수는 늘지 않음(직전 테스트에서 만든 1건 그대로), `reservation_requests`에는 새 `SUCCESS` 감사 기록 1건이 추가됨을 검증.
- **존재하지 않는 예약에 대한 취소통보**: 등록된 적 없는 `platformReservationRef`로 `cancelConfirm(...)` 호출 → `resultStatus = FAILED`, `rejectReason = "RESERVATION_NOT_FOUND"`, `reservationId = null`, `outbound_notifications` row 생성 안 됨 검증.
- **동일 통보 재시도(요청 단위 멱등성)**: 같은 `externalRequestId`로 `cancelConfirm(...)`를 두 번 호출 → 두 번째 호출은 재처리 없이 첫 번째와 동일한 `ReservationRequest`를 반환하고 `reservation_requests`/`outbound_notifications` row 수가 늘지 않는지 검증 (BOOK의 멱등성 테스트와 대칭).
- **낙관적 락 충돌 재시도**: `ReservationRepositoryTest`의 낙관적 락 테스트와 같은 방식으로, `cancelConfirm` 호출 도중 네이티브 쿼리로 대상 row의 `version`을 미리 올려 첫 시도가 `ObjectOptimisticLockingFailureException`을 맞게 만든 뒤, 재시도 루프가 최신 상태를 다시 읽어 결국 `SUCCESS`로 끝나는지 검증 (재시도 로직이 실제로 동작함을 증명하는 핵심 테스트).
- CI/로컬 실행 전제: Docker 데몬 필요(Testcontainers) — #13/#14와 동일.

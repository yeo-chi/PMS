# #2 [예약] 도메인/Entity/Repository 생성

> Context: PR #7 (issue #1, Gradle 멀티모듈 구조)이 `main`에 머지되어, `reservation`/`operation` 두 모듈이 각각
> 독립 실행 가능한 Spring Boot 앱으로 이미 구성돼 있다 (`reservation/build.gradle.kts`,
> `ReservationApplication.kt` 등 확인 완료). 5개 패키지 컨벤션(`controller`/`service`/`domain`/`persistent`/
> `configuration`)도 이미 스캐폴딩되어 있고 `reservation/domain`, `reservation/persistent`는 현재 비어 있다
> (`.gitkeep`만 존재). 이번 티켓은 그 자리에 실제 `Reservation` Entity, 상태 enum, `ReservationRepository`를
> 채우는 작업이다.
>
> 이슈 #2의 본문은 이번 확인 시점에는 제목과 일치하는 내용(예약 도메인 모델 정의, H2 영속성 계층,
> `Reservation` Entity, 상태 enum, `ReservationRepository`, `@DataJpaTest` 테스트)으로 되어 있어 별도 보정이
> 필요 없다. 다만 필드 스펙은 이슈 본문보다 구체적으로 아래처럼 확정되었으므로, 이 문서의 필드 정의를
> 기준으로 구현한다.

## Requirements

- `reservation` 모듈의 `domain` 패키지(`yeo.chi.proejct.pms.reservation.domain`)에 `Reservation` JPA Entity와
  예약 상태 enum을 정의한다.
- `Reservation` 필드는 다음으로 확정:
  - `id`: PK (자동 채번)
  - `platformCode`: 예약이 발생한 플랫폼 식별 코드
  - `roomId`: 객실 ID
  - `userIdentifyCode`: 예약자(고객) 식별 코드
  - `startDate`: 예약 시작일
  - `endDate`: 예약 종료일
  - `reservedAt`: 예약이 실제로 발생/접수된 일시
  - `code`: 플랫폼이 발급한 예약 코드. **멱등성 키(idempotency key)** 로 사용되며, `platformCode` + `code`
    조합에 유니크 제약이 걸려야 한다 (동일 플랫폼에서 동일 예약 코드가 두 번 저장되는 것을 DB 레벨에서 방지).
  - `status`: `ReservationStatus` enum, 값은 `CONFIRMED` / `CANCELLED` 두 가지.
- `reservation` 모듈의 `persistent` 패키지(`yeo.chi.proejct.pms.reservation.persistent`)에
  `ReservationRepository` (Spring Data JPA)를 정의한다.
- H2 기반 영속성 계층으로 동작해야 하며(이미 `reservation/build.gradle.kts`에 `runtimeOnly("com.h2database:h2")`
  구성돼 있음), 별도 데이터소스 설정 변경 없이 `application.yaml` 기본값(임베디드 H2 자동 구성)을 그대로
  사용한다.
- 5개 패키지 컨벤션을 그대로 따른다: `domain`에 Entity/enum, `persistent`에 Repository. `controller`/
  `service`/`configuration`은 이번 티켓에서 건드리지 않는다 (각각 #4, #3, 추후 티켓 소관).
- `ReservationApplication`의 기존 `@EntityScan(basePackages = [..., "yeo.chi.proejct.pms.reservation.domain", ...])`
  범위에 이미 `reservation.domain`이 포함돼 있으므로, 이번 티켓에서 엔티티 스캔 설정을 추가로 손댈 필요는
  없다 (변경 불필요, 확인만 한다).

## Technical Approach

### 1. `ReservationStatus` enum

`reservation/src/main/kotlin/yeo/chi/proejct/pms/reservation/domain/ReservationStatus.kt`:

```kotlin
package yeo.chi.proejct.pms.reservation.domain

enum class ReservationStatus {
    CONFIRMED,
    CANCELLED,
}
```

### 2. `Reservation` Entity

`reservation/src/main/kotlin/yeo/chi/proejct/pms/reservation/domain/Reservation.kt`:

- `id`는 생성자 밖에서 `@Id @GeneratedValue(strategy = GenerationType.IDENTITY)`로 선언하고 `protected set`으로
  막아 외부에서 임의로 값을 넣지 못하게 한다 (H2/IDENTITY 채번 방식은 기존 프로젝트의 다른 H2 사용 방식과
  일치).
- `status`도 `protected set`으로 캡슐화하고 기본값 `CONFIRMED`를 준다. 상태 변경은 `cancel()` 같은 도메인
  메서드를 통해서만 하도록 한다 (setter 직접 노출 금지 — 필수는 아니지만 kotlin-springboot 스킬의 불변성/
  캡슐화 권장 사항에 맞춤. 이번 티켓 범위를 최소화하고 싶다면 `cancel()` 메서드는 생략하고 `var status`만
  두어도 무방).
- 나머지 필드(`platformCode`, `roomId`, `userIdentifyCode`, `startDate`, `endDate`, `reservedAt`, `code`)는
  모두 생성 시점에 확정되는 값이므로 주 생성자의 `val` 파라미터로 선언하고 `updatable = false`를 준다.
- `platformCode` + `code` 조합에 `@Table(uniqueConstraints = [...])`로 DB 유니크 제약을 건다.
- `kotlin-jpa`(`no-arg`) 컴파일러 플러그인이 이미 `reservation/build.gradle.kts`에 적용돼 있어 별도의 no-arg
  생성자를 직접 작성할 필요는 없다.

```kotlin
package yeo.chi.proejct.pms.reservation.domain

import jakarta.persistence.Column
import jakarta.persistence.Entity
import jakarta.persistence.EnumType
import jakarta.persistence.Enumerated
import jakarta.persistence.GeneratedValue
import jakarta.persistence.GenerationType
import jakarta.persistence.Id
import jakarta.persistence.Table
import jakarta.persistence.UniqueConstraint
import java.time.LocalDate
import java.time.LocalDateTime

@Entity
@Table(
    name = "reservation",
    uniqueConstraints = [
        UniqueConstraint(
            name = "uk_reservation_platform_code_code",
            columnNames = ["platform_code", "code"],
        ),
    ],
)
class Reservation(
    @Column(name = "platform_code", nullable = false, updatable = false)
    val platformCode: String,

    @Column(name = "room_id", nullable = false, updatable = false)
    val roomId: Long,

    @Column(name = "user_identify_code", nullable = false, updatable = false)
    val userIdentifyCode: String,

    @Column(name = "start_date", nullable = false, updatable = false)
    val startDate: LocalDate,

    @Column(name = "end_date", nullable = false, updatable = false)
    val endDate: LocalDate,

    @Column(name = "reserved_at", nullable = false, updatable = false)
    val reservedAt: LocalDateTime,

    // 플랫폼이 발급한 예약 코드. platformCode + code 조합이 멱등성 키이며,
    // 위 @Table(uniqueConstraints=...)로 DB 레벨 중복 저장을 막는다.
    @Column(name = "code", nullable = false, updatable = false)
    val code: String,
) {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    @Column(name = "id")
    var id: Long? = null
        protected set

    @Enumerated(EnumType.STRING)
    @Column(name = "status", nullable = false)
    var status: ReservationStatus = ReservationStatus.CONFIRMED
        protected set

    fun cancel() {
        status = ReservationStatus.CANCELLED
    }
}
```

Note: `roomId`는 현재 `operation` 모듈에 아직 Room/Platform 매핑 엔티티가 없으므로(#5에서 생성 예정) 단순
`Long` 값으로만 저장하고, JPA 연관관계(`@ManyToOne` 등)는 만들지 않는다. 모듈 간 엔티티 직접 참조는 피하고,
필요한 교차 검증(예: roomId가 실제 존재하는지)은 이후 티켓에서 서비스 레이어가 `operation`의 공개 API를 통해
수행하도록 남겨둔다.

### 3. `ReservationRepository`

`reservation/src/main/kotlin/yeo/chi/proejct/pms/reservation/persistent/ReservationRepository.kt`:

멱등성 키(`platformCode` + `code`) 기준 조회/존재 확인 메서드를 함께 제공해, #3에서 예약 생성 서비스가
"이미 처리된 예약인지" 저장 전에 확인할 수 있게 한다.

```kotlin
package yeo.chi.proejct.pms.reservation.persistent

import org.springframework.data.jpa.repository.JpaRepository
import yeo.chi.proejct.pms.reservation.domain.Reservation

interface ReservationRepository : JpaRepository<Reservation, Long> {

    fun existsByPlatformCodeAndCode(platformCode: String, code: String): Boolean

    fun findByPlatformCodeAndCode(platformCode: String, code: String): Reservation?
}
```

### 4. 스캔 설정 확인 (변경 불필요)

`reservation/src/main/kotlin/yeo/chi/proejct/pms/reservation/ReservationApplication.kt`은 이미
`@EntityScan(basePackages = ["yeo.chi.proejct.pms.reservation.domain", "yeo.chi.proejct.pms.operation.domain"])`
을 가지고 있어 새로 추가하는 `Reservation` 엔티티가 자동으로 스캔 대상에 포함된다. `ReservationRepository`도
`yeo.chi.proejct.pms.reservation.persistent` 패키지가 `@SpringBootApplication`의 기본 base package
(`yeo.chi.proejct.pms.reservation`) 하위이므로 Spring Data JPA의 기본 리포지토리 스캔 범위에 자동으로
포함된다 (별도 `@EnableJpaRepositories` 불필요). 이 티켓에서는 이 두 스캔 설정을 **수정하지 않는다** — 그대로
잘 동작하는지 빌드/테스트로 확인만 한다.

### 5. Edge cases

- `roomId`/`userIdentifyCode`/`platformCode`/`code`는 모두 생성 후 불변(`updatable = false`)으로 두어, 예약
  원본 데이터가 서비스 로직에서 실수로 변경되는 것을 막는다. 변경 가능한 필드는 `status`뿐이다.
- 동일 `platformCode` + `code` 조합으로 두 번 저장을 시도하면 `DataIntegrityViolationException`이 발생해야
  한다 (DB 유니크 제약을 통한 멱등성 보장 확인 — 테스트 플랜에 포함).
- `code`는 플랫폼마다 독립적인 채번 규칙을 가질 수 있으므로 유니크 제약은 `code` 단독이 아니라 반드시
  `platformCode + code` 조합이어야 한다 (서로 다른 플랫폼이 같은 `code` 값을 발급해도 충돌하면 안 됨).
- `id`, `status`의 setter는 `protected`로 막아 엔티티 불변식을 보호한다 (Kotlin에서 JPA 필드 변경을 임의
  setter로 노출하지 않는 관례).

## Testing Plan

`@DataJpaTest` 기반으로 저장/조회 테스트를 작성한다 (JUnit5 `@Test` + Kotest matchers 조합 — 기존
`ReservationApplicationTests.kt`와 동일하게 JUnit5 러너를 쓰되, 프로젝트에 이미 있는 `io.kotest:kotest-assertions-core`
의 `shouldBe` 등 matcher를 사용해 가독성을 높인다).

`reservation/src/test/kotlin/yeo/chi/proejct/pms/reservation/persistent/ReservationRepositoryTest.kt`:

```kotlin
package yeo.chi.proejct.pms.reservation.persistent

import io.kotest.matchers.nulls.shouldNotBeNull
import io.kotest.matchers.shouldBe
import org.junit.jupiter.api.Test
import org.springframework.beans.factory.annotation.Autowired
import org.springframework.boot.test.autoconfigure.orm.jpa.DataJpaTest
import org.springframework.dao.DataIntegrityViolationException
import yeo.chi.proejct.pms.reservation.domain.Reservation
import yeo.chi.proejct.pms.reservation.domain.ReservationStatus
import java.time.LocalDate
import java.time.LocalDateTime
import kotlin.test.assertFailsWith

@DataJpaTest
class ReservationRepositoryTest @Autowired constructor(
    private val reservationRepository: ReservationRepository,
) {

    private fun newReservation(
        platformCode: String = "AIRBNB",
        code: String = "AIRBNB-CODE-0001",
    ) = Reservation(
        platformCode = platformCode,
        roomId = 1L,
        userIdentifyCode = "guest-001",
        startDate = LocalDate.of(2026, 9, 1),
        endDate = LocalDate.of(2026, 9, 3),
        reservedAt = LocalDateTime.of(2026, 8, 13, 10, 0),
        code = code,
    )

    @Test
    fun `저장 후 id로 조회하면 저장한 값이 그대로 조회된다`() {
        val saved = reservationRepository.save(newReservation())

        saved.id.shouldNotBeNull()
        val found = reservationRepository.findById(saved.id!!).orElseThrow()
        found.platformCode shouldBe "AIRBNB"
        found.code shouldBe "AIRBNB-CODE-0001"
        found.status shouldBe ReservationStatus.CONFIRMED
    }

    @Test
    fun `동일 platformCode + code 조합을 다시 저장하면 유니크 제약 위반으로 실패한다`() {
        reservationRepository.saveAndFlush(newReservation())

        assertFailsWith<DataIntegrityViolationException> {
            reservationRepository.saveAndFlush(newReservation())
        }
    }

    @Test
    fun `platformCode가 다르면 동일한 code 값이어도 함께 저장할 수 있다`() {
        reservationRepository.saveAndFlush(newReservation(platformCode = "AIRBNB"))
        reservationRepository.saveAndFlush(newReservation(platformCode = "BOOKING_COM"))

        reservationRepository.findAll() shouldHaveSize 2
    }

    @Test
    fun `findByPlatformCodeAndCode로 멱등성 키 기준 조회가 가능하다`() {
        reservationRepository.save(newReservation())

        reservationRepository.findByPlatformCodeAndCode("AIRBNB", "AIRBNB-CODE-0001").shouldNotBeNull()
        reservationRepository.findByPlatformCodeAndCode("AIRBNB", "NO-SUCH-CODE") shouldBe null
    }

    @Test
    fun `existsByPlatformCodeAndCode로 멱등성 키 존재 여부를 확인할 수 있다`() {
        reservationRepository.save(newReservation())

        reservationRepository.existsByPlatformCodeAndCode("AIRBNB", "AIRBNB-CODE-0001") shouldBe true
        reservationRepository.existsByPlatformCodeAndCode("AIRBNB", "OTHER-CODE") shouldBe false
    }
}
```

(`shouldHaveSize`는 `io.kotest.matchers.collections.shouldHaveSize`를 추가로 import해야 함 — 구현 시 정리.)

검증 커맨드:

1. `./gradlew :reservation:test --tests "*ReservationRepositoryTest*"` — 위 5개 케이스가 모두 통과하는지 확인.
2. `./gradlew :reservation:test` — 기존 `ReservationApplicationTests`/`ReservationModuleSmokeTest`를 포함해
   `reservation` 모듈 전체 테스트가 깨지지 않는지 확인.
3. `./gradlew :reservation:build` — 컴파일 및 전체 빌드 성공 확인 (엔티티/enum/리포지토리 추가로 인한 컴파일
   에러가 없는지).
4. (선택) `./gradlew :reservation:bootRun` 후 H2 콘솔 또는 로그로 `reservation` 테이블이 `platform_code`,
   `room_id`, `user_identify_code`, `start_date`, `end_date`, `reserved_at`, `code`, `status` 컬럼과
   `uk_reservation_platform_code_code` 유니크 제약으로 정상 생성되는지 수동 확인.

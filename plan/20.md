# 20 [운영] Inbound event 수신 API - 멱등 처리 + outbox_events 발행

## Requirements

- 예약 서버로부터 오는 이벤트(`RESERVATION_CONFIRMED`/`RESERVATION_REJECTED`/`CANCEL_REQUESTED`/`RESERVATION_CANCELLED`)를 받는 REST 엔드포인트 (`controller` 패키지).
- `notification_key`로 `inbound_events`에 먼저 UNIQUE 저장 시도 → 이미 존재하면(중복 수신) 처리 없이 이전과 동일한 성공 응답만 반환 (수신측 멱등성).
- 신규 수신 건은 이벤트 유형에 따라 통보 대상(`target_type`: `OTA_CHANNEL` 또는 `HOST`)을 판정해 `outbox_events`에 **같은 트랜잭션**으로 append한다.
- 교차 DB라 조인이 불가능하므로, 대상 판정에 필요한 정보(`platform_id` 등)는 예약 서버가 payload에 미리 담아 보낸 것을 그대로 쓴다 — operation 쪽에서 별도 조회를 하지 않는다.

## Technical Approach

### 0. 실제 병합된 코드 기준 확인 — 그리고 아직 안 끝난 선행 티켓(#19)에 대한 주의

`git pull` 후 두 가지를 확인했다.

- **수신 계약은 이미 확정돼 있다.** #18(PR #27, 병합됨)의 `reservation/.../service/InboundEventRequest.kt` + `OutboundNotificationDispatchWorker.kt`가 이미 실제로 호출하는 계약이 존재한다:
  ```kotlin

  data class InboundEventRequest(
      val notificationKey: String,
      val reservationNo: String,
      val eventType: String,
      @get:JsonRawValue val payload: String,   // 이미 직렬화된 JSON을 raw로 실어 보냄
  )
  ```

- **`operation` 모듈의 #19(도메인/persistent)는 아직 완료되지 않았다.** 지금 워킹 트리에는 `domain/Host.kt`/`HostStatus.kt`/`OtaChannel.kt`/`OtaChannelIntegrationMode.kt`/`OtaChannelStatus.kt`/`Room.kt`/`RoomStatus.kt`까지만 있고, `RoomChannelListing`, `InboundEvent`, `OutboxEvent`와 `persistent` 패키지 전체가 아직 없다(커밋도 안 된 진행 중 상태). 이 플랜은 `plan/19.md`가 제안한 설계(`InboundEvent`/`OutboxEvent` 도메인 필드, `LocalDateTime` 타임스탬프, `createdAt`/`updatedAt` DB 관리, `findByNotificationKey`/`findByOutboxKey` 리포지토리 메서드)를 그대로 전제로 삼는다. **#19가 실제로 병합된 뒤, 이 플랜을 실행하기 전에 `InboundEventEntity`/`OutboxEventEntity`/`OutboxEventRepository`의 실제 시그니처를 다시 확인해야 한다** (plan/13.md와 실제 PR #22 사이에 있었던 것과 같은 종류의 사소한 차이가 있을 수 있음).

### 1. 대상(target) 판정 — 조인 없이 payload만으로, 그리고 지금은 항상 `OTA_CHANNEL`

이슈가 명시한 대로 조인은 하지 않는다. `#14`~`#17`이 이미 만들어 보낸 4가지 payload(`ReservationConfirmedPayload`/`ReservationCancelledPayload`/`ReservationCancelRequestedPayload`/`ReservationChangedPayload`, 전부 `reservation/.../service/ReservationService.kt`에 private data class로 정의됨)는 **전부 `platformId` 필드를 공통으로 갖고 있다.** 이 값을 그대로 `outbox_events.target_code`로 쓰고, `target_type`은 항상 `OTA_CHANNEL`로 고정한다:

- `RESERVATION_CONFIRMED`, `RESERVATION_REJECTED` → 예약/변경을 시도한 채널에 결과 통보.
- `CANCEL_REQUESTED` → 호스트가 시작했더라도, 통보 대상은 **호스트가 아니라 그 예약을 소유한 OTA**다(기획문서 4.3: "운영 서버 → 대상 OTA: 취소요청 전달" — 호스트의 요청을 OTA에 릴레이하는 것이지 호스트에게 보내는 게 아님).
- `RESERVATION_CANCELLED` → 예약을 소유한 채널에 재고 오픈 통보.

**범위에서 뺀 것 (결정 사항)**: 기획문서 4.1/4.2/4.3은 "그 외 관련 채널에도 재고 마감/오픈 통보 (필요 시)"를 언급하지만, 이건 "이 room_code를 리스팅한 다른 모든 OTA 채널"을 찾아 `outbox_events`를 여러 건 fan-out해야 한다는 뜻이라 (a) `room_channel_listings` 조회가 필요해 "조인 없이 payload만으로" 원칙과 충돌하고 (b) 이슈의 테스트 계획이 "outbox_events가 정확한 target_type/target_code로 **1건** append"라고 못박고 있어, 여러 건 발행을 요구하지 않는다. **이번 티켓은 inbound event 1건당 outbox_event 1건(원 채널 대상)만 만든다** — 다른 채널 팬아웃은 범위 밖으로 명시하고, 필요하면 별도 이슈로 분리할 것을 제안한다.
  > **업데이트(#33)**: `RESERVATION_CONFIRMED`/`RESERVATION_CANCELLED`에 대해 다른 채널 팬아웃이 실제로 구현됐다(`INVENTORY_CLOSED`/`INVENTORY_REOPENED`). #34에서 `RESERVATION_CHANGED`(`INVENTORY_CHANGED`)까지 확장됐다.
- `target_type = HOST`는 스키마에 정의는 돼 있지만 이 4개 이벤트 타입 중 어느 것도 실제로 HOST를 대상으로 하지 않는다(기획문서의 4개 시나리오 어디에도 "운영 서버 → 호스트" 통보가 나오지 않음) — 이번 티켓에서는 안 쓰고, 향후 이벤트 타입이 추가되면 그때 분기를 넣는다.
  > **업데이트(#34)**: `RESERVATION_CHANGED`(예약 변경)가 방을 소유한 호스트에게도 통보돼야 한다는 요구사항이 추가로 확인돼, `HOST` 대상 `outbox_events`를 실제로 만드는 경로가 생겼다(`notifyHost`). 이벤트 타입 목록도 5개로 늘었다.

### 2. `InboundEventService` — reservation의 `TransactionTemplate` 패턴을 그대로 재사용

단순히 `@Transactional` 사설 메서드를 같은 클래스 안에서 `this.xxx()`로 호출하면 #14~#17에서 이미 겪은 self-invocation 문제(AOP 프록시 우회)에 그대로 부딪힌다. reservation이 확립한 `TransactionTemplate` 패턴을 operation에도 동일하게 도입한다 (`configuration/TransactionConfiguration.kt`를 reservation과 똑같이 추가 — `PlatformTransactionManager`를 받아 `TransactionTemplate` 빈을 만듦).

```kotlin
// service/InboundEventService.kt
@Service
class InboundEventService(
    private val inboundEventRepository: InboundEventRepository,
    private val outboxEventRepository: OutboxEventRepository,
    private val transactionTemplate: TransactionTemplate,
    private val objectMapper: ObjectMapper,
) {
    fun receive(request: InboundEventRequest): Unit {
        // 요청 단위 멱등성: 정확히 같은 notification_key 재전송은 여기서 걸러진다 (reservation의 findByRequestKey와 동일 패턴)
        if (inboundEventRepository.findByNotificationKey(request.notificationKey) != null) return

        try {
            processNew(request)
        } catch (duplicateKey: DataIntegrityViolationException) {
            // uq_notification_key 위반 = 두 요청이 findByNotificationKey를 동시에 통과한 극단적 레이스.
            // 이미 다른 스레드가 처리했으므로 재조회하지 않고 그냥 성공으로 간주한다 (내용이 같으므로 재조회 불필요 —
            // reservation의 recordConflict가 결과값을 돌려줘야 해서 재조회했던 것과 달리, 여기는 반환값이 없어 더 단순함).
        }
    }

    private fun processNew(request: InboundEventRequest) {
        transactionTemplate.execute {
            val payloadJson = objectMapper.writeValueAsString(request.payload)
            inboundEventRepository.saveAndFlush(
                InboundEvent(
                    id = null,
                    notificationKey = request.notificationKey,
                    reservationNo = request.reservationNo,
                    eventType = request.eventType,
                    payload = payloadJson,
                ).toEntity(),
            )

            val platformId =
                requireNotNull(request.payload.get("platformId")?.asText()) {
                    "payload에 platformId가 없습니다: notificationKey=${request.notificationKey}"
                }
            outboxEventRepository.saveAndFlush(
                OutboxEvent(
                    id = null,
                    outboxKey = "${request.reservationNo}:OTA_CHANNEL:$platformId:${request.eventType}",
                    targetType = OutboxTargetType.OTA_CHANNEL,
                    targetCode = platformId,
                    reservationNo = request.reservationNo,
                    eventType = request.eventType,
                    payload = payloadJson,
                    status = OutboxEventStatus.PENDING,
                    retryCount = 0,
                    nextRetryAt = LocalDateTime.now(),   // next_retry_at은 created_at/updated_at과 달리 DB가 관리하지 않음(plan/19.md 6번) — 즉시 폴링 대상이 되도록 app이 채운다
                ).toEntity(),
            )
        }
    }
}
```

`outbox_key` 포맷은 스키마 주석(`reservation_no + ':' + target_type + ':' + target_code + ':' + event_type`)을 그대로 따른다.

### 3. 요청 DTO — 수신 측은 `payload`를 `String`이 아니라 `JsonNode`로 받는다

발신 측(`InboundEventRequest`, reservation)은 `payload: String`에 `@get:JsonRawValue`를 붙여 **직렬화 시** 이스케이프 없이 중첩 JSON으로 내보낸다. 수신 측에서 이 필드를 그대로 `String`으로 선언하면 Jackson이 JSON 객체를 문자열로 역직렬화하려다 실패한다. **수신용 DTO는 `payload`를 `com.fasterxml.jackson.databind.JsonNode`로 선언**해 중첩 JSON을 트리로 파싱받고, DB에 저장할 때만 `objectMapper.writeValueAsString(...)`으로 다시 문자열화한다 (2번 코드 참고). 발신/수신 양쪽 모두 `InboundEventRequest`라는 같은 이름의 클래스지만, 서로 다른 모듈(Gradle 컴파일 의존성 없음, CLAUDE.md 원칙)이라 이름이 같아도 무방하다.

```kotlin
// controller/InboundEventRequest.kt
data class InboundEventRequest(
    @field:NotBlank val notificationKey: String,
    @field:NotBlank val reservationNo: String,
    @field:NotBlank val eventType: String,
    val payload: JsonNode,
)
```

`spring-boot-starter-validation`을 `operation/build.gradle.kts`에 추가한다 (reservation은 이미 갖고 있음, operation은 아직 없음).

### 4. 컨트롤러

```kotlin
// controller/InboundEventController.kt
@RestController
@RequestMapping("/api/inbound-events")
class InboundEventController(
    private val inboundEventService: InboundEventService,
) {
    @PostMapping
    fun receive(@Valid @RequestBody request: InboundEventRequest): ResponseEntity<Void> {
        inboundEventService.receive(request)
        return ResponseEntity.ok().build()
    }
}
```

- 호출 측(reservation의 `OutboundNotificationDispatchWorker`)이 `toBodilessEntity()`로 상태 코드만 본다는 걸 이미 확인했으므로, 응답 바디는 굳이 만들지 않는다 — 신규 처리든 멱등 재처리든 **항상 200**.
- `eventType`이 4개 알려진 값(`RESERVATION_CONFIRMED`/`RESERVATION_REJECTED`/`CANCEL_REQUESTED`/`RESERVATION_CANCELLED`) 밖이면 400을 반환하도록 서비스 진입 시점에 검증한다 (스키마 컬럼 자체엔 `CHECK` 제약이 없어 DB가 걸러주지 않으므로, 애플리케이션 경계에서 검증).
- `payload`에 `platformId`가 없는 등 처리 중 실패는 `IllegalArgumentException`/`requireNotNull` → 이 경우 `inbound_events`도 저장되지 않는 게 맞다(트랜잭션 안에서 예외가 나면 전체 롤백) — 재전송 시 다시 시도할 수 있도록 자연스럽게 열어둔다.

## Testing Plan

`MockMvc` 기반 컨트롤러 테스트로 작성한다 (이슈가 명시한 방식).

- **신규 수신 성공**: 4개 이벤트 타입 각각에 대해 `POST /api/inbound-events` → `200`, `inbound_events`에 1건(payload가 원본 JSON 그대로 저장됐는지), `outbox_events`에 정확히 1건(`target_type=OTA_CHANNEL`, `target_code`=payload의 `platformId`, `outbox_key` 포맷, `status=PENDING`) 검증.
- **동일 `notification_key` 재전송 시 멱등 응답**: 같은 요청을 두 번 보내 → 둘 다 `200`, `inbound_events`/`outbox_events` row 수가 늘지 않음(각각 1건 유지) 검증.
- **`platformId` 없는 payload**: 처리 실패 → `inbound_events`/`outbox_events` 어디에도 row가 생기지 않는지(트랜잭션 롤백 확인) 검증.
- **알려지지 않은 `eventType`**: `400` 반환, row 생성 안 됨 검증.
- **필수 필드 누락(`notificationKey`/`reservationNo`/`eventType` blank)**: `@Valid` 검증으로 `400` 반환 확인.
- **동시 중복 수신 레이스**: `#14`의 `ExecutorService`+`CountDownLatch` 패턴을 재사용해, 같은 `notification_key`로 두 요청을 동시에 보냄 → 둘 다 `200`, `inbound_events`/`outbox_events` 각각 정확히 1건만 생성되는지 검증 (`uq_notification_key` 레이스 처리 경로가 실제로 동작함을 증명).
- `InboundEventEntity`/`OutboxEventEntity` 매퍼 단위 테스트는 #19 범위이므로 이 티켓에서 새로 만들지 않고 재사용한다.
- CI/로컬 실행 전제: Docker 데몬 필요(Testcontainers, MySQL) — #19와 동일. **#19가 먼저 병합돼 있어야 이 티켓의 컴파일이 가능하다** (의존 관계).

# 14 [예약] 예약 요청(BOOK) 처리 - 멱등성 + 중복재고 판정 + outbound_notifications 발행

## Requirements

- OTA/자사 서비스로부터 예약 요청(BOOK)을 받아 `reservation_requests`에 멱등키(`request_key`)로 기록한다.
- 동일한 BOOK 요청(같은 `platform_id`+`room_code`+날짜) 재시도 시 재처리 없이 이전 결과(`ReservationRequest`)를 그대로 반환한다 (멱등성).
- 같은 `room_code`·겹치는 날짜에 대한 동시 확정 요청은 하나만 성공한다. **애플리케이션 레벨 선점 조회(TOCTOU)로 동시성을 보장하려 하지 않고, DB의 `excl_room_date_overlap` GIST exclusion 제약 위반(예외)을 캐치해 `CONFLICT`로 변환하는 방식**을 쓴다.
- 성공 시 `reservations`에 `CONFIRMED`로 저장하고 `reservation_requests.result_status=SUCCESS`로 기록한다. 실패(겹침) 시 `reservation_requests.result_status=CONFLICT`, `reject_reason=DUPLICATE_BOOKING`으로 기록한다.
- 확정된 예약에 대해 `RESERVATION_CONFIRMED` 이벤트를 `outbound_notifications`에 예약 상태 변경과 **같은 트랜잭션**으로 append한다 (실제 HTTP 발신은 #18 워커 티켓에서 처리).
- 이 티켓 범위는 `service` 패키지의 BOOK 처리 로직까지다. `controller`(REST 엔드포인트)는 이슈 본문에 언급이 없고 `#14~#17` 각 액션 티켓과 별개로 다뤄질 것으로 보이므로 이번 티켓에서는 만들지 않는다. `CHANGE`/`CANCEL_REQUEST`/`CANCEL_CONFIRM`은 각각 #17/#16/#15에서 다룬다.

## Technical Approach

### 0. 실제 머지된 코드 기준 확인 (plan/13.md가 아니라 PR #22 결과물)

`gh pr view 22`로 병합된 실제 구현을 직접 읽고 아래 실제 시그니처를 기준으로 설계한다 (plan/13.md에 적힌 설계와 몇 가지 다름 — PR #22의 "Plan과의 구현 시 결정/차이점" 참고).

- `domain/Reservation.kt` — `data class Reservation(id: Long?, reservationNo: String?, platformId, platformReservationRef, roomCode, dateRange: ReservationDateRange, status: ReservationStatus, version: Int, createdAt, updatedAt)`이고, **`companion object Reservation.createNew(platformId, platformReservationRef, roomCode, dateRange, createdAt): Reservation`** 팩토리가 이미 존재한다 (`status=CONFIRMED`, `version=1` 고정). BOOK 신규 예약 생성은 이 팩토리를 그대로 재사용한다 (직접 `Reservation(...)` 생성자 호출 지양).
- `domain/ReservationRequest.kt` — `resultStatus: RequestResultStatus`에는 `SUCCESS`/`CONFLICT`/`FAILED`만 있고 `PENDING` 같은 중간 상태가 없다. 즉 `reservation_requests` 행은 **결과가 확정된 후에 한 번만 insert**되는 설계다 (선기록 후 상태 업데이트 방식이 아님).
- `persistent/ReservationRepository.kt` — 커스텀 조회 메서드 없음 (`JpaRepository<ReservationEntity, Long>`만). BOOK은 신규 생성이므로 조회가 필요 없어 문제 없음.
- `persistent/ReservationRequestRepository.kt` — `findByRequestKey(requestKey: String): ReservationRequestEntity?` 존재 (멱등성 조회에 그대로 사용).
- `persistent/OutboundNotificationRepository.kt` — `findByNotificationKey(...)` 존재.
- `persistent/ReservationEntity.kt` — `status`만 `var`(다른 필드는 `val`), GIST exclusion/`uq_reservation_no` 위반은 실제 테스트(`ReservationRepositoryTest`)에서 전부 **`org.springframework.dao.DataIntegrityViolationException`** 으로 확인됨 (Spring의 예외 변환 계층을 통과한 표준 예외 — 커스텀 예외 매핑 불필요).
- `reservation/build.gradle.kts`에는 이미 `spring-boot-starter-web`(Jackson `ObjectMapper` 자동 구성 포함)이 있으므로 `payload` JSON 직렬화에 새 의존성이 필요 없다.

### 1. 요청 커맨드 (`service` 패키지에 정의, 새 `dto` 패키지 만들지 않음)

```kotlin
// service/BookReservationCommand.kt
data class BookReservationCommand(
    val platformId: String,
    val platformReservationRef: String,
    val roomCode: String,
    val dateRange: ReservationDateRange,
    val initiatedBy: RequestInitiator, // OTA 또는 SELF_SERVICE만 유효 (HOST는 BOOK 불가 — 기획문서 2.2)
)
```

- `request_key`는 **외부에서 받지 않고 서비스가 직접 계산**한다. `reservation_server_schema.sql`의 주석(BOOK: `platform_id + ':' + product_code + ':' + start_date + ':' + end_date + ':BOOK'`)에서 `product_code`는 실제 컬럼명 기준으로 `room_code`를 의미한다 — 스키마에 별도 상품코드 컬럼은 없다. 기존 테스트(`ReservationRequestRepositoryTest`)가 이미 `"OTA_BOOKING:ROOM-101:2026-01-01:2026-01-05:BOOK"` 형태를 사용하고 있으므로 이 포맷과 일치시킨다.
  ```kotlin
  fun buildBookRequestKey(platformId: String, roomCode: String, dateRange: ReservationDateRange): String =
      "$platformId:$roomCode:${dateRange.startDate}:${dateRange.endDate}:BOOK"
  ```
  서비스 바깥에서 검증 가능하도록 순수 함수로 분리한다 (Spring 컨텍스트 없이 단위 테스트 가능).
- `initiatedBy == RequestInitiator.HOST`인 경우 `require(...)`로 즉시 거부한다 (호스트는 취소요청만 가능 — 기획문서 2.2 액터별 가능 액션 표).

### 2. 트랜잭션 경계 — 왜 `@Transactional` 셀프 호출로는 안 되는가

PostgreSQL은 트랜잭션 내에서 한 statement가 제약 위반으로 에러나면 그 트랜잭션 전체가 abort 상태가 되어, 같은 트랜잭션 안의 이후 statement는 전부 실패한다 (Hibernate 세션 레벨 문제가 아니라 Postgres 자체의 트랜잭션 동작). 따라서:

- "예약 insert 시도"와 "결과 기록(reservation_requests + outbound_notifications insert)"은 **겹침이 발생하면 서로 다른 트랜잭션**이어야 한다 — 겹침 시 첫 시도가 통째로 롤백된 뒤에야 CONFLICT 기록을 위한 새 트랜잭션을 열 수 있다.
- 같은 클래스 안에서 `@Transactional` 메서드를 `this.xxx()`로 호출하면 Spring AOP 프록시를 우회해 트랜잭션 경계가 적용되지 않는다 (self-invocation 문제). 별도 협력 빈으로 쪼개는 대신, **`TransactionTemplate`을 이용한 프로그래밍 방식 트랜잭션**을 채택해 이 문제를 원천적으로 피한다.
- `configuration` 패키지에 `TransactionTemplate` 빈을 등록한다 (Spring Boot가 `PlatformTransactionManager`는 자동 구성하지만 `TransactionTemplate`은 자동 구성하지 않음):
  ```kotlin
  // configuration/TransactionConfiguration.kt
  @Configuration
  class TransactionConfiguration {
      @Bean
      fun transactionTemplate(transactionManager: PlatformTransactionManager): TransactionTemplate =
          TransactionTemplate(transactionManager)
  }
  ```
- `ReservationService.book(command)`는 `@Transactional`을 달지 않은 일반 메서드로 두고, 내부에서 `transactionTemplate.execute { ... }`를 두 단계(성공 시도 / 실패 기록)로 순차 호출한다. 두 호출은 서로 중첩되지 않으므로 `REQUIRES_NEW` propagation 설정 없이 기본 동작만으로 충분하다.

### 3. 처리 흐름 (`ReservationService.book`)

```
1. requestKey = buildBookRequestKey(command)
2. reservationRequestRepository.findByRequestKey(requestKey) 존재하면 → 그 결과의 toDomain()을 그대로 반환 (재처리 없음, 여기서 끝)
3. transactionTemplate.execute { // 트랜잭션 A: "성공 시도"
     reservation = Reservation.createNew(platformId, platformReservationRef, roomCode, dateRange, now).toEntity()
     saved = reservationRepository.saveAndFlush(reservation)   // 겹치면 여기서 DataIntegrityViolationException
     request = ReservationRequest(..., reservationId = saved.id, resultStatus = SUCCESS, rejectReason = null, ...)
     savedRequest = reservationRequestRepository.saveAndFlush(request.toEntity())
     outboundNotificationRepository.saveAndFlush(RESERVATION_CONFIRMED 알림 생성)  // 같은 트랜잭션 — 상태 변경과 outbox가 원자적으로 커밋됨
     return savedRequest.toDomain()
   }
4. 3번에서 DataIntegrityViolationException 발생 시 → 트랜잭션 A는 이미 롤백됨. transactionTemplate.execute { // 트랜잭션 B: "충돌 기록"
     request = ReservationRequest(..., reservationId = null, resultStatus = CONFLICT, rejectReason = "DUPLICATE_BOOKING", ...)
     try {
       savedRequest = reservationRequestRepository.saveAndFlush(request.toEntity())
       return savedRequest.toDomain()
     } catch (uniqueViolation: DataIntegrityViolationException) {
       // 동일 request_key로 진짜 동시에 두 요청이 findByRequestKey를 함께 통과한 극단적 레이스.
       // 이미 다른 스레드가 uq_request_key를 선점했다는 뜻이므로 재조회해서 그 결과를 반환한다 (신규 예외를 던지지 않음).
       val existing = checkNotNull(reservationRequestRepository.findByRequestKey(requestKey)) {
         "uq_request_key 위반이면 동일 requestKey row가 반드시 존재해야 함"
       }
       return existing.toDomain()
     }
   }
```

- 4번의 "재조회 후 반환" 분기는 `uq_request_key` UNIQUE 제약을 최후의 동시성 방어선으로 신뢰하는 것이지, `excl_room_date_overlap`처럼 매 요청마다 기대되는 정상 경로는 아니다 — 발생 빈도는 낮지만 무시하면 예외가 그대로 호출자에게 전파되므로 반드시 처리한다.

### 4. `outbound_notifications` — 리젝트(CONFLICT) 케이스는 이번 티켓에서 발행하지 않는다 (핵심 결정 사항)

이슈 본문은 "처리 결과(확정 RESERVATION_CONFIRMED **또는 거부 RESERVATION_REJECTED**)를 outbound_notifications에 append"라고 적어, 마치 CONFLICT 케이스도 통보 대상인 것처럼 보인다. 하지만 실제 병합된 스키마(`docs/schema/reservation_server_schema.sql:126`)는

```sql
reservation_id  BIGINT NOT NULL REFERENCES reservations(id),
```

로 **`outbound_notifications.reservation_id`가 NOT NULL FK**다. 이 티켓의 CONFLICT 설계(겹침 → insert 자체가 실패 → 예약 row가 아예 생성되지 않음)에서는 리젝트된 요청에 연결할 `reservation_id`가 존재하지 않으므로, 스키마를 어기지 않고서는 `RESERVATION_REJECTED` 알림을 넣을 수 없다.

- **채택**: 이번 티켓은 `RESERVATION_CONFIRMED` 성공 케이스에서만 `outbound_notifications`를 append한다. 이슈의 테스트 계획 문구("outbound_notifications에 이벤트가 **정확히 1건** append 되는지 검증")도 겹치는 두 동시 요청 중 성공한 한 건만 알림을 남긴다는 이 해석과 일치한다.
- **대안(이번 티켓 범위 밖으로 명시)**: 기획문서 4.1의 "나중에 도착한 요청을 자동으로 취소 처리하고, 해당 채널에는 '중복예약으로 인한 취소' 사유로 통보한다"를 문자 그대로 구현하려면, 리젝트된 요청에 대해 `CANCELLED` 상태의 예약 row를 별도로 생성해(이 상태는 `excl_room_date_overlap` 제약의 `WHERE` 절 대상이 아니므로 겹쳐도 insert 가능) `reservation_id`를 확보한 뒤 `RESERVATION_REJECTED`를 append하는 방법이 있다. 이는 CANCEL 관련 로직과 맞닿아 있어 스코프가 커지므로, 필요하다면 별도 이슈로 분리해 이슈 작성자와 논의할 것을 권장한다.

### 5. `payload` 직렬화

`OutboundNotification.payload`는 `String`(JSON 텍스트)이다. 새 의존성 없이 자동 구성된 Jackson `ObjectMapper`를 `ReservationService`에 주입해 작은 payload 데이터 클래스(`service` 패키지 내부)를 직렬화한다.

```kotlin
// service 패키지 내부, 컨트롤러가 없으므로 별도 dto 패키지를 만들지 않음
private data class ReservationConfirmedPayload(
    val reservationNo: String,
    val platformId: String,
    val roomCode: String,
    val startDate: LocalDate,
    val endDate: LocalDate,
)
```

`notification_key`는 스키마 주석 포맷(`reservation_no + ':' + event_type`)을 따른다: `"${saved.reservationNo}:RESERVATION_CONFIRMED"`.

## Testing Plan

모든 테스트는 Kotest `FeatureSpec`. 서비스 테스트는 `@DataJpaTest` 슬라이스가 아니라 `@SpringBootTest`가 필요하므로(트랜잭션 매니저·전체 빈 그래프 필요), 기존 `PostgresIntegrationTest`(공용 Testcontainer 베이스, `persistent` 패키지에 이미 존재)를 그대로 상속하되 `@SpringBootTest`로 감싼 새 테스트 클래스를 `service` 패키지 밑에 만든다.

- **`buildBookRequestKey` 단위 테스트** (Spring 컨텍스트 불필요): `platformId:roomCode:startDate:endDate:BOOK` 포맷 검증.
- **`ReservationServiceTest`** (`@SpringBootTest`, `PostgresIntegrationTest` 상속):
  - 신규 BOOK 성공: `reservations`에 `CONFIRMED` 1건, `reservation_requests`에 `SUCCESS` 1건(`reservationId` 채워짐), `outbound_notifications`에 `RESERVATION_CONFIRMED`/`PENDING` 1건 저장 검증.
  - 동일 커맨드(같은 `platformId`+`roomCode`+날짜) 재요청 시: 반환값이 첫 호출과 동일한 `ReservationRequest`이고, `reservations`/`reservation_requests`/`outbound_notifications` 각 테이블의 row 수가 늘지 않는지(멱등) 검증.
  - 겹치는 날짜·같은 `room_code`로 두 개의 서로 다른 BOOK 커맨드(`platformReservationRef` 다름)를 `ExecutorService` + `CountDownLatch`로 동시에 `book()` 호출 → 정확히 하나만 `resultStatus=SUCCESS`(그 `reservationId`로 `reservations` row 1건 존재), 나머지 하나는 `resultStatus=CONFLICT`이고 `rejectReason=DUPLICATE_BOOKING`, `reservationId=null` 검증. `outbound_notifications`는 정확히 1건만 존재하는지 검증 (4번 결정 사항의 근거 재확인).
  - `initiatedBy = RequestInitiator.HOST`로 호출 시 예외(`IllegalArgumentException`) 발생 검증.
- CI/로컬 실행 전제: Docker 데몬 필요(Testcontainers) — plan/13.md와 동일.

# 18 [예약] Outbound notification 발신 워커 - operation 서버로 재시도/폴링 전송

## Requirements

- `outbound_notifications`에서 `PENDING`/`FAILED` 상태이면서 `next_retry_at <= now()`인 건을 폴링해 operation 서버로 실제 HTTP 통보를 발송한다.
- 발송 시 `notification_key`를 그대로 전달해 operation 서버가 동일 값으로 수신 멱등성을 보장하도록 한다.
- 성공 시 `status=SENT`, 실패 시 `retry_count` 증가 + `next_retry_at` 갱신(백오프), 일정 횟수 초과 시 `DEAD`.
- 여러 워커 인스턴스가 동시 실행돼도 중복 발송되지 않도록 스키마 주석의 `FOR UPDATE SKIP LOCKED` 폴링 쿼리 패턴을 그대로 따른다.
- `controller`는 이번 티켓 범위 밖 (이 워커는 스케줄러가 트리거하며, 외부에서 호출하는 REST 엔드포인트가 아니다).

## Technical Approach

### 0. 실제 병합된 코드 기준 확인 — 그리고 "받는 쪽"이 아직 없다는 중요한 사실

`git pull` 후 `outbound_notifications` 관련 실제 코드(`persistent/OutboundNotificationEntity.kt`, `OutboundNotificationRepository.kt`)와 기존 HTTP 클라이언트 설정(`configuration/RestClientConfiguration.kt`, `OperationClientProperties.kt`)을 직접 읽었다.

- **`operation` 모듈은 아직 완전히 비어있다** (`gh issue list`로 확인: #19 "Operation 서버 MySQL 전환"과 #20 "Inbound event 수신 API"가 모두 `OPEN`, 미착수). `operation/.../controller`, `persistent`, `domain`, `service` 패키지는 전부 `.gitkeep`뿐이다. 즉 **이 워커가 실제로 호출할 HTTP 엔드포인트가 지금 존재하지 않는다.** 이 플랜은 `docs/schema/operation_server_schema.sql`의 `inbound_events` 테이블 구조(`notification_key`, `reservation_no`, `event_type`, `payload`)에 맞춰 요청 계약(request contract)을 **이 티켓에서 직접 제안**하고, #20 구현 시 이 계약과 실제로 맞춰야 한다는 점을 리스크로 남긴다 (아래 4번).
- **`OutboundNotificationEntity`의 `status`/`retryCount`/`nextRetryAt`가 전부 `val`이다.** `ReservationEntity.status`(#13)와 `dateRange`(#17)가 같은 이유로 `var`가 된 전례를 그대로 따라, 이 세 필드도 `var`로 바꿔야 워커가 상태를 갱신할 수 있다. **이 변경 없이는 이 티켓을 구현할 수 없다** — plan/17.md의 "선행 코드 수정" 섹션과 동일한 성격의 막힌 지점.
- **`operationRestClient` 빈은 이미 있지만 타임아웃이 설정돼 있지 않다** (`RestClientConfiguration.kt`, `RestClient.Builder` 기본값 그대로). HTTP 호출이 걸리는 동안 이 티켓의 설계상 DB row lock(아래 2번)을 들고 있게 되므로, 타임아웃 미설정은 락을 무한정 붙들 위험으로 이어진다 — 이 티켓에서 반드시 함께 고친다.
- **`OutboundNotification` 도메인에는 `reservationNo` 필드가 없다** (`reservationId: Long`만 있음). operation 서버에 보낼 `reservation_no`(교차 시스템 식별자)를 얻으려면 `reservationRepository.findById(notification.reservationId)`로 조회해야 한다 — 이미 있는 `JpaRepository.findById` 기본 메서드로 충분하다 (새 조회 메서드 불필요).

### 1. `OutboundNotificationRepository`에 SKIP LOCKED 폴링 쿼리 추가

Spring Data JPA의 파생 쿼리 메서드로는 `FOR UPDATE SKIP LOCKED`를 표현할 수 없다. 스키마 주석이 제시한 예시 쿼리를 그대로 네이티브 쿼리로 옮긴다 (Hibernate의 락 힌트 기반 트릭보다 스키마 문서와 1:1 대응되는 이 방식이 안전하다):

```kotlin
@Query(
    value = """
        SELECT * FROM outbound_notifications
        WHERE status IN ('PENDING', 'FAILED') AND next_retry_at <= :now
        ORDER BY created_at
        LIMIT :limit
        FOR UPDATE SKIP LOCKED
    """,
    nativeQuery = true,
)
fun findBatchForDispatch(now: OffsetDateTime, limit: Int): List<OutboundNotificationEntity>
```

이 락은 **트랜잭션이 끝나야 풀린다** — 반드시 활성 트랜잭션 안에서만 호출돼야 한다 (2번 참고).

### 2. 폴링 워커 — 배치 단위 트랜잭션, `SKIP LOCKED`로 워커 간 배타성 확보

`SELECT ... FOR UPDATE SKIP LOCKED`로 얻은 락은 해당 트랜잭션이 커밋될 때까지 유지돼야 "조회~처리~상태갱신" 사이의 틈에 다른 워커가 같은 row를 다시 집어가는 걸 막을 수 있다. 따라서 "배치 조회 + 각 건 발송 + 상태 갱신"을 **하나의 트랜잭션**(하나의 `transactionTemplate.execute` 블록)으로 묶는다. 배치 크기를 적당히 작게(예: 20건, 설정 가능) 유지해 트랜잭션 보유 시간을 제한한다 — 다른 워커는 이 배치가 잠근 row들을 `SKIP LOCKED`로 건너뛰고 남은 row를 처리하므로 블로킹되지 않는다.

```kotlin
// service/OutboundNotificationDispatchWorker.kt
@Service
class OutboundNotificationDispatchWorker(
    private val outboundNotificationRepository: OutboundNotificationRepository,
    private val reservationRepository: ReservationRepository,
    private val transactionTemplate: TransactionTemplate,
    private val operationRestClient: RestClient,
    private val properties: OutboundNotificationDispatchProperties,
) {
    @Scheduled(fixedDelayString = "\${outbound-notification.poll-interval-millis}")
    fun dispatchPendingNotifications() {
        transactionTemplate.execute {
            val batch = outboundNotificationRepository.findBatchForDispatch(OffsetDateTime.now(), properties.batchSize)
            batch.forEach { notification -> dispatchOne(notification) }
        }
    }

    private fun dispatchOne(notification: OutboundNotificationEntity) {
        try {
            val reservationNo = checkNotNull(
                reservationRepository.findById(notification.reservationId).orElseThrow().reservationNo,
            ) { "저장된 예약은 reservation_no를 가지고 있어야 합니다" }

            operationRestClient.post()
                .uri("/api/inbound-events")
                .contentType(MediaType.APPLICATION_JSON)
                .body(InboundEventRequest(notification.notificationKey, reservationNo, notification.eventType, notification.payload))
                .retrieve()
                .toBodilessEntity()

            notification.status = OutboundNotificationStatus.SENT
        } catch (deliveryFailure: RestClientException) {
            // 4xx/5xx/timeout/커넥션 실패를 전부 "발송 실패"로 취급 (이슈 테스트 계획이 셋을 같은 범주로 다룸)
            notification.retryCount += 1
            notification.status =
                if (notification.retryCount >= properties.maxRetryCount) OutboundNotificationStatus.DEAD
                else OutboundNotificationStatus.FAILED
            notification.nextRetryAt = computeNextRetryAt(notification.retryCount, properties)
        }
        outboundNotificationRepository.saveAndFlush(notification)   // 같은 트랜잭션 — 상태 갱신과 락 해제(커밋)가 함께 일어남
    }
}
```

- 한 건의 발송 실패가 배치의 나머지 건 처리를 막지 않도록 `dispatchOne` 내부에서 예외를 잡고 다음 건으로 넘어간다 (배치 전체가 롤백되지 않게).
- 지수 백오프: `nextRetryAt = now + min(maxBackoffSeconds, initialBackoffSeconds * 2^(retryCount-1))`. 초기값/최대값/`maxRetryCount`/배치 크기/폴링 주기는 전부 설정으로 뺀다 (`OperationClientProperties`와 같은 패턴):
  ```kotlin
  // configuration/OutboundNotificationDispatchProperties.kt
  @ConfigurationProperties(prefix = "outbound-notification")
  data class OutboundNotificationDispatchProperties(
      val batchSize: Int = 20,
      val maxRetryCount: Int = 5,
      val initialBackoffSeconds: Long = 30,
      val maxBackoffSeconds: Long = 1800,
      val pollIntervalMillis: Long = 5000,
  )
  ```
- `@EnableScheduling`이 아직 어디에도 없다 — `configuration/SchedulingConfiguration.kt`를 새로 추가한다 (기존 `RestClientConfiguration`/`TransactionConfiguration`과 같은 "단일 목적 `@Configuration` 클래스" 패턴 유지).

### 3. `operationRestClient`에 타임아웃 추가 (기존 `RestClientConfiguration.kt` 수정)

락을 들고 있는 동안 HTTP 호출이 무한정 걸리지 않도록 connect/read 타임아웃을 명시적으로 설정한다 (예: connect 2초 / read 5초, 설정 가능하게). Spring Boot 3.5의 `ClientHttpRequestFactorySettings`/`ClientHttpRequestFactoryBuilder`로 구성하고, `restClientBuilder.requestFactory(...)`에 적용한다. 정확한 빌더 API 표면은 구현 시점에 Spring Boot 3.5.14 문서로 재확인한다 (버전마다 세부 API가 바뀐 이력이 있는 영역).

### 4. HTTP 요청 계약 — **이 티켓이 처음 정의하는 것이며, #20과 조율이 필요한 리스크**

`docs/schema/operation_server_schema.sql`의 `inbound_events` 테이블 컬럼(`notification_key`, `reservation_no`, `event_type`, `payload`)에 1:1 대응시켜 제안한다:

```kotlin
// service/InboundEventRequest.kt
data class InboundEventRequest(
    val notificationKey: String,
    val reservationNo: String,
    val eventType: String,
    @get:JsonRawValue
    val payload: String,
)
```

`payload`는 `OutboundNotification.payload`(이미 직렬화된 JSON 문자열)를 **그대로 중첩 JSON으로** 실어 보내야 한다 — `@get:JsonRawValue`(Jackson) 없이 평범한 `String` 필드로 두면 이중 이스케이프된 문자열 값으로 나가버려 operation 서버가 파싱하기 훨씬 번거로워진다.

- 엔드포인트는 `POST /api/inbound-events`로 가정한다 (스키마의 `inbound_events` 테이블명을 그대로 리소스 경로화). **이 경로/요청 바디 형태는 #20(Inbound event 수신 API) 구현 시 실제로 맞춰봐야 하는 가정**이다 — #20을 플래닝/구현할 때 이 파일(`plan/18.md`)의 계약을 참고하도록 이슈에 코멘트로 남기거나, #20 플랜 작성 시 이 문서를 명시적으로 참조할 것을 권장한다.
- 응답 바디는 사용하지 않는다(`toBodilessEntity()`) — 성공 판정은 순수하게 HTTP 상태 코드(2xx)로만 한다. operation 서버가 이미 처리한 `notification_key`를 다시 받아도(재시도) 자기 쪽에서 멱등하게 처리하고 2xx를 반환해야 한다는 전제이며, 이는 #20의 요구사항이다.

## Testing Plan

`operation` 서버가 아직 없으므로 실제 서버 대신 **`MockRestServiceServer`**(Spring Framework 6.1+/Boot 3.2+, `spring-boot-starter-test`에 이미 포함 — 새 의존성 불필요)를 `operationRestClient`의 `RestClient.Builder`에 bind해서 검증한다.

- **정상 발송**: `PENDING` 알림 1건 픽스처 생성 → `MockRestServiceServer`가 `POST /api/inbound-events`에 200 응답 등록 → `dispatchPendingNotifications()` 호출 → `status=SENT` 전이 검증. 요청 바디의 `notificationKey`/`reservationNo`/`eventType`이 정확한지, `payload`가 이중 인코딩 없이 원본 JSON 그대로 실렸는지 `jsonPath`로 검증 (`@JsonRawValue` 효과 확인).
- **4xx/5xx/타임아웃 시 재시도 갱신**: 각각 500, 400, (커넥션 강제 실패) 응답을 등록 → `retry_count` 1 증가, `status=FAILED`, `next_retry_at`이 미래로 갱신(백오프 공식대로)됐는지 검증. 세 실패 유형이 동일한 코드 경로(`RestClientException`)로 처리되는지 확인.
- **`maxRetryCount` 초과 시 DEAD 전이**: `retryCount = maxRetryCount - 1`인 픽스처에 실패 응답 → 이번 실패로 `retryCount = maxRetryCount`가 되며 `status=DEAD`로 전이하는지 검증. 이후 재폴링 쿼리(`findBatchForDispatch`)에 이 row가 더 이상 걸리지 않는지도 함께 검증.
- **`next_retry_at`이 미래인 `FAILED` 건은 이번 폴링에서 제외**: `next_retry_at`을 미래로 설정한 `FAILED` 픽스처 → `findBatchForDispatch`가 이 row를 반환하지 않는지 검증.
- **동시 워커 시뮬레이션 (`SKIP LOCKED`)**: `OutboundNotificationRepositoryTest`(또는 새 테스트)에서, 여러 건의 `PENDING` 알림을 만들어두고 `CountDownLatch`로 동기화한 두 스레드가 각자 별도 트랜잭션 안에서 `findBatchForDispatch(...)`를 동시에 호출 → 두 스레드가 반환한 row ID 집합에 **교집합이 없는지**(같은 row를 두 번 집어가지 않음) 검증 (#14의 `ExecutorService`+`CountDownLatch` 동시성 테스트 패턴 재사용).
- **`InboundEventRequest` 직렬화 단위 테스트** (Spring 컨텍스트 불필요): `ObjectMapper`로 직접 직렬화해 `payload` 필드가 중첩 JSON 객체로(문자열이 아니라) 나오는지 검증.
- CI/로컬 실행 전제: Docker 데몬 필요(Testcontainers, DB 관련 테스트) — #13~#17과 동일. HTTP 관련 테스트는 `MockRestServiceServer`만 사용하므로 별도 인프라 불필요.

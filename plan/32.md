# 32 [예약] BOOK 중복예약 거부 시 RESERVATION_REJECTED 통보가 발행되지 않음

## Requirements

- BOOK이 `excl_room_date_overlap` 위반으로 거부될 때도, 패자 채널에 `RESERVATION_REJECTED` 통보를 `outbound_notifications`에 남긴다 (기획문서 §4.1).
- 통보 payload는 예약 row 없이도 구성 가능해야 한다 — `platformId`/`platformReservationRef`/`roomCode`/날짜/거부사유 등 `BookReservationCommand`에 이미 있는 정보로만 구성한다.

## Technical Approach

### 0. 실제 병합된 코드 기준 확인 — 그리고 갭이 생긴 정확한 지점

`git pull` 후(main은 #13~#21, #35까지 병합돼 깨끗함) `ReservationService.recordConflict()`(BOOK), `OutboundNotificationDispatchWorker`, `OutboundNotification`/`OutboundNotificationEntity`, `docs/schema/reservation_server_schema.sql`, 그리고 operation의 `InboundEventService`(#20)를 직접 다시 읽었다.

- **`recordConflict()`의 현재 실제 코드**: `reservation_requests`에 `CONFLICT`/`DUPLICATE_BOOKING_REJECT_REASON`만 저장하고 끝난다 — `outbound_notifications` insert가 아예 없다. `plan/14.md`가 이 갭을 의도적으로 남긴 이유(`outbound_notifications.reservation_id BIGINT NOT NULL REFERENCES reservations(id)` — 거부된 BOOK은 예약 row가 없어 참조할 대상이 없음)를 이슈가 정확히 지적하고 있다.
- **CHANGE의 `recordChangeRejected()`는 이미 `RESERVATION_REJECTED`를 정상 발행하고 있다** (원본 예약 row가 살아있어 `reservation_id`를 채울 수 있었기 때문 — plan/17.md 4번 참고). `RESERVATION_REJECTED_EVENT_TYPE` 상수도 이미 `ReservationService.kt`에 정의돼 있다 — **새로 만들 필요 없이 재사용**한다.
- **`OutboundNotificationDispatchWorker.dispatchOne()`은 항상 `reservationRepository.findById(notification.reservationId).orElseThrow()`로 `reservationNo`를 얻는다** — `reservationId`가 nullable이 되면 이 경로가 깨진다. 이슈가 제안한 "null이면 스킵" 분기가 필요하지만, 스킵한 뒤 `reservationNo`를 어디서 얻을지가 관건이다 (1번 참고).
- **operation 쪽은 변경이 필요 없다.** `InboundEventService.kt`(#20)의 `KNOWN_EVENT_TYPES`에 `"RESERVATION_REJECTED"`가 이미 포함돼 있고, `inbound_events`/`outbox_events` 어디에도 예약 서버의 `reservation_id`(내부 PK)를 참조하는 FK가 없다(전부 `reservation_no`를 문자열로만 보관, 교차 DB) — operation은 이미 이 이벤트 타입을 완전히 지원한다.
- **주의**: 지금 워킹 트리에는 `OutboundNotificationDispatchWorker.kt`에 대한 **커밋되지 않은 변경**이 하나 있다 — 별개 이슈 `#34`("예외 처리 범위가 좁아 배치 전체 롤백 위험")를 고치는 중으로 보인다(`catch (RestClientException)` → `catch (Exception)`으로 넓히는 변경, HTTP 호출 이전 단계의 예외도 같은 배치의 다른 건을 롤백시키지 않도록). **이 티켓도 같은 파일의 같은 메서드(`dispatchOne`)를 건드리므로, 구현 시작 전에 `#34`의 실제 병합 상태를 확인하고 그 위에 이어 붙여야 한다** (머지 충돌 가능성을 미리 인지).

### 1. `reservationNo`는 DB 조회 없이 계산할 수 있다 — 이게 이 티켓의 핵심 트릭

`reservations.reservation_no`는 `platform_id || ':' || platform_reservation_ref`로 생성되는 컬럼이다(V1 마이그레이션 확인). 거부된 BOOK은 이 두 값을 **커맨드에 이미 갖고 있으므로**, DB에 저장된 적 없는 예약이라도 그 예약이 저장됐더라면 가졌을 `reservation_no`와 동일한 문자열을 애플리케이션에서 그대로 계산할 수 있다:

```kotlin
val reservationNo = "${command.platformId}:${command.platformReservationRef}"
```

이 값을 **payload 안에 담아서** 발행한다(다른 3개 액션의 `*Payload` data class가 전부 `reservationNo`를 필드로 갖고 있는 것과 동일한 패턴). 그러면 `OutboundNotificationDispatchWorker`가 `reservationId == null`일 때 DB 조회 대신 **payload에서 `reservationNo`를 읽으면 된다** — 이슈가 제안한 "Flyway로 nullable 전환"과 자연스럽게 맞물리는 설계다.

### 2. 스키마 변경 — Flyway 마이그레이션과 **소스 오브 트루스 문서를 함께** 갱신한다

이슈 본문은 Flyway 마이그레이션만 언급하지만, `CLAUDE.md`는 `docs/schema/reservation_server_schema.sql`을 도메인 소스 오브 트루스로 명시하고 있다 — 실제 DB만 바꾸고 이 문서를 그대로 두면 문서와 실제 스키마가 어긋난다. **둘 다 고친다:**

- `docs/schema/reservation_server_schema.sql`: `outbound_notifications.reservation_id` 정의에서 `NOT NULL` 제거.
  ```sql
  reservation_id                 BIGINT REFERENCES reservations(id),
  ```
- 신규 Flyway 파일: `reservation/src/main/resources/db/migration/V2__outbound_notifications_reservation_id_nullable.sql` (현재 `V1`만 있으므로 다음 버전):
  ```sql
  ALTER TABLE outbound_notifications ALTER COLUMN reservation_id DROP NOT NULL;
  ```
  FK 제약(`REFERENCES reservations(id)`)과 인덱스는 그대로 둔다 — nullable FK는 Postgres에서 정상 동작(NULL은 FK 검사 대상이 아님).

### 3. 도메인/persistent 타입 변경

- `domain/OutboundNotification.kt`: `val reservationId: Long` → `val reservationId: Long?`.
- `persistent/OutboundNotificationEntity.kt`: `@Column(name = "reservation_id") val reservationId: Long` → `Long?`. `toDomain()`/`toEntity()`는 타입만 따라가면 되고 로직 변경 없음.
- 기존 호출부(BOOK 성공, CANCEL_CONFIRM, CANCEL_REQUEST, CHANGE 성공/거부 알림 생성 코드)는 전부 non-null `Long`을 넘기고 있어 Kotlin이 `Long?` 파라미터에 그대로 대입 가능 — **수정 불필요**.

### 4. `recordConflict()` — 같은 트랜잭션에 `outbound_notifications` insert 추가

```kotlin
private fun recordConflict(
    command: BookReservationCommand,
    requestKey: String,
): ReservationRequest =
    try {
        checkNotNull(
            transactionTemplate.execute {
                val now = OffsetDateTime.now()
                val savedRequest =
                    reservationRequestRepository.saveAndFlush(
                        ReservationRequest(
                            id = null,
                            requestKey = requestKey,
                            reservationId = null,
                            platformId = command.platformId,
                            action = ReservationRequestAction.BOOK,
                            initiatedBy = command.initiatedBy,
                            roomCode = command.roomCode,
                            oldDateRange = null,
                            newDateRange = command.dateRange,
                            resultStatus = RequestResultStatus.CONFLICT,
                            rejectReason = DUPLICATE_BOOKING_REJECT_REASON,
                            requestedAt = now,
                        ).toEntity(),
                    )

                outboundNotificationRepository.saveAndFlush(
                    rejectedNotificationEntity(command, savedRequest.id, now),
                )

                savedRequest.toDomain()
            },
        ) { "충돌 기록 트랜잭션은 항상 값을 반환해야 합니다" }
    } catch (duplicateRequestKey: DataIntegrityViolationException) {
        // 기존 로직 그대로 — uq_request_key 위반 시 재조회
        checkNotNull(reservationRequestRepository.findByRequestKey(requestKey)) {
            "uq_request_key 위반이면 동일 requestKey row가 반드시 존재해야 합니다"
        }.toDomain()
    }

private fun rejectedNotificationEntity(
    command: BookReservationCommand,
    requestId: Long,
    now: OffsetDateTime,
): OutboundNotificationEntity {
    val reservationNo = "${command.platformId}:${command.platformReservationRef}"
    val payload =
        ReservationRejectedPayload(
            reservationNo = reservationNo,
            platformId = command.platformId,
            roomCode = command.roomCode,
            startDate = command.dateRange.startDate,
            endDate = command.dateRange.endDate,
            rejectReason = DUPLICATE_BOOKING_REJECT_REASON,
        )

    // CHANGE의 거부 알림과 같은 이유로 requestId를 키에 포함한다. BOOK의 request_key가 이미
    // platformReservationRef를 포함하므로(#14) 이론적으로는 reservationNo만으로도 유일하지만,
    // 그 전제에 기대지 않고 CHANGE와 동일하게 안전한 패턴을 그대로 따른다.
    return OutboundNotification(
        id = null,
        notificationKey = "$reservationNo:$RESERVATION_REJECTED_EVENT_TYPE:$requestId",
        reservationId = null,
        requestId = requestId,
        eventType = RESERVATION_REJECTED_EVENT_TYPE,
        payload = objectMapper.writeValueAsString(payload),
        status = OutboundNotificationStatus.PENDING,
        retryCount = 0,
        nextRetryAt = now,
        createdAt = now,
        updatedAt = now,
    ).toEntity()
}
```

`ReservationRejectedPayload`는 다른 `*Payload` data class들과 나란히 파일 상단에 추가한다:

```kotlin
private data class ReservationRejectedPayload(
    val reservationNo: String,
    val platformId: String,
    val roomCode: String,
    val startDate: LocalDate,
    val endDate: LocalDate,
    val rejectReason: String,
)
```

### 5. `OutboundNotificationDispatchWorker` — `reservationId == null`이면 payload에서 `reservationNo`를 읽는다

`ObjectMapper`를 새로 주입받아야 한다(현재 생성자에 없음 — reservation 쪽 `ReservationService`는 이미 갖고 있지만 이 워커는 지금까지 필요 없었다).

```kotlin
class OutboundNotificationDispatchWorker(
    private val outboundNotificationRepository: OutboundNotificationRepository,
    private val reservationRepository: ReservationRepository,
    private val transactionTemplate: TransactionTemplate,
    private val operationRestClient: RestClient,
    private val properties: OutboundNotificationDispatchProperties,
    private val objectMapper: ObjectMapper,   // 신규
) {
    private fun resolveReservationNo(notification: OutboundNotificationEntity): String {
        val reservationId = notification.reservationId
        return if (reservationId != null) {
            requireNotNull(reservationRepository.findById(reservationId).orElseThrow().reservationNo) {
                "저장된 예약은 reservation_no를 가지고 있어야 합니다"
            }
        } else {
            val payloadNode = objectMapper.readTree(notification.payload)
            requireNotNull(payloadNode.get("reservationNo")?.asText()) {
                "reservationId가 없는 알림은 payload에 reservationNo가 있어야 합니다: notificationKey=${notification.notificationKey}"
            }
        }
    }
}
```

`dispatchOne()`의 `val reservationNo = requireNotNull(reservationRepository.findById(notification.reservationId)...)` 줄을 `val reservationNo = resolveReservationNo(notification)`으로 교체한다. `#34`가 이 메서드의 예외 처리 범위를 넓히는 작업을 병행 중이므로(0번 참고), `resolveReservationNo`가 던질 수 있는 예외(`IllegalArgumentException`/JSON 파싱 실패)도 그 넓어진 catch 절 안에 자연스럽게 들어가는지 구현 시점에 다시 확인한다.

- **`OutboundNotification`/`OutboundNotificationEntity` 매퍼 단위 테스트**: `reservationId = null`인 인스턴스의 `toDomain()`/`toEntity()` 왕복 검증 (기존 non-null 케이스에 추가).

- **`ReservationServiceTest`의 "동시 겹침 요청" 시나리오 확장** (이슈가 명시한 기존 테스트): 현재 `successCount`/`conflictCount` 검증에 더해, `CONFLICT` 결과의 `outbound_notifications`도 검증 추가 — `outboundNotificationRepository.findAll().count { it.requestId == conflictOutcome.id }`가 정확히 1건이고, `eventType = "RESERVATION_REJECTED"`, `reservationId = null`, payload의 `reservationNo`가 거부된 요청의 `platformId:platformReservationRef`와 일치하는지 확인.
- **`OutboundNotificationDispatchWorkerTest`에 케이스 추가** (이슈가 명시): `reservationId = null`이고 payload에 `reservationNo`가 담긴 알림을 직접 픽스처로 만들어 `dispatchPendingNotifications()` 호출 → `reservationRepository.findById`를 호출하지 않고도(즉, 존재하지 않는 어떤 예약도 조회 시도 없이) 발송에 성공해 `SENT`로 전이하는지, 요청 바디의 `reservationNo`가 payload에서 읽은 값과 일치하는지 검증.
- CI/로컬 실행 전제: Docker 데몬 필요(Testcontainers) — 기존과 동일.

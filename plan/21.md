# 21 [운영] Outbox 발송 워커 - OTA/호스트 대상 통보 재시도/폴링

## Requirements

- `outbox_events`에서 `PENDING`/`FAILED` 상태이면서 `next_retry_at <= now()`인 건을 폴링해 실제 OTA/호스트 채널로 발송한다.
- 대상이 `OTA_CHANNEL`이면 `ota_channels.callback_base_url`, `HOST`면 호스트 알림 채널로 전달한다.
- `outbox_key`를 그대로 외부에 전달해 외부 시스템의 중복수신 방어를 지원한다.
- 성공 시 `SENT`, 실패 시 `retry_count` 증가 + `next_retry_at` 갱신(backoff), 임계치 초과 시 `DEAD`.
- 여러 워커 인스턴스가 동시 실행돼도 중복 발송되지 않도록 `FOR UPDATE SKIP LOCKED` 패턴을 쓴다.
- 실제 OTA 연동이 없는 현재 단계에서는 외부 호출을 로깅/스텁으로 시작해도 되지만, **재시도/상태 전이 로직 자체는 실제로 동작해야 한다** (이슈 본문이 명시한 이 프로젝트의 목적).

## Technical Approach

### 0. 실제 코드 기준 확인 — #19는 도메인/persistent까지 진행 중(WIP), #20은 아직 없음

`git pull` 후 `operation` 모듈을 직접 확인했다. **#19가 커밋되지는 않았지만 도메인/persistent 파일은 이미 디스크에 존재해서 plan/19.md의 제안이 아니라 실제 코드를 읽고 반영했다** (단, 여전히 커밋 전이라 최종적으로 다를 수 있음 — #21 구현 시작 전 재확인 필요):

- `persistent/OutboxEventEntity.kt`, `OutboxEventRepository.kt`(`findByOutboxKey`만 있음), `persistent/OtaChannelEntity.kt`(`callbackBaseUrl: String?`, nullable), `OtaChannelRepository.kt`(**커스텀 조회 메서드 없음, `JpaRepository`만**), `persistent/HostEntity.kt`(`hostCode`/`name`/`contactEmail`/`contactPhone`/`status`만 — **콜백 URL/웹훅 같은 API 채널 필드가 아예 없다**), `HostRepository.kt`(역시 커스텀 메서드 없음).
- `createdAt`/`updatedAt`은 plan/19.md의 결정대로 이미 `@Generated`(DB 관리)로 매핑돼 있다.
- **`OutboxEventEntity.status`/`retryCount`/`nextRetryAt`가 전부 `val`이다.** reservation의 `OutboundNotificationEntity`가 #13에서 `val`로 시작했다가 #18(발송 워커)에서 `var`로 바꿔야 했던 것과 정확히 같은 상황 — **이 티켓에서 세 필드를 `var`로 바꿔야 한다.** (#19는 "엔티티/리포지토리까지"가 스코프라 워커가 필요로 하는 가변성까지 미리 준비해두지 않은 것이 자연스러움 — reservation 쪽과 동일한 패턴이 반복됨.)
- `operation/.../configuration`, `controller`, `service` 패키지는 전부 `.gitkeep`뿐이다 — **#20(수신 API)도 아직 시작 전**이다. 즉 `TransactionConfiguration`(TransactionTemplate 빈)도 아직 없다. plan/20.md가 이미 이 설정을 추가하도록 제안했으므로, **#20이 먼저 병합되면 그 빈을 재사용하고 중복 추가하지 않는다** — #21 구현 시작 시점에 존재 여부를 다시 확인한다.

### 1. `OutboxEventRepository`에 SKIP LOCKED 폴링 쿼리 추가

reservation `#18`(`OutboundNotificationRepository.findBatchForDispatch`)과 완전히 대칭. 스키마 주석의 예시 쿼리를 네이티브 쿼리로 그대로 옮긴다 (파라미터 타입만 `LocalDateTime`으로 다름 — operation은 `DATETIME`이라 `OffsetDateTime`을 쓰지 않는다는 plan/19.md의 결정과 일관):

```kotlin
@Query(
    value = """
        SELECT * FROM outbox_events
        WHERE status IN ('PENDING', 'FAILED') AND next_retry_at <= :now
        ORDER BY created_at
        LIMIT :limit
        FOR UPDATE SKIP LOCKED
    """,
    nativeQuery = true,
)
fun findBatchForDispatch(now: LocalDateTime, limit: Int): List<OutboxEventEntity>
```

### 2. 대상 조회 메서드 신규 추가 — `OtaChannelRepository`/`HostRepository`

`outbox_events.target_code`(`ota_channels.platform_id` 또는 `hosts.host_code`)로 실제 채널 정보를 찾아야 한다. reservation `#15`가 `findByPlatformIdAndPlatformReservationRef`를 "실제 필요해진 시점"에 추가했던 것과 같은 원칙으로, 이번 티켓에서 처음 추가한다:

```kotlin
interface OtaChannelRepository : JpaRepository<OtaChannelEntity, Long> {
    fun findByPlatformId(platformId: String): OtaChannelEntity?
}
interface HostRepository : JpaRepository<HostEntity, Long> {
    fun findByHostCode(hostCode: String): HostEntity?
}
```

### 3. 발송 워커 — reservation `#18`과 동일한 배치·트랜잭션·백오프 구조

`SELECT ... FOR UPDATE SKIP LOCKED`의 락이 트랜잭션 종료까지 유지돼야 하는 이유, 배치를 하나의 트랜잭션으로 묶는 이유, 한 건 실패가 배치 전체를 롤백시키지 않도록 개별 `try/catch`로 감싸는 이유 — 전부 `plan/18.md`/PR #27과 동일하다 (반복 설명 생략, 코드만 아래에).

```kotlin
// configuration/OutboxEventDispatchProperties.kt (OutboundNotificationDispatchProperties와 대칭)
@ConfigurationProperties(prefix = "outbox-event")
data class OutboxEventDispatchProperties(
    val batchSize: Int = 20,
    val maxRetryCount: Int = 5,
    val initialBackoffSeconds: Long = 30,
    val maxBackoffSeconds: Long = 1800,
    val pollIntervalMillis: Long = 5000,
)
```

```kotlin
// service/OutboxEventDispatchWorker.kt
@Service
class OutboxEventDispatchWorker(
    private val outboxEventRepository: OutboxEventRepository,
    private val otaChannelRepository: OtaChannelRepository,
    private val hostRepository: HostRepository,
    private val transactionTemplate: TransactionTemplate,
    private val channelDeliveryRestClient: RestClient,
    private val properties: OutboxEventDispatchProperties,
) {
    @Scheduled(fixedDelayString = "\${outbox-event.poll-interval-millis}")
    fun dispatchPendingOutboxEvents() {
        transactionTemplate.execute {
            outboxEventRepository
                .findBatchForDispatch(LocalDateTime.now(), properties.batchSize)
                .forEach { dispatchOne(it) }
        }
    }

    private fun dispatchOne(event: OutboxEventEntity) {
        try {
            val delivered =
                when (event.targetType) {
                    OutboxTargetType.OTA_CHANNEL -> deliverToOtaChannel(event)
                    OutboxTargetType.HOST -> deliverToHost(event)
                }
            check(delivered) { "채널 설정을 찾을 수 없어 전달하지 못했습니다: targetCode=${event.targetCode}" }
            event.status = OutboxEventStatus.SENT
        } catch (deliveryFailure: Exception) {
            // 실제 HTTP 실패(RestClientException)와 "채널/콜백 URL 설정 없음"(check 실패)을 같은 재시도
            // 경로로 합친다 — 둘 다 "지금은 전달 못 했다"는 점에서 동일하게 취급해도 무방하다 (5번 참고).
            event.retryCount += 1
            event.status = if (event.retryCount >= properties.maxRetryCount) OutboxEventStatus.DEAD else OutboxEventStatus.FAILED
            event.nextRetryAt = computeNextRetryAt(event.retryCount, properties)
        }
        outboxEventRepository.saveAndFlush(event)
    }

    private fun deliverToOtaChannel(event: OutboxEventEntity): Boolean {
        val channel = otaChannelRepository.findByPlatformId(event.targetCode) ?: return false
        val callbackBaseUrl = channel.callbackBaseUrl ?: return false

        channelDeliveryRestClient
            .post()
            .uri(callbackBaseUrl)   // 채널마다 URL이 다르므로 절대 URI를 그대로 지정한다 (4번 참고)
            .contentType(MediaType.APPLICATION_JSON)
            .body(ChannelNotificationRequest(event.outboxKey, event.reservationNo, event.eventType, event.payload))
            .retrieve()
            .toBodilessEntity()
        return true
    }

    private fun deliverToHost(event: OutboxEventEntity): Boolean {
        // hosts 테이블엔 API로 호출 가능한 채널이 없다(이메일/전화만) — 6번 결정 사항 참고.
        logger.info("[STUB] HOST 알림: outboxKey=${event.outboxKey}, targetCode=${event.targetCode}, eventType=${event.eventType}")
        return true
    }
}
```

```kotlin
// service/ChannelNotificationRequest.kt — reservation의 InboundEventRequest와 같은 이유로 payload를 raw로 보낸다
data class ChannelNotificationRequest(
    val outboxKey: String,
    val reservationNo: String,
    val eventType: String,
    @get:JsonRawValue val payload: String,
)
```

### 4. `RestClient` 빈 — reservation의 `RestClientConfiguration`과 다르게 **고정 `baseUrl`을 두지 않는다**

reservation `#18`의 `operationRestClient`는 상대 경로(`/api/inbound-events`)로 호출하는 **단일** 고정 서버(operation)를 향하므로 `baseUrl`을 빈에 미리 박아뒀다. 이번 워커는 `ota_channels.callback_base_url`이 **행마다 다른 절대 URL**이라 같은 패턴을 쓸 수 없다 — `baseUrl` 없이 타임아웃만 설정한 범용 `RestClient` 빈을 새로 만들고, 호출 시 `.uri(callbackBaseUrl)`에 절대 URL을 그대로 넘긴다.

```kotlin
// configuration/ChannelDeliveryClientConfiguration.kt
@Configuration
class ChannelDeliveryClientConfiguration {
    @Bean
    fun channelDeliveryRestClient(builder: RestClient.Builder): RestClient {
        val requestFactory =
            ClientHttpRequestFactoryBuilder.detect().build(
                ClientHttpRequestFactorySettings.defaults()
                    .withConnectTimeout(Duration.ofSeconds(2))
                    .withReadTimeout(Duration.ofSeconds(5)),
            )
        return builder.requestFactory(requestFactory).build()
    }
}
```

(정확한 Boot 3.5.14 빌더 API 표면은 `RestClientConfiguration.kt`(reservation, 이미 병합됨)를 그대로 참고하면 된다 — 이미 검증된 코드.)

`configuration/SchedulingConfiguration.kt`(`@EnableScheduling`)도 새로 추가한다 — operation 모듈엔 아직 스케줄러가 하나도 없다.

### 5. 실패 원인을 세분화하지 않는다 (결정 사항)

"채널/콜백 URL 설정 없음"(영구적일 가능성이 높음)과 "일시적 네트워크 실패"(재시도하면 나을 수 있음)를 구분해 다르게 처리하는 것도 고려했으나, 이번 티켓 스코프에서는 **구분하지 않는다** — 둘 다 같은 백오프·`maxRetryCount` 초과 시 `DEAD`행 흐름을 타게 한다. 설정 누락은 결국 `DEAD` 상태로 드러나 운영자가 알아챌 수 있고, 실시간으로 "이건 설정 문제니까 즉시 DEAD" 같은 특수 분기를 넣는 것은 이번 프로젝트의 목적(신뢰성 메커니즘 검증)에 비해 과한 설계로 판단했다.

### 6. `HOST` 발송은 스텁으로 유지한다 (결정 사항, 근거: 스키마에 채널 필드 자체가 없음)

`hosts` 테이블에는 `contact_email`/`contact_phone`만 있고 API로 호출 가능한 웹훅/콜백 URL이 없다 — 이메일/SMS 발송은 이 프로젝트의 신뢰성 메커니즘(멱등성/재시도/Outbox) 검증 범위를 벗어나는 별도 인프라(메일 발송기 등)가 필요하다. 게다가 `plan/20.md`에서 이미 확인했듯 현재 4개 이벤트 타입 중 어느 것도 `HOST`를 대상으로 만들지 않는다 — 즉 이 분기는 지금은 절대 실행되지 않는다. 로그만 남기고 즉시 `SENT` 처리하는 최소 스텁으로 남겨두고, 실제로 호스트 대상 알림이 필요한 기능이 생기면(예: 향후 이슈) 그때 재설계한다.

## Testing Plan

reservation `#18`의 `MockRestServiceServer` 기반 테스트 전략을 그대로 재사용한다 (새 의존성 불필요).

- **OTA_CHANNEL 정상 발송**: `ota_channels` 픽스처(`callbackBaseUrl` 설정) + `PENDING` outbox_event 1건 → `MockRestServiceServer`가 그 `callbackBaseUrl`에 200 응답 등록 → `dispatchPendingOutboxEvents()` 호출 → `status=SENT` 검증. 요청 바디의 `outboxKey`/`reservationNo`/`eventType`/`payload`(raw JSON, 이중 인코딩 아님)를 `jsonPath`로 검증.
- **4xx/5xx/타임아웃 시 재시도 갱신**: `RestClientException` 계열 실패 응답 → `retry_count` 증가, `status=FAILED`, `next_retry_at` 백오프 검증 (#18과 동일 구조).
- **`callbackBaseUrl`이 없는 OTA 채널**: `callbackBaseUrl=null`인 채널 픽스처 → 발송 시도 → `retry_count` 증가, `status=FAILED`(HTTP 호출 자체가 발생하지 않았는지도 `MockRestServiceServer`의 미호출 검증으로 확인).
- **`target_code`에 해당하는 채널이 아예 없음**: 존재하지 않는 `platform_id`를 가진 `outbox_event` → 위와 동일하게 재시도 경로 검증.
- **`maxRetryCount` 초과 시 DEAD 전이**: #18과 동일한 방식.
- **HOST 스텁**: `target_type=HOST` outbox_event → `dispatchPendingOutboxEvents()` 호출 → 예외 없이 `status=SENT`로 즉시 전이하는지 검증 (실제 HTTP 호출이 없었음을 `MockRestServiceServer` 미사용으로 확인).
- **동시 워커 시뮬레이션(`SKIP LOCKED`)**: #18의 `CountDownLatch` 기반 동시성 테스트 패턴을 그대로 재사용해 `findBatchForDispatch` 레벨에서 검증.
- CI/로컬 실행 전제: Docker 데몬 필요(Testcontainers, MySQL) — #19/#20과 동일. **#19(엔티티/리포지토리), 이상적으로는 #20(TransactionConfiguration 등 설정 재사용)까지 먼저 병합돼 있어야 이 티켓의 구현을 시작할 수 있다.**
